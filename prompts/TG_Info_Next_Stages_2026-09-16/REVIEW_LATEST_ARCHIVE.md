## Вывод
Основа продукта уже реализована. Теперь главным ограничением является не отсутствие модулей, а точность перехода «публикация → утверждение → применимость к конкретному обращению → вывод → неизменный снимок». Расширять число источников и доверять досье для переговоров до исправления обнаруженных смысловых ошибок рискованно: отдельные корректно сохранённые факты могут применяться к не той стройке/работам.

## 3. Реестр замечаний
Приоритет — рекомендация по порядку исправления в локальном продукте, не заявление об эксплуатируемой публичной уязвимости. Репозиторий не подтверждает, что какой-либо реальный контрагент уже получил ошибочное досье.

### F01. Недостаточный контроль тестовой цели для benchmark
**Высокий перед изменяющими операциями. Статический анализ. Этап 10.**
`backend/src/release/cli.ts`: самостоятельная проверка имени базы регулярным выражением `/test/i` перед benchmark. При этом `backend/src/db/testTarget.ts` содержит более сильный механизм: выделенное подключение, разрешённая локальная цель, маркер и проверки фактической базы. Эти гарантии нужно использовать на всём пути до первой записи, в том числе auth harness.

Сам факт слова test в имени не доказывает безопасность записи. Это не воспроизведённое повреждение базы — БД не подключалась. Проверить нужно реальный flow CLI и повторное использование guard без тихого fallback.

### F02. Compare не проверяет содержимое, структуру трактует слишком мягко
**Высокий для доказательства восстановления. Код + R06/R07. Этап 10.**
`release/inventory.ts`, `diffInventory`: несовпадение миграций осталось только note, `equal=true`; отсутствующая обязательная таблица с прежним count=0 трактуется как ноль и тоже даёт equal. Количества не выявляют замену цитаты, реквизитов или смысла решения при том же числе строк.

Сохранить быстрые числа, добавить content-manifest и отдельное сравнение схемы/обязательных таблиц. Отсутствие необходимых данных/проверок не PASS. Сравнение restore и baseline должно относиться к одному состоянию; источник ролей/конфигурации окружения отдельно.

### F03. Ошибочный HTTP-ответ может участвовать в benchmark как измерение
**Средний, блокирует достоверный performance verdict. Код + пользовательский отчёт. Этапы 10/18.**
`release/bench.ts`: измеряет elapsed и записывает HTTP status, но результат не обязан быть успешным бизнес-ответом. В `evidence/09/USER_RUN.md` поиск HTTP400 занял 1ms; документ правильно отказывается считать это поиском. Путь уже исправлен, но общий механизм должен валидировать успешность каждого шага и состав отчёта.

### F04. Запланированная и реально используемая конфигурации модели не связаны жёстко
**Высокий до новых model experiments. Код + R10 с mocks. Этап 11.**
`reprocess/provider.ts` создаёт fingerprint; `runs.ts::enqueueRun` сохраняет его. `claimNextRun` переносит в claim chunker, а `processRun` принимает runtime provider без проверки полного сохранённого fingerprint. `worker.ts` берёт текущую конфигурацию.

Следствие по структуре кода: настройка A может остаться записанной как основание запуска, который обработается текущим B; resume может смешать несовместимые конфигурации. Изолированное исполнение подтвердило отсутствие чтения/сверки fingerprint в processRun; реальную смену модели/серверов и DB race здесь не испытывали. Нужен config mismatch gate, а не редактирование подписи у старого результата.

### F05. Отзыв допуска после начала многочанкового запуска
**Высокий до живых материалов. Код + R09 с mocks. Этап 11.**
`runs.ts`: допуск проверяется при enqueue/claim и отдельно при publication, но в цикле `processRun` перед каждым `provider.extract` повторного gate нет. После симулированного отзыва между двумя chunks выполнены оба вызова. Защита публикации не отменяет уже выполненную обработку второго текста.

Нужны checks перед каждым новым outbound/retry, безопасное прекращение и понятный статус. Уже отправленный запрос нельзя гарантированно «забрать назад»; это отдельная граница, которую надо честно отражать.

### F06. Неверная область роли/отрицания/договора в досье обращения
**Высокий для основного продукта. Код + R01–R05. Этап 12.**
`backend/src/dossier/caseDossier.ts`:
- неизвестный project у contract проходит `onProject`, и chain становится `documented` для выбранной стройки (R01);
- negative по корпусу 1 делает роль `contradicted` по корпусу 2 (R02);
- negative со status rejected продолжает менять итог роли (R03);
- unknown scopeBuilding считается совпадающим с выбранным корпусом и попадает в established (R04);
- contract на другой корпус/вид работ того же объекта подтверждает chain текущего обращения (R05).

Контроль C01: положительное участие в явно другом корпусе правильно вынесено в otherBuildings. Значит, требуется согласовать все ветки, а не утверждать, что scope вообще отсутствует.

Главное исправление: общий scope comparator (объект/корпус/работы/роль/период); unknown даёт контекст/пробел, не подтверждение. Отклонённое аналитиком утверждение не должно решать текущий вывод, но историческая запись сохраняется. При действительно применимом отрицании наличие analyst_reviewed само по себе не снимает противоречие.

### F07. Ключ снимка не проверяется на совпадение намерения запроса
**Высокий для правильности выдачи, не подтверждённая межпользовательская утечка. R08. Этап 13.**
`snapshot/repository.ts::createSnapshot`: найденный idempotency_key немедленно возвращает snapshot id/hash без сверки case и filters. В mocked lookup ключ от одного запроса вернулся при новом caseId. Это может дать не то досье и не требует большого объёма данных.

Решение: request identity с известной нормализацией/версией; повтор того же намерения возвращает прежний snapshot, другое намерение с тем же key отвергается. Возможные конкурентные unique conflicts — отдельный integration test, не доказанный этим изолированным случаем.

### F08. Часть snapshot metadata читается вне snapshot transaction
**Высокий для целостности снимка. Статический риск конкуренции, не воспроизведённая DB race. Этап 13.**
`snapshot/repository.ts` начинает REPEATABLE READ; `snapshot/build.ts` вызывает `refreshState()`; `signals/refresh.ts::refreshState` получает общий pool вместо переданного transaction executor. Аналогично `dossier/load.ts`.

Следовательно, само наличие REPEATABLE READ у внешней функции не гарантирует общую точку чтения всех зависимостей. Исправить передачу executor и добавить настоящий barrier-based DB тест. Многобатчевую генерацию signals также проверить на согласованное состояние.

### F09. Метаданные latest revision используются для старого evidence
**Средний/высокий для происхождения и аналитики. Статический анализ. Этап 13.**
`signals/load.ts`: evidence связан с revision, но publications берутся через последнюю revision на cutoff, затем evidence группируется только по source_item_id. completeness/dedup_hash могут относиться не к редакции-основанию.

Нужны отдельные понятия evidence revision и latest observed revision. Правка, ещё не прошедшая извлечение, не должна менять задним числом происхождение старой цитаты/кластер перепечаток.

### F10. Ограниченные выборки могут выглядеть полными
**Высокий до увеличения корпуса. Статический анализ. Этапы 13/15/18.**
`dossier/facts.ts`: ORDER BY id LIMIT1000 возвращается как IFact[] без полноты; `graph/load.ts`: LIMIT2000 до части последующих фильтров, co-mention LIMIT500; есть локальные ограничения evidence/reviews/queues. Graph node truncation — не то же самое, что truncation загрузки.

Поздние факты могут не попасть в ответ, а UI не сообщит, что данные ограничены. Решение — bounded paging/filtering + coverage envelope/hasMore, а не безлимитное чтение всего.

### F11. Legacy shadow/compare не измеряет текущий контур
**Высокий для выбора улучшений модели. Статический анализ. Этап 14A.**
`pipeline/compare.ts` использует legacy raw_documents/extractions и `extractFromText`; в `llm/client.ts` это extract@2. Текущий worker — semantic extract@3. README/CLAUDE по-прежнему предлагают старый путь оценки.

Нужно явно отделить legacy и сделать current evaluation теми же версиями extraction/verification/assembly, что рабочий pipeline. Сравнение по model+prompt без остальных параметров недостаточно воспроизводимо.

### F12. Ошибки модели могут уменьшать число проверок
**Высокий для честного качества. Статический анализ. Этап 14A.**
`reprocess/semantic/benchmark.ts`: error-case получает checks:[], сводка строится из фактически имеющихся checks. Из-за этого ошибки не входят в прежний знаменатель успешности; пустой выбор и partial/truncated input требуют явного неприемлемого verdict. Gate нельзя строить на доле среди только успешно разобранных ответов.

Сначала planned evaluation matrix, затем PASS/FAIL/ERROR/NOT_RUN, отдельно от числовых extraction metrics.

### F13. Диагноз недостаточной полноты пока неполон
**Продуктовый блокер для автоматических выводов. Документы. Этап 14B.**
3/9 checks и 24/25 safety зафиксированы, но отсутствует raw JSON, а причина каждого пропуска может быть в парсере/chunker/model/verifier/resolver/dossier. Нельзя сразу назначать fine-tuning или замену модели. Нужен каталог ошибок и paired эксперименты на текущем корректном scorer.

### F14. Нет законченного рабочего пути разрешения identity ambiguity
**Средний. Код/UI. Этап 15A.**
ReviewQueuePage и MergeQueuePanel уже есть. `api/entities.routes.ts` выдаёт ambiguities, но текущий обзор не обнаружил законченного UI/action workflow именно разрешения одного упоминания; переход в admin не равен решению. Добавлять адресно, не объявляя отсутствующей всю ручную проверку.

### F15. Решения после merge должны быть доступны с границами действия
**Средний, станет высоким если исчезает важное решение в реальном сценарии. Код/контракт. Этап 15A.**
`resolve/entityMerge.ts` сохраняет старые assertions и создаёт/переносит поддержку к новым, отзывы остаются у исходных. Это может быть правильной историей, не обязательно ошибка FK. Необходимо сделать lineage доступной каноническому досье и проверять применимость, а не перенести все решения массовым UPDATE.

### F16. API запусков есть, операторского контура недостаточно
**Средний. Код/UI. Этап 15B.**
`api/reprocess.routes.ts` уже даёт runs/preview/publish. Нужен связный экран текущего semantic pipeline, ошибок, chunk coverage, ревизий и проверки candidates; не новый второй backend. Default autopublish остаётся false.

### F17. Источники требуют профилей и пользовательской валидации
**Средний; permission gate высокий. Архитектура/документы. Этап 16.**
В новом архиве website/Telegram сбор существенно развиты, поэтому старое заключение «есть только RSS» сюда не переносится. Следующий шаг — проверка конкретных адресов/профилей и observable coverage, а не универсальное обещание любой сайт/весь Telegram. Живых валидированных источников нет.

### F18. Резюме должно отвечать на предмет обращения
**Продуктовая рекомендация. Этап 17.**
Сохранить существующие досье, улучшить короткий вывод для переговоров: прямой контрагент/роль/корпус/работы, неизвестное, применимые события и вопросы. Общий фон отдельно; перепечатки не независимые подтверждения; судебная сумма не автоматически долг. Не возвращать светофор надёжности.

### F19. UI и нагрузочная проверка не закрыты соответствующими тестами
**Средний. Документы/код. Этап 18.**
В архиве нет полноценной browser regression, print/390px NOT_RUN. Маленький synthetic benchmark и unit не доказывают UX/нагрузку. Подготовить тесты и измерения, запускаемые пользователем, адресно оптимизировать после profiling.

### F20. Нужен явный ограниченный переход к реальным данным
**Процессная рекомендация. Этап 19.**
Статусы fixture/model/sources правильно разделены. Сохранить это при пилоте: отдельный manifest разрешений/области/конфигурации/ручного review и stop conditions. Новый пакет не разрешает рабочую миграцию, публичный доступ или постоянный сбор.

## 4. Что не рекомендую менять сейчас
Не переписывать сбор/ревизии/утверждения целиком; не вводить Neo4j/ORM/microservices; не начинать fine-tuning; не включать background job flags ради красивого демо; не расширять количество источников раньше контроля контекста и качества. Не заменять локальную модель на Claude лишь потому, что Claude используется для разработки.

Не нужно «опровергать» все принятые ранее тесты или начинать 09 заново. Вместо этого — точечные regression tests для F01–F12 и сохранение уже работающего поведения.

## 5. Последовательность
10: release/guards → 11: execution identity/policy → 12: scope → 13: snapshots/coverage → 14A: truthful evaluation → 14B: controlled quality improvement → 15A: identity decisions → 15B: run workbench → 16: source onboarding → 17: business dossier → 18: UI/performance → 19: pilot.

Это не обязательно 12 одинаково больших итераций: каждый этап имеет отдельный gate и отчёт. Без допуска к реальной модели/источникам разрешённая офлайн-разработка продолжается там, где она независима; результаты REAL_MODEL/LIVE_SOURCE не выдумываются.

## 6. Внешние технические основания
Проверены официальные источники 16.09.2026; список — [reference/SOURCES.md](reference/SOURCES.md). PostgreSQL описывает снимок данных внутри repeatable-read транзакции; это основание проверки F08, но конкретная ошибка установлена по коду проекта. pg_dump делает согласованный дамп одной БД; отдельный inventory вне него требует согласованной последовательности. LM Studio поддерживает schema-based output; семантическая истинность и полнота остаются задачей вашего verification/evaluation. Условия Telegram требуют отдельного рассмотрения прав использования контента; approval в приложении должен отражать реальное основание, а не создавать его.

**Итог:** проект стал существенно ближе к рабочему инструменту. Главная ближайшая ценность — не ещё один экран и не новая модель, а отсутствие ложных связей в конкретном обращении, воспроизводимые выводы и понятное оператору происхождение каждой строки.
