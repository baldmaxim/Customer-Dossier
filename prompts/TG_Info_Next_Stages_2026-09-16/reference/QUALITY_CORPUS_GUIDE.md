# Корпус и измерение качества

## Что уже имеется
В репозитории есть SYN01–SYN17 и старые результаты с checks. Сохранить их. Приложенный `SYNTHETIC_CASES.json` — **24 дополнительные авторские синтетические ситуации для регрессии**, не новый размеченный промышленный датасет и не проверенные результаты модели. Они видимы разработчику, поэтому не называются скрытым holdout.

Тексты вымышленные; `SYN_*` обозначает фикстурные сущности, а INN_A/B — параметры тестового генератора. В реестр источников и рабочих компаний они не импортируются автоматически. Эти placeholders не должны становиться «извлечёнными реквизитами» настоящих компаний.

## Уровни проверки
1. Получение текста: источник/редакция/полнота/дата. Модель не может извлечь то, что не скачано.
2. Raw extraction: выраженные в тексте компании/объекты/роли/события с цитатами.
3. Verification/assembly: кто именно относится к числу/отрицанию/договору; корректное объединение чанков.
4. Identity resolution: юридическое лицо и объект, а не похожее имя.
5. End-to-end: тот же scope/evidence принят и правильно показан в досье нужного обращения.

Отдельно инфраструктурные errors и invalid/truncated output. Если для end-to-end нужны реальные source policy/DB, это пользовательский test fixture, не необъявленный сетевой запуск.

## Разметка
Для каждого материала: synthetic/permission status, caseId и original-cluster id, текст/версии, ожидаемые assertions (predicate, участники, project, building, work, period, polarity, modality), exact supporting spans/quotes, запрещённые выводы, допустимые unknown и отрицательные примеры. Event date отличается от publication date. Извлечение цитаты не подтверждает юридическую истинность.

Разметка первична относительно вывода модели. Спорные gold labels хранить как unresolved и разрешать человеком; не назначать ground truth большинством одинаковых моделей. Нужны версии annotation guideline и adjudication reason. Для важных классов (идентичность, direct contract, отрицание, суммы/стадии суда) разметку желательно перепроверять вторым человеком, когда такой ресурс доступен.

## Метрики
План case/check составить заранее. Сводка: planned cases/checks, evaluated, errors, skipped, mandatory failed. Если все cases упали, результат непригоден, а не 100% среди пустого списка.

При настоящем reference set: TP/FP/FN по типам facts и matching rule. Exact match scope и relaxed name normalization — разные метрики. Наказывать ложный прямой договор отдельно от пропуска второстепенного упоминания. Unknown не засчитывать как правильный конкретный ответ.

24/25 safety checks и 3/9 recall checks в прежнем отчёте — именно checks. Не называть их точностью 96% и полнотой 33% всей системы. Не объявлять общее качество по 17 коротким материалам.

## Разделение выборок
Dev для промтов/исправлений; regression для всех известных ошибок; holdout для финальной проверки после заморозки. Одна публикация, её редакции и перепечатки одного origin — в одном split. Новое название сайта не делает текст независимым. После просмотра holdout с целью настройки он перестаёт быть скрытым тестом.

Размер первоначального реального пилотного корпуса — предмет ограниченного пользовательского решения, а не обещание статистической достаточности. Можно подготовить стратифицированную форму для 30–50 разрешённых материалов, но не считать это обязательной нормой или гарантией. В неё нужны короткие и длинные тексты, разные источники, роли, unknown/negative и плохой HTML, а не только хорошие пресс-релизы.

## Эксперимент
Каждый variant: frozen config, corpus hash/split, prediction budget, версии scorer/validation, planned changes, gate thresholds до прогона. Обязательные safety не ослабляются. Выбор варианта по явной paired таблице per fact type; ошибки и пропуски не скрываются.

Предложенный gate до ограниченного пилота: все обязательные safety регрессии пройдены, planned cases учтены, нет регрессии scope/history/policy, output failures отдельно, по каждому критичному типу фактов есть человеческая оценка полноты. Количественные targets согласовать до просмотра holdout и обозначать как цели, не уже достигнутые показатели.

Реальные тексты/ответы модели хранятся локально по допустимому основанию. В cloud IDE/chat разрешено передавать только допустимую часть материалов; наличие пакета промтов не даёт прав на их отправку.
