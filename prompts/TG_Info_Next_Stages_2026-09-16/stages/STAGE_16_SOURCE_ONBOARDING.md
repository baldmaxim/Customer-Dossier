# Этап 16 — Подключение и наблюдаемость конкретных источников

Ты — основной инженер реализации существующего TG_Info / Customer Dossier. Выполни **только этот этап**, не весь пакет. Обязательны `../COMMON_RULES.md` и текущие пользовательские ограничения. Не начинай с переписывания проекта.

## Результат для владельца
Каждый выбранный сайт/канал имеет проверяемый профиль, историю покрытия и понятный статус: действительно пусто, не было запуска, потерян диапазон или сломался парсер.

## Предпосылки и основания
**Зависимости:** 11, 13, 15B. Live-source validation — только для источника с реальным разрешением; готовность адаптера можно проверить offline.
**Замечания анализа:** F17; уже реализованные website/Telegram адаптеры не переписывать. Подробности и границы доказательств — `../REVIEW_LATEST_ARCHIVE.md`.
Сначала проверь, воспроизводится ли это на фактической ветке: исправленные места не менять повторно. Исторический PASS этапа 09 сохраняется с прежней областью; новые дефекты и проверки вести отдельно.

## Прочитать до изменений
- `backend/src/ingest/{website,telegram,sources,store}.ts` или фактические аналоги, shared safeFetch и robots/allowlist handling.
- Source policy API/editor, `frontend/src/components/SourceHealth.tsx`, source cursors и fetch-attempt history.
- ADR-006/007, `../reference/SOURCE_PILOT_TEMPLATE.md`, текущие пользовательские ограничения.
Также прочитай относящиеся к области ADR, предыдущие stage reports и `../reference/ACCEPTANCE_MATRIX.md`. Имена/номера файлов — навигация по архиву, а не требование создать дубль после рефакторинга.

## Что реализовать
1. Составить реестр возможностей текущих адаптеров: RSS/full article/HTML list, Telegram web preview/cursor/edit, bot как отдельный режим. Помечать фактическое покрытие, не утверждать полную историю канала по окну свежих постов. Не переносить старую найденную в первой версии ошибку «нет HTML» на этот архив без проверки.
2. Ввести versioned source profile: allowed origins/paths, способ сбора, list/article selectors, pagination/end condition, timezone/date formats, content completeness, restrictions, frequency/budget, owner и permissions evidence. Unknown по умолчанию; проверка parser config не выдаёт допуск на AI.
3. Offline contract-tests из фиксированных HTML/RSS/Telegram-представлений: полная статья vs анонс, пустая страница, paywall/баннер/anti-bot, изменившаяся верстка, повтор pagination, правка поста, удалённая/недоступная публикация, неизвестная дата, вложение без текста. Не запускать OCR/распознавание изображений автоматически; вложение отмечать как необработанное.
4. Health должен различать never_run, healthy, degraded, policy_blocked, temporary_error, partial_history/gap. Изменение селекторов/резкий обвал извлечённого текста не превращается в «новостей нет». Метрики количества — не гарантированная полнота; там, где total источника неизвестен, писать неизвестно.
5. Cursor/checkpoint только после атомарной записи результата по утверждённому контракту. Ошибка на поздней странице/вставке не проглатывает диапазон. Ограниченный retry с backoff и rate budget; interruption resume воспроизводим. Отдельно latest revision и changes pending extraction.
6. Сохранить safeFetch: allowlist, проверка redirect/DNS/IP назначения и лимитов тела/времени по текущему контракту. Новые ручные URL/preview не обходят этот путь. Не делать загрузку произвольной сети по URL из текста статьи. Cache и ETag условны по поддержке, без выдуманного «не изменялось».
7. В интерфейсе подключения показывать dry-run результат и текстовые фрагменты с редакцией без автопубликации. Пользователь самостоятельно заполняет основание и допускает действие; не создавать approved synthetic fixture в рабочем реестре.
8. Подготовить по одному профилю-шаблону сайта и Telegram канала, но адреса/права оставить неутверждёнными. Без указанного разрешённого списка результат READY_FOR_OPERATOR_CONFIG, LIVE_SOURCE_VALIDATED остаётся пустым.

## Критерии приёмки и регрессии
- T16-01…T16-08. Корректная пустая лента и сломанный selector имеют разные статусы.
- Только анонс не помечается full article; дата unknown не today.
- Redirect на запрещённую цель/loopback не выполняется; права на сбор не означают права на AI.
- Поздняя ошибка страницы не продвигает cursor за потерянные сообщения; повтор не удваивает revision.
- Изменённый текст создаёт новую revision с прежней source identity.
- Telegram preview не заявляет полный backfill; восстановленный диапазон документирован фактическими границами.
- Неизвестный total coverage честно unknown.
Проверки должны утверждать правильное поведение, а не подстраивать ожидание под обнаруженный дефект. Не помечать готовность по одному числу тестов. Ошибки и NOT_RUN перечислять явно.

## Прогон пользователя
Пользователь может выполнить ограниченный dry-run только после явного списка URL/каналов и оснований. Сначала один выбранный сайт, затем один канал отдельно; небольшой фиксированный диапазон, обработчики по умолчанию выключены. Для неподтверждённых источников live NOT_RUN. В отчёте отдельные результаты collection, content completeness и AI policy.
Агент подготавливает точные команды под существующие scripts и PowerShell/Git Bash, но не выполняет Docker/БД/browser/model/network. Перед каждой изменяющей командой указать цель, побочный эффект, способ убедиться в тестовом контуре и ожидаемый результат. Не включать рабочие URL/пароли в пример.

## Не делать
Не обходить ограничения сайтов/Telegram, не заменять web preview на сбор приватных сообщений/MTProto без запроса, не вставлять чужие ключи, не считать публичность разрешением, не подключать условный example.invalid как реальный approved источник.
Дополнительно действуют все ограничения COMMON_RULES. Не открывать новый этап, не публиковать данные и не менять глобальные флаги автоматически.

Сохранить `docs/development/stages/16_REPORT.md`, handoff и форму пользовательского прогона `docs/development/evidence/16/USER_RUN.md`. Указать, какие контракты/индексы/миграции затронуты, как прежний код читает старые данные и как остановить новую функцию без потери истории. При отсутствии миграций написать это явно.

В финале показать выполненные проверки, незапущенные проверки, открытые дефекты и точное следующее действие пользователя. **Остановиться после этапа 16.**
