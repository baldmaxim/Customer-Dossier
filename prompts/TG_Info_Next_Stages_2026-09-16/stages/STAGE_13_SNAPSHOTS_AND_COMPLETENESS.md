# Этап 13 — Согласованный снимок и честная полнота выборки

Ты — основной инженер реализации существующего TG_Info / Customer Dossier. Выполни **только этот этап**, не весь пакет. Обязательны `../COMMON_RULES.md` и текущие пользовательские ограничения. Не начинай с переписывания проекта.

## Результат для владельца
Снимок принадлежит именно заданному обращению, собран из одного согласованного состояния и явно сообщает об ограничении выборки или новой необработанной редакции.

## Предпосылки и основания
**Зависимости:** 10 и 12; runtime-инварианты 11 сохранить. Старые immutable snapshots не переписывать.
**Замечания анализа:** F07, F08, F09, F10; R08. Подробности и границы доказательств — `../REVIEW_LATEST_ARCHIVE.md`.
Сначала проверь, воспроизводится ли это на фактической ветке: исправленные места не менять повторно. Исторический PASS этапа 09 сохраняется с прежней областью; новые дефекты и проверки вести отдельно.

## Что реализовать
1. Idempotency: одинаковый key нельзя повторно использовать для другого case/фильтров/формата. Определи нормализованный request identity; прежнее совпадение возвращает тот же snapshot, несовпадение — явный 409/422, не чужой payload и не 500. Проверь actor/ownership в рамках существующей модели одного оператора. Отличай повтор операции от запроса «сделать новый снимок актуального состояния» — ему нужен новый ключ. Case version/expected version согласовать явно, не ломая настоящий повтор после изменения live case.
2. Конкурентный повтор одинакового key должен обрабатываться предсказуемо при unique conflict/isolation retry. Для старых записей без request hash прочитать неизменный payload и безопасно восстановить только действительно сохранённые параметры; неизвестность не выдавать за совпадение. Не менять старый payloadHash ради добавления метаданных.
3. Проверь все read dependencies построения. Сейчас `refreshState()` обращается к общему pool вне переданного snapshot transaction. Все влияющие на снимок чтения должны использовать тот же client/executor; глобальное состояние refresh либо фиксируется тем же чтением, либо явно выносится из исторического payload по версионированному контракту. Обоснуй snapshot isolation и commit/retry, не держи транзакцию во время внешних вызовов. Для refresh-generation обеспечь целостный ввод/публикацию поколения, не смешивая партии разных состояний без отметки.
4. Доказательство связано с конкретной revision. В signals/load не заменять её completeness/dedup/provenance метаданными latest revision. Разделить «редакция основания» и «последняя наблюдаемая редакция публикации». Новая необработанная правка отражается как pending/stale, а не делает старую цитату якобы актуальной. Перепечатки группировать по содержимому соответствующего основания.
5. Инвентаризируй лимиты: dossier facts 1000, graph 2000/500, evidence/reviews, очереди. Верни envelope coverage с loaded/hasMore и известным total либо totalUnknown. Фильтры объекта/работ/типа/периода применять до лимита, где возможно. Node-budget графа и лимит исходных связей — разные причины truncation; отражать обе.
6. Сохрани ресурсные границы: пагинация/cursor, стабильный tie-breaker, server maximum, bounded depth и ограниченный экспорт. Не решать молчаливую неполноту удалением LIMIT. Неполная выборка не может формулировать «других сведений нет». Coverage включается в новый snapshot и печатное/JSON/Markdown представление.
7. Исторический knowledgeCutoff, если ранее запрещён без temporal-модели, оставить честно запрещённым. Не обещать полный time-travel из фильтра по publication date.

## Критерии приёмки и регрессии
- T13-01…T13-12. R08: key от case A при запросе B отвергается. Одинаковый intent повторяет A даже если живое досье позднее изменилось, по выбранному контракту идемпотентности.
- Реальные конкурентные интеграционные тесты с barrier: refresh/rename/review commit между чтениями не создаёт гибридный snapshot; use same executor проверяется unit дополнительно.
- Payload/hash/HTML старого snapshot идентичны после правки/merge/refresh.
- Старое evidence revision1 + latest revision2 с другим completeness/dedup: provenance остаётся revision1, pending revision2 виден отдельно.
- 1001+ facts и 2001+ edges: найденное после старой границы не теряется тихо; пагинация не дублирует/не пропускает, фильтрация до truncation; экспорт предупреждает об ограничении.
- Неизвестный total не подменяется loaded как будто полный.
Проверки должны утверждать правильное поведение, а не подстраивать ожидание под обнаруженный дефект. Не помечать готовность по одному числу тестов. Ошибки и NOT_RUN перечислять явно.

## Прогон пользователя
Подготовить отдельные marked-test фикстуры для гонок snapshot, одинаковых ключей, большого связного набора и двух редакций. Пользователь выполняет DB concurrency и browser export; агент выполняет чистые сериализационные/coverage unit без БД. Snapshot restore-сравнение из этапа 10 повторяется на новой версии формата.
Агент подготавливает точные команды под существующие scripts и PowerShell/Git Bash, но не выполняет Docker/БД/browser/model/network. Перед каждой изменяющей командой указать цель, побочный эффект, способ убедиться в тестовом контуре и ожидаемый результат. Не включать рабочие URL/пароли в пример.

## Не делать
Не пересчитывать старые снимки, не выдавать mock конкуренции за PostgreSQL race test, не кэшировать live досье внутри snapshot без версии входа, не увеличивать лимиты до бесконечности, не заявлять полный исторический срез.
Дополнительно действуют все ограничения COMMON_RULES. Не открывать новый этап, не публиковать данные и не менять глобальные флаги автоматически.
