# Этап 15B — Рабочее место контроля запусков и публикации

Ты — основной инженер реализации существующего TG_Info / Customer Dossier. Выполни **только этот этап**, не весь пакет. Обязательны `../COMMON_RULES.md` и текущие пользовательские ограничения. Не начинай с переписывания проекта.

## Результат для владельца
Оператор видит, почему текст не попал в досье, проверяет кандидатов по цитатам и управляет отдельным запуском без скрытого массового переразбора.

## Предпосылки и основания
**Зависимости:** 11, 13; 15A для единых review-компонентов. 14A scorer готов, качество реальной модели может оставаться отдельным NOT_RUN.
**Замечания анализа:** F16, F10. Подробности и границы доказательств — `../REVIEW_LATEST_ARCHIVE.md`.
Сначала проверь, воспроизводится ли это на фактической ветке: исправленные места не менять повторно. Исторический PASS этапа 09 сохраняется с прежней областью; новые дефекты и проверки вести отдельно.

## Прочитать до изменений
- `backend/src/api/reprocess.routes.ts`, revisions routes, run/candidate/publish service.
- `frontend/src/pages/AdminPage.tsx`, `DocumentPage.tsx`, review components, source health и auth client.
- Существующие GET runs, preview и POST publish; не создавать параллельное API без причины.
Также прочитай относящиеся к области ADR, предыдущие stage reports и `../reference/ACCEPTANCE_MATRIX.md`. Имена/номера файлов — навигация по архиву, а не требование создать дубль после рефакторинга.

## Что реализовать
1. Добавь список запусков с фильтрами по источнику/редакции/статусу/schema/model fingerprint, pagination, start/end, coverage chunks и policy reason. Значения должны идти из current pipeline, не legacy counters. Неизвестную latency/расход токенов не вычислять из догадки.
2. Детальная страница: опубликованная редакция и новая версия, run lineage, ошибки по чанкам, verification reasons, принято/отклонено/неоднозначно, полная цитата в своей редакции. Покажи pending latest revision отдельно от основания текущего факта.
3. Preview перед publish: новые/изменяемые/superseded assertions, влияние на текущие досье, scope, конфликты, решения, которые сохраняются. Не превращать количества кандидатов в подтверждённые факты.
4. Enqueue/retry/cancel/preview/publish — только явные точечные действия по ID, через общий policy/execution gate. Если endpoint отсутствует, добавь минимальный с auth/CSRF/idempotency/version. Бounded batch можно только preview+явное подтверждение списка, default не auto. REPROCESS_AUTO_PUBLISH остаётся false.
5. Publish отвергает stale preview при новой ревизии/policy/decision/fingerprint, а не публикует расчёт по старому состоянию. Нельзя публиковать incomplete/truncated/failed/mismatch. Объяснение отказа даёт следующую безопасную операцию.
6. Cancel означает остановить дальнейшие шаги; явно отображать in-flight запрос, который уже мог уйти. Переотправка successful chunk не происходит бесконечно. Не добавлять механизмы, позволяющие UI обойти lease fencing.
7. Ошибки соединения/401/403/500 различаются от пустого списка. Очередь identity с этапа 15A связана ссылкой с run, но не создаёт цикл «автоматически разрешить→слияние→publish».

## Критерии приёмки и регрессии
- T15B-01…T15B-07. Один невалидный/timeout chunk видно в UI с причиной; canon не изменился.
- Отозван допуск между preview/publish → отказ; latest revision изменилась → stale preview.
- Retry same intent идемпотентен; cancel прекращает будущие calls, не обещает удаление уже отправленного.
- Без cookie/CSRF/с чужим Origin ничего не пишет; backend flag false нельзя обойти кнопкой.
- Из общего review можно открыть свою цитату/revision/run, а не только статью latest.
- 101+ runs не теряются за первой страницей.
Проверки должны утверждать правильное поведение, а не подстраивать ожидание под обнаруженный дефект. Не помечать готовность по одному числу тестов. Ошибки и NOT_RUN перечислять явно.

## Прогон пользователя
Пользователь на synthetic DB выполняет: enqueue→просмотр failed→retry→preview→изменение решения/допуска→stale publish отказ→актуальный preview→разрешённая публикация. Используется deterministic provider; живые источники не нужны. Browser E2E запускает пользователь.
Агент подготавливает точные команды под существующие scripts и PowerShell/Git Bash, но не выполняет Docker/БД/browser/model/network. Перед каждой изменяющей командой указать цель, побочный эффект, способ убедиться в тестовом контуре и ожидаемый результат. Не включать рабочие URL/пароли в пример.

## Не делать
Не включать scheduler ради интерфейса, не добавлять кнопку «переобработать всё» без предохранителей, не печатать prompts с секретами/реальными материалами в общие логи, не ставить analyst_confirmed для модельных кандидатов.
Дополнительно действуют все ограничения COMMON_RULES. Не открывать новый этап, не публиковать данные и не менять глобальные флаги автоматически.
