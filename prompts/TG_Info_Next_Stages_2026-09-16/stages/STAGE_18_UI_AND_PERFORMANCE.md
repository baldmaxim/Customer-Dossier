# Этап 18 — Регрессия интерфейса и измеряемая скорость

Ты — основной инженер реализации существующего TG_Info / Customer Dossier. Выполни **только этот этап**, не весь пакет. Обязательны `../COMMON_RULES.md` и текущие пользовательские ограничения. Не начинай с переписывания проекта.

## Результат для владельца
Ежедневный маршрут аналитика работает на разных размерах окна, ошибки не маскируются, а ускорения обоснованы реальными замерами.

## Предпосылки и основания
**Зависимости:** 13, 15A–17. Baseline этапа 09 маленький и не содержит успешного поиска, не использовать его как нагрузочный SLA.
**Замечания анализа:** F03, F10, F19. Подробности и границы доказательств — `../REVIEW_LATEST_ARCHIVE.md`.
Сначала проверь, воспроизводится ли это на фактической ветке: исправленные места не менять повторно. Исторический PASS этапа 09 сохраняется с прежней областью; новые дефекты и проверки вести отдельно.

## Прочитать до изменений
- Frontend pages/components/API/session/cache purge/PWA, package scripts и existing tests.
- Release bench этапа 10, queries dossier/graph/signals и explainable coverage.
- `evidence/09/USER_RUN.md`: print/390px NOT_RUN, поиск HTTP400; существующие source/snapshot browser сценарии.
Также прочитай относящиеся к области ADR, предыдущие stage reports и `../reference/ACCEPTANCE_MATRIX.md`. Имена/номера файлов — навигация по архиву, а не требование создать дубль после рефакторинга.

## Что реализовать
1. Добавить минимальную автоматизацию компонентов/маршрутов на синтетических API fixtures: поиск омонимов, case form, scope statuses, policy отказ, queue paging, stale preview, snapshot replay conflict, truncation, error vs empty. Переиспользовать текущий test stack; новую зависимость обосновать, не переписывать frontend.
2. Подготовить E2E (например, выбранный существующим стеком browser runner) на marked synthetic test окружении. Агент пишет тесты, browser запускает пользователь. Включить login/logout, CSRF/Origin, queue review, source revision, snapshot/HTML/print, 390px и обычное окно. Печатные страницы без обрезки и с доказательствами; manual PDF NOT_RUN нельзя превратить в PASS component test.
3. Проверить защиту вывода untrusted strings, ссылки, logout/session reset и отсутствие dossier/API payload в неуправляемом PWA cache. Это проверка, не предположение о найденной XSS/утечке. Не «исправлять» существующий рабочий cachePurge вслепую. Использовать вымышленные secrets-canaries вместо поиска общих слов token.
4. В бенчмарке запросы проходят реальный auth/middleware, все обязательные responses валидны. Публикуется объём/форма синтетических данных, Node/машина/concurrency, warm-up, repetitions, elapsed, error count, per-step p50/min/max; дополнительные p95 допустимы при указании N и ограничения малой выборки. Не сравнивать несопоставимые наборы.
5. Создать воспроизводимый bounded большой synthetic набор, ориентированный на найденные пределы: >1000 facts по компании, >2000 edges, множество редакций/решений. Генератор только test-target guard, deterministic seed, не реальные компании. Размер и запуск подтверждает пользователь; не заливать бесконтрольно миллионы строк.
6. По пользовательским EXPLAIN/профилю найти дорогие queries и N+1, затем адресные индексы/пагинация/выборки с regression. Не удалять security checks и evidence joins ради скорости. Индексы additive и по реальным планам, не угадывать «ускорит в 10 раз».
7. Кэшировать только при доказанной необходимости, с ключом source version/identity/review/generation/scope и правильной инвалидизацией. Иммутабельный snapshot отличается от live dossier. Redis и отдельный search engine вне этапа.
8. Низкая память/DB down/API error должны показывать контролируемый отказ, а не благополучное пустое досье. Уточнить достаточные machine-specific budgets после прогона, не превращать tiny fixture latency в гарантию.

## Критерии приёмки и регрессии
- T18-01…T18-08. Component tests включают negative states; browser/print выполнены отдельно либо NOT_RUN.
- Выход/смена session не показывает прошлое досье из клиентского кеша.
- Вредоносная строка не исполняется/не ломает ссылки и экспорт; canary не в логах и bundle.
- Синтетика после прежних LIMIT видна через paging/coverage без ложного «всё».
- Прежде/после одинаковые данные/окружение, оба корректны по HTTP/payload, ошибки не входят в успешный latency.
- Индекс/оптимизация не меняет содержимое досье и snapshot hash на одном входе.
- Нет обещанных SLA без пользовательского замера.
Проверки должны утверждать правильное поведение, а не подстраивать ожидание под обнаруженный дефект. Не помечать готовность по одному числу тестов. Ошибки и NOT_RUN перечислять явно.

## Прогон пользователя
Пользователь запускает browser regression, печать в PDF и узкое окно 390px, затем bounded dataset+EXPLAIN+release:bench. Вновь отметить, что bench создаёт snapshots и не выполняется между baseline и dump. Unit/typecheck/build агент выполняет только при доступных зависимостях и без побочных actions.
Агент подготавливает точные команды под существующие scripts и PowerShell/Git Bash, но не выполняет Docker/БД/browser/model/network. Перед каждой изменяющей командой указать цель, побочный эффект, способ убедиться в тестовом контуре и ожидаемый результат. Не включать рабочие URL/пароли в пример.

## Не делать
Не запускать браузер/БД агентом, не добавлять инфраструктуру ради предполагаемой нагрузки, не завершать все Node-процессы для освобождения памяти, не подменять end-to-end check скриншотом моковой страницы.
Дополнительно действуют все ограничения COMMON_RULES. Не открывать новый этап, не публиковать данные и не менять глобальные флаги автоматически.
