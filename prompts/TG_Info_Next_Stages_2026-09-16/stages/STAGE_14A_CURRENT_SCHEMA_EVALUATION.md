# Этап 14A — Единая проверка качества текущей схемы

Ты — основной инженер реализации существующего TG_Info / Customer Dossier. Выполни **только этот этап**, не весь пакет. Обязательны `../COMMON_RULES.md` и текущие пользовательские ограничения. Не начинай с переписывания проекта.

## Результат для владельца
Проверяется именно extract@3 и действующий путь формирования доказательств, а ошибки модели не исчезают из расчёта качества.

## Предпосылки и основания
**Зависимости:** 11, 12, 13: происхождение запуска и правильные scope/read semantics. Разрешённая синтетика; реальная модель вызывается только пользователем.
**Замечания анализа:** F11, F12, F13. Подробности и границы доказательств — `../REVIEW_LATEST_ARCHIVE.md`.
Сначала проверь, воспроизводится ли это на фактической ветке: исправленные места не менять повторно. Исторический PASS этапа 09 сохраняется с прежней областью; новые дефекты и проверки вести отдельно.

- `backend/src/reprocess/semantic/benchmark.ts`, `assemble.ts`, `verify.ts`, corpus SYN01–SYN17 и sample benchmark schemas.

## Что реализовать
1. Зафиксируй разницу: действующий run — extract@3, старый shadow — legacy `extractFromText`/extract@2 и legacy `extractions`. Не оставлять пользователю «проверку модели», которая молча тестирует другую схему. Старый режим пометить LEGACY/явный отдельный флаг либо закрыть; создать отдельный current-schema evaluate/compare с непротиворечивой документацией. Не мигрировать legacy результаты в доказательства задним числом.
2. Вынеси минимальные общие pure-интерфейсы этапов: chunk plan → extraction → verify → assemble → candidate decision. Оценщик должен использовать те же реализации и бюджеты, что current pipeline, включая полное покрытие, truncated input и invalid-output handling. На коротком корпусе можно отдельно оценивать raw extraction, но это другой уровень метрики, а не end-to-end quality.
3. План проверок строить до исполнения модели. Для каждого case сохранять planned, evaluated, passed, failed, error, skipped и reason. Ошибка/timeout не создаёт пустой набор checks с уменьшенным знаменателем; unknown case selector и пустая выборка — ошибка CLI. Отчёт не PASS, если обязательные кейсы не оценены. Непубликуемый truncated результат не засчитывается как успешное end-to-end извлечение.
4. Раздели безопасность (не выдумывает реквизиты/участников/связи), полноту извлечения, schema validity, отказ инфраструктуры, entity resolution и end-to-end доступность факта в досье. Отношения вида 24/25 и 3/9 — только число соответствующих checks. Precision/recall допустимы лишь с явным reference set фактов, matching rule, знаменателями и разбором FN/FP; не пересчитывать прежние checks в «проценты качества».
5. Сравнивать конфигурации по полному fingerprint из этапа 11, а не только model_id+prompt_version. Один и тот же корпус/сплит/нормализатор/правила scoring. Покажи paired per-case deltas, потери на safety и причины, а не лишь общую сумму. Нельзя скрыть ухудшение отрицаний ростом количества компаний.
6. Сохранить 17 прежних синтетических кейсов как regression baseline. Расширить корпус boundary-кейсами из reference, не подгонять старую разметку под output. Ground truth отдельная от parser output структура, с точными цитатами и разрешёнными unknown. Дедуп/перепечатки одного origin держать в одном train/dev/holdout split. Данные, виденные при настройке промта, не называть unseen holdout.
7. Зафиксировать происхождение corpus version/hash, schema, renderer, gate thresholds, код commit/diff, model reported metadata и время. Секреты не сохранять; реальные тексты не коммитить/не отправлять наружу автоматически. Отчёты должны воспроизводиться по сохранённым mock outputs без обращения к провайдеру.
8. `benchmark-06.json` в ZIP отсутствует. Создай безопасный импорт локального отчёта/форму анализа, но не придумывай, какая именно safety-проверка провалилась. Пока исходник отсутствует — UNKNOWN, разбор подготавливается, не объявляется завершённым.

## Критерии приёмки и регрессии
- T14A-01…T14A-08. Raw extraction v2 нельзя принять за оценку v3; current smoke metadata указывает точную schema и execution fingerprint.
- Все кейсы ошиблись → не 100% и не PASS; один ошибся → остаётся в planned denominator. Пустой --case/неизвестный case → ненулевой exit.
- Перепечатки не утекли в holdout через другой URL; тест scoring на известных FP/FN и unknown.
- Benchmark и worker одинаково отвергают невалидный/обрезанный/частичный output по shared logic.
- Сравнение разной схемы/корпуса/гейтов отмечается incompatible, а не как улучшение модели.
- Сохранённый фикстурный ответ воспроизводит score без сети. Нельзя переписать ground truth генерацией из самого ответа.
Проверки должны утверждать правильное поведение, а не подстраивать ожидание под обнаруженный дефект. Не помечать готовность по одному числу тестов. Ошибки и NOT_RUN перечислять явно.

## Прогон пользователя
Подготовь user-run только после offline scorer tests. Пользователь делает один baseline текущей конфигурации на синтетике в LM Studio и сохраняет JSON; машина, concurrency, фактическая модель фиксируются. Нет разрешения модели — REAL_MODEL=NOT_RUN, при этом scorer и mocks могут быть CODE_READY. Не требуй реальные публикации для этого этапа.
Агент подготавливает точные команды под существующие scripts и PowerShell/Git Bash, но не выполняет Docker/БД/browser/model/network. Перед каждой изменяющей командой указать цель, побочный эффект, способ убедиться в тестовом контуре и ожидаемый результат. Не включать рабочие URL/пароли в пример.

## Не делать
Не снижать защиту цитат/реквизитов, не выбирать модель по старому `--compare`, не маскировать provider errors пропущенными checks, не скачивать модели, не обучать и не менять `.env`, не называть fixture PASS валидацией qwen.
Дополнительно действуют все ограничения COMMON_RULES. Не открывать новый этап, не публиковать данные и не менять глобальные флаги автоматически.

## Результаты, совместимость и остановка
CURRENT_EVALUATION_CONTRACT, versioned corpus/scoring, parity tests и обновлённые команды вместо misleading legacy пути. Отдельно — перечень неизвестного по старому benchmark, без выдуманного диагноза.
Сохранить `docs/development/stages/14A_REPORT.md`, handoff и форму пользовательского прогона `docs/development/evidence/14A/USER_RUN.md`. Указать, какие контракты/индексы/миграции затронуты, как прежний код читает старые данные и как остановить новую функцию без потери истории. При отсутствии миграций написать это явно.

В финале показать выполненные проверки, незапущенные проверки, открытые дефекты и точное следующее действие пользователя. **Остановиться после этапа 14A.**
