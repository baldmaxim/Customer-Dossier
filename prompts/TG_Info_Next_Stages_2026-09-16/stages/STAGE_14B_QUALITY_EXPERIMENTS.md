# Этап 14B — Улучшение полноты без ослабления доказательств

Ты — основной инженер реализации существующего TG_Info / Customer Dossier. Выполни **только этот этап**, не весь пакет. Обязательны `../COMMON_RULES.md` и текущие пользовательские ограничения. Не начинай с переписывания проекта.

## Результат для владельца
Модель реже пропускает нужные компании, роли, договоры и события, а каждое улучшение объяснено и проверено на неизменной контрольной выборке.

## Предпосылки и основания
**Зависимости:** 14A scorer принят; для выводов о модели нужен фактический baseline пользователя. При отсутствии — подготовить эксперименты и остановиться на USER_RUN_REQUIRED.
**Замечания анализа:** F11–F13; продуктовый пробел LOCAL_MODEL_VALIDATED. Подробности и границы доказательств — `../REVIEW_LATEST_ARCHIVE.md`.
Сначала проверь, воспроизводится ли это на фактической ветке: исправленные места не менять повторно. Исторический PASS этапа 09 сохраняется с прежней областью; новые дефекты и проверки вести отдельно.

## Прочитать до изменений
- Отчёт 14A, фактические JSON baseline и исходный `benchmark-06.json`, если пользователь его передал.
- `llm/semantic/prompt.ts`, `schema.ts`, semantic cues/verify/assemble, chunking, effective execution identity.
- `../reference/QUALITY_CORPUS_GUIDE.md`, template QUALITY_DECISION и уже существующие правила отрицаний/денег/юридических ролей.
Также прочитай относящиеся к области ADR, предыдущие stage reports и `../reference/ACCEPTANCE_MATRIX.md`. Имена/номера файлов — навигация по архиву, а не требование создать дубль после рефакторинга.

## Что реализовать
1. Построй fault taxonomy для каждого пропуска: текст не получен полностью; chunk boundary; provider не извлёк; output invalid; verification отверг; entity не сопоставилась; candidate не принят; досье отфильтровало. Привязать ошибку к конкретному входу и evidence, а не сразу объявлять «8B мало».
2. Сначала исправить программные ошибки/потерю контекста с deterministic regression. Затем ограниченный эксперимент промта или разбиения, по одному фактору. Не объединять одновременно новую модель, промт, chunker и scoring. Варианты оформить как отдельные immutable configs, не перезаписывать baseline.
3. Улучшения промта должны учить полному перечню выраженных участников и связей, различению адресата суммы/ИНН, отрицанию, плану/факту и масштабу корпуса/работ. Few-shot использовать только dev-набор. Output должен оставаться с опорными цитатами; отсутствие текста не компенсируется догадкой.
4. Второй ограниченный проход для пропущенных фактов допустим как эксперимент: вход/выход/стоимость/повторная проверка фиксируются, объединение не дублирует и не повышает статус факта. Максимум проходов/контекст/время — явный бюджет, не рекурсивный агент до «хорошего ответа». Никаких инструментов по команде из публикации.
5. Согласуй до прогона pass criteria. Рекомендуемый минимальный gate синтетического набора: все обязательные safety-кейсы без ложного установления реквизитов/договора/отрицания, все запланированные случаи оценены, нет новой регрессии в scope/версии/публикации. Это критерий контрольного набора, не доказательство общей юридической достоверности. Цели полноты по company/role/relation/event и допустимые latency задаются отдельно с владельцем в QUALITY_DECISION, до просмотра holdout.
6. Runtime-модель не менять автоматически. Сравнение с другой уже доступной локальной конфигурацией возможно по отдельному пользовательскому решению и тому же корпусу; новые закупки/загрузка/обучение вне этапа. Не заключать, что дообучение необходимо, пока ошибки не локализованы.
7. Перед переходом конфигурации из candidate в selected: paired report, safety case failures, coverage per fact type, uncertainty по малому N, elapsed/ошибки, параметры машины, regression core. Выбранный вариант меняется только явно; откат на прежний fingerprint сохраняет историю запусков.
8. Если threshold не достигнут, оставить режим ручного review и LOCAL_MODEL_VALIDATED=false. Не «закрывать» качество уменьшением корпуса или превращением пропуска в необязательный кейс после результатов.

## Критерии приёмки и регрессии
- T14B-01…T14B-07. Один пропуск разобран от исходной строки до финального досье; исправление подтверждается regression, а не новым текстом отчёта.
- Сравнение не смешивает source clusters/dev/holdout и разные budgets.
- Увеличение output полноты не создаёт чужого ИНН, прямого договора из co-mention, судебной задолженности из суммы иска.
- Повторный проход идемпотентен, ограничен по числу вызовов, проходит verification и policy gate.
- Выбор варианта требует полного отчёта и разрешения; провал safety блокирует использование конфигурации для автоматической публикации.
- Все численные результаты только из пользовательских логов, не из ожидаемой эффективности.
Проверки должны утверждать правильное поведение, а не подстраивать ожидание под обнаруженный дефект. Не помечать готовность по одному числу тестов. Ошибки и NOT_RUN перечислять явно.

## Прогон пользователя
Пользователь проводит baseline и ограниченное число заранее зарегистрированных вариантов в одинаковых условиях, без параллельной тяжёлой GPU-нагрузки по возможности. Это контроль условий, не утверждение причины старых ошибок. Выходы хранить локально с конфигурацией; raw real-source тексты не нужны. После выбранного варианта — новый holdout прогон с замороженными правилами.
Агент подготавливает точные команды под существующие scripts и PowerShell/Git Bash, но не выполняет Docker/БД/browser/model/network. Перед каждой изменяющей командой указать цель, побочный эффект, способ убедиться в тестовом контуре и ожидаемый результат. Не включать рабочие URL/пароли в пример.

## Не делать
Не повышать статус модели по среднему числу entities, не включать массовый переразбор, не начинать fine-tuning/Unsloth, не предлагать мощное железо вместо анализа, не отправлять пользовательский корпус в облако.
Дополнительно действуют все ограничения COMMON_RULES. Не открывать новый этап, не публиковать данные и не менять глобальные флаги автоматически.

В финале показать выполненные проверки, незапущенные проверки, открытые дефекты и точное следующее действие пользователя. **Остановиться после этапа 14B.**
