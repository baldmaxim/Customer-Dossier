# Этап 12 — Правильная роль и договорная цепочка по конкретной стройке

Ты — основной инженер реализации существующего TG_Info / Customer Dossier. Выполни **только этот этап**, не весь пакет. Обязательны `../COMMON_RULES.md` и текущие пользовательские ограничения. Не начинай с переписывания проекта.

## Результат для владельца
Сведения о другой стройке, корпусе, работе или периоде не подтверждают и не опровергают заявленную роль в текущем обращении.

## Предпосылки и основания
**Зависимости:** 10; 11 нужен для общего дальнейшего пути, но pure scope tests можно готовить независимо. Не менять схему извлечения ради исправления отображения уже записанных фактов.
**Замечания анализа:** F06; R01–R05, контроль C01. Подробности и границы доказательств — `../REVIEW_LATEST_ARCHIVE.md`.
Сначала проверь, воспроизводится ли это на фактической ветке: исправленные места не менять повторно. Исторический PASS этапа 09 сохраняется с прежней областью; новые дефекты и проверки вести отдельно.

## Прочитать до изменений
- `backend/src/dossier/caseDossier.ts`, `facts.ts`, `companyDossier.ts`, проектное досье и типы.
- `backend/src/signals/{context,intervals,rules}.ts`, `graph` builders и правила attribution/status.
- ADR-008/010, dossier tests, формы обращения и описания IFact. R01–R05 и C01 в аудите.
Также прочитай относящиеся к области ADR, предыдущие stage reports и `../reference/ACCEPTANCE_MATRIX.md`. Имена/номера файлов — навигация по архиву, а не требование создать дубль после рефакторинга.

## Что реализовать
1. До изменения напиши unit-регрессии по исходным случаям: договор без объекта даёт documented; отрицание по корпусу 1 делает contradicted корпус 2; rejected negative всё ещё влияет; неизвестный корпус считается установленным; договор по другому корпусу/работам подтверждает chain. Положительный контроль C01 сохранить.
2. Введи единое явное сравнение контекста assertion и обращения: точное совпадение, доказанное включение/совместимость, неизвестная часть, конфликт. Компоненты: каноническая компания, конкретный объект, очередь/корпус, вид работ, роль и период. Null не wildcard, который автоматически доказывает факт. Не придумывать сопоставление ОВ/ВК/ЭОМ или «весь объект» без основания. Нормализация синонимов только детерминированная/утверждённая.
3. Факт с неизвестным корпусом при выбранном корпусе — проектный контекст/требует уточнения; не established для корпуса. Факт явно для всего объекта может покрывать корпус только при явно сохранённом scope all_project, а не из null. Старые null не backfill в all_project.
4. Договорная цепочка требует основания каждого перехода с правильными сторонами и контекстом. Без projectId — общий фон отношений, не подтверждение текущей стройки. Корпус/работы/период другого договора показываются отдельно. Нельзя автоматически вывести прямую связь между всеми участниками одного объекта, договор из владения или ответственность из группы компаний.
5. Противоречие существует только между применимыми по scope/роли/времени утверждениями. Rejected negative оставить в истории/атрибуции, но не использовать как активное основание вывода. Если отрицание не отклонено и относится к той же области, сохранить честное противоречие даже при analyst_reviewed; показать конкретное решение, а не скрывать источник.
6. Дата сообщения, дата события и период действия различаются. Неизвестная дата не today; непересекающиеся периоды смены подрядчика не конфликт. Если форма обращения ещё не содержит необходимого периода, добавить явный запрос/поле с backward-compatible unknown, не притворяться что выполняется временное сравнение.
7. Возвращать объяснение каждого результата: применённый scope, missing dimensions, причины исключения, evidence IDs и источник. Обновить UI labels/API так, чтобы unknown/contradicted/context не выглядели как один зелёный статус. Условия claimedClient сравнивать только с релевантными договорами.
8. Одинаковое правило применяется к dossier, graph и snapshots при новом построении. Исторический снимок не менять; в новом будет новая версия правил/формата.

## Критерии приёмки и регрессии
- T12-01…T12-12. Не менее одного теста на каждую размерность scope, unknown и конкретное несовпадение.
- Исходные R01–R05 становятся корректными; C01 остаётся корректным. Формат статусов допускается пересмотреть версионированно, но смысл — никаких ложных подтверждений.
- Два корпуса, одинаковая роль, разные даты, планы vs факт, отклонённое отрицание, одновременные непересекающиеся виды работ.
- Факт для всего объекта проходит к корпусу только по явному основанию all_project. Null таким основанием не является.
- Ответ на вопрос «кто нанял этого подрядчика на этот пакет работ» либо содержит точный источник, либо «прямой договор не установлен».
Проверки должны утверждать правильное поведение, а не подстраивать ожидание под обнаруженный дефект. Не помечать готовность по одному числу тестов. Ошибки и NOT_RUN перечислять явно.

## Прогон пользователя
Синтетический набор: одна компания, два корпуса, ВК/электрика, два заказчика, последовательная смена подрядчика, неизвестный договор. Через API и затем браузер пользователь проверяет досье нескольких обращений и graph. В логах показать различие контекста, а не только HTTP200.
Агент подготавливает точные команды под существующие scripts и PowerShell/Git Bash, но не выполняет Docker/БД/browser/model/network. Перед каждой изменяющей командой указать цель, побочный эффект, способ убедиться в тестовом контуре и ожидаемый результат. Не включать рабочие URL/пароли в пример.

## Не делать
Не удалять отрицательные публикации, не превращать analyst_reviewed в confirmed автоматически, не понижать все противоречия до «информации нет», не исправлять проблему только текстом подписи при прежнем неправильном decision/status.
Дополнительно действуют все ограничения COMMON_RULES. Не открывать новый этап, не публиковать данные и не менять глобальные флаги автоматически.

## Результаты, совместимость и остановка
ADR/контракт SCOPE_MATCH, regression suite, таблица прежнее→новое поведение, совместимый вывод существующих данных и новые признаки неполноты. Нужен понятный руководителю пример до/после без реальных названий компаний.
Сохранить `docs/development/stages/12_REPORT.md`, handoff и форму пользовательского прогона `docs/development/evidence/12/USER_RUN.md`. Указать, какие контракты/индексы/миграции затронуты, как прежний код читает старые данные и как остановить новую функцию без потери истории. При отсутствии миграций написать это явно.

В финале показать выполненные проверки, незапущенные проверки, открытые дефекты и точное следующее действие пользователя. **Остановиться после этапа 12.**
