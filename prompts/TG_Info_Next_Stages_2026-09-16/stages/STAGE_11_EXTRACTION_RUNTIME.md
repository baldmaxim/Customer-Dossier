# Этап 11 — Неизменная конфигурация запуска и отзыв допуска

Ты — основной инженер реализации существующего TG_Info / Customer Dossier. Выполни **только этот этап**, не весь пакет. Обязательны `../COMMON_RULES.md` и текущие пользовательские ограничения. Не начинай с переписывания проекта.

## Результат для владельца
Каждый результат точно связан с конфигурацией реально вызванной модели. После отзыва допуска новые фрагменты и повторы не отправляются.

## Предпосылки и основания
**Зависимости:** 10 — безопасная цель и корректный исходный статус. Схема extract@3 остаётся текущей до явного versioned изменения.
**Замечания анализа:** F04, F05; R09–R10. Подробности и границы доказательств — `../REVIEW_LATEST_ARCHIVE.md`.
Сначала проверь, воспроизводится ли это на фактической ветке: исправленные места не менять повторно. Исторический PASS этапа 09 сохраняется с прежней областью; новые дефекты и проверки вести отдельно.

## Прочитать до изменений
- `backend/src/reprocess/{provider,runs,worker,publish,publishContent}.ts` и действующие типы claim/fencing.
- `backend/src/llm/client.ts`, `backend/src/llm/semantic/{prompt,schema}.ts`, source policy helpers и API/CLI-входы.
- `reprocess/reprocess.int.test.ts`, ADR-004, ADR-008, R09/R10 из аудита.
Также прочитай относящиеся к области ADR, предыдущие stage reports и `../reference/ACCEPTANCE_MATRIX.md`. Имена/номера файлов — навигация по архиву, а не требование создать дубль после рефакторинга.

## Что реализовать
1. Проследи enqueue → claim → provider call → chunk result → resume → candidates → publish. Сейчас enqueue сохраняет fingerprint, а claim возвращает chunker без полной проверки runtime provider; processRun принимает текущий provider. Зафиксируй контракт, при котором нельзя обработать запланированную модель A моделью B и сохранить старую атрибуцию.
2. Сделай full execution identity неизменной: provider/model identifier, эффективные сообщения/шаблоны и их версии (включая дополнительные инструкции вроде `/no_think`), schema, sampling/context/output budgets, chunker, версии сборки/валидации. Секретные endpoints/tokens не включать в публичный fingerprint. Для параметров, о которых сервер не сообщает, писать unknown, а не предполагать фактическое железо/квантизацию.
3. До первого вызова сверить claim, recorded identity и фактический provider. При несовпадении не переписывать run и не вызывать модель: явный blocked/config_mismatch либо эквивалент по контракту. Новая конфигурация — новый run с ссылкой на прежний. Успешные старые chunks нельзя использовать как chunks новой конфигурации без отдельного явного контракта совместимости; по умолчанию не смешивать.
4. Проверять актуальный AI-допуск непосредственно перед каждым очередным запросом и retry. Между чанками допуск может истечь/отзываться. Отсутствие разрешения прекращает дальнейшие вызовы; до publish также действующая проверка. Отдельно не путать разрешение collection с AI.
5. Уже ушедший запрос нельзя «отменить задним числом». Введи best-effort abort, если клиент его поддерживает, с ограничением: данные могли уже быть отправлены. Ответ после revocation не публиковать; статус/аудит и правила хранения обработать по существующему retention-контракту, не удалять историю самовольно. Не держать долгую DB-транзакцию/локи вокруг модели.
6. Проверить fencing и lease перед новым вызовом: worker с потерянной арендой не продолжает бесконечно тратить запросы. Результат stale worker не меняет run/canon. Сохранить идемпотентность, heartbeat и корректное восстановление после рестарта.
7. Все исполнения (CLI, scheduler, будущий UI, batch/shadow) проходят один общий gate. Если offline benchmark не использует source table, это отдельный явно синтетический контракт, а не обход допуска реальных публикаций. Добавить reason codes без вывода секретов.

## Критерии приёмки и регрессии
- T11-01…T11-09. A enqueue / B worker: ноль вызовов, mismatch явный. Resume прежних chunks с B не смешивает результаты. A/A проходит.
- Отзыв и истечение допуска после первого из двух chunks: второй не отправлен. Retry после revocation также запрещён. Сбор разрешён, AI неизвестен — вызовов нет.
- Ответ in-flight после отзыва не публикуется; прежний canon и решение аналитика не меняются.
- Смена effective prompt/chunker/schema/validator version выявляется; скрытые недоступные metadata остаются unknown.
- Lease утрачена после chunk: stale worker не пишет/не публикует; отказ модели на позднем chunk не даёт частичной канонической публикации.
Проверки должны утверждать правильное поведение, а не подстраивать ожидание под обнаруженный дефект. Не помечать готовность по одному числу тестов. Ошибки и NOT_RUN перечислять явно.

## Прогон пользователя
Подготовить DB-интеграцию с двумя управляемыми исполнителями и deterministic provider: изменение допуска и конфигурации между вызовами, потеря lease, restart. Реальная модель не нужна для доказательства этих инвариантов. Пользователь запускает их на выделенной test-цели; агент не вызывает LM Studio.
Агент подготавливает точные команды под существующие scripts и PowerShell/Git Bash, но не выполняет Docker/БД/browser/model/network. Перед каждой изменяющей командой указать цель, побочный эффект, способ убедиться в тестовом контуре и ожидаемый результат. Не включать рабочие URL/пароли в пример.

## Не делать
Не переходить на extract@2, не ослаблять verification, не перезаписывать атрибуцию исторических runs, не выдавать отмену HTTP за гарантию отсутствия уже отправленных данных, не блокировать всё приложение одной транзакцией на время inference.
Дополнительно действуют все ограничения COMMON_RULES. Не открывать новый этап, не публиковать данные и не менять глобальные флаги автоматически.
