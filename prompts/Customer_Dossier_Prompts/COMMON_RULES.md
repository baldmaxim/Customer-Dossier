# Общие правила исполнения каждого этапа

Прочитай этот файл заново в каждой новой сессии. Это задания для разработки **Customer Dossier**, не для других проектов пользователя. Не переносить сюда решения Quantor или «Нормирования».

## 1. Цель и доказательность

Компания/юрлицо → конкретный объект/корпус → роль/пакет работ/период → доказанные связи → события → досье по обращению. Совместное упоминание, совместное участие, прямой договор и корпоративная связь — разные сущности. Не выводить договор транзитивно. Не переносить неблагоприятные сообщения на группу, однофамильную компанию или всех участников объекта. Не изобретать реквизиты, географию, стоимость, НДС, сроки, авансы или причины задержки.

Цитата подтверждает, что написано в источнике, а не истинность сообщения. Отрицание, предположение, планы и оспаривание сохранять. Отсутствие информации не превращать в зелёную оценку. ИНН/ОГРН с корректным форматом не доказывает связь реквизита с упомянутой компанией.

## 2. Фактическая база важнее старого отчёта

Проверь cwd, доступные инструкции, Git status/HEAD/diff и реальные файлы. Если `.git` отсутствует, явно укажи и используй снимок файлов/хеши; не придумывай commit. Старые reference-документы — свидетельство о переданном архиве на 11.09.2026, не о сегодняшней рабочей папке. Наличие текста «исправлено» не доказывает установку исправления.

Не перезаписывай незакоммиченные изменения пользователя. Если они затрагивают ту же строку, интегрируй только после сравнения; неясный конфликт изолируй. Не запускай старые команды из CLAUDE.md автоматически. Конфликтующие указания сначала перечисли, затем устрани в рамках этапа 01, сохранив полезные правила. Не заменяй CLAUDE.md, AGENTS.md и правила Cursor целиком и не создавай постоянные настройки всех трёх инструментов без отдельного указания.

## 3. Разрешённый объём и режим работы

Отправленный пользователем этап разрешает исследовать и реализовать **только этот этап**, запускать безопасные проверки и писать отчёты. Не запрашивай повторное подтверждение каждого файла, индекса или теста. Сначала кратко обозначь план и затрагиваемые модули, затем работай. На границе этапа остановись.

Без отдельного разрешения запрещены: commit/push/merge/rebase/reset/clean/stash, публикация, внешние уведомления, новые платные сервисы, смена runtime LLM на облачный, запись в рабочую БД, массовый backfill/reextract/renormalize/merge рабочих данных, включение новых источников и изменение секретов. Тестовый merge как функция приложения разрешён на изолированных синтетических данных; Git merge — нет.

Не ослабляй защиту, чтобы пройти тесты. Не добавляй bypass permissions, автодеплой или фоновые задания вне локального приложения. Не запускай следующие этапы ради красивого итогового отчёта.

## 4. Локальная безопасность без избыточной архитектуры

Сохраняй текущий стек, если локальная проверка не выявила объективный блокер: TypeScript, Express, PostgreSQL с pg, React/Vite. Одно приложение и локальная БД допустимы. Не добавляй брокер, ORM, графовую БД и микросервисы только ради дизайна.

По умолчанию loopback, один оператор, изменяющие операции защищены, ingest/bot/pipeline/автопересчёт выключены до явного включения. Не полагайся на CORS как на авторизацию. Не кэшируй чувствительные API в PWA. Локальный режим не обещает защиту от вредоносной программы с доступом к компьютеру.

У парсера внешних сайтов и у доверенного клиента локальной LLM разные сетевые политики. Блокировка SSRF для источников не должна ломать разрешённый loopback LM Studio; исключение для LM Studio не должно открывать loopback произвольным ссылкам публикаций.

Разрешённый сбор и разрешённая ИИ-обработка проверяются отдельно на каждом входе: шедулер, CLI, бот, ручной импорт и повторная обработка. Неподтверждённое основание — отключённая соответствующая операция, не догадка агента. Код и синтетические тесты можно разрабатывать без новых внешних данных.

## 5. Данные и миграции

Рабочая БД не испытательный стенд. До DB-тестов проверь фактические host/port/database/роль без печати пароля. Одного суффикса `_test` мало: нужна явно выделенная цель и проверка несовпадения с рабочей. Если её нет, подготовь проверку и пометь NOT_RUN; не используй DATABASE_URL по умолчанию. Создание новой тестовой БД допустимо только в подтверждённо локальном тестовом контуре, без изменения системных служб или удаления существующих баз.

Проверяй тестовые setup-файлы, скрипты установки и startup до запуска. Не запускай `npm run dev` как безобидный просмотр, пока не доказано отключение фоновых обработчиков. Не печатай `.env`, bot token, пароль, DSN, персональные данные и полные тексты источников в отчёте. Значения секретов не передавай субагентам.

Применённые миграции 001–009 не переписывать. Новые номера определяй по актуальному реестру, а не жёстко считай следующий номер 010. Для изменения схемы: расширение → проверяемый backfill на копии → сверка → переключение совместимого read/write пути → старый путь выключен. Удаление старых таблиц в эти этапы не входит. Совместимость не означает запуск старого destructive apply параллельно новому.

Каждый backfill — явная отдельная команда с dry-run, пределом батча, контрольными количествами, идемпотентностью и checkpoint. Не запускать автоматически из migration/startup. Если исторических данных не хватает, сохранять unknown/legacy_unreviewed; не создавать фиктивные доказательства. Откат приложения после переключения — безопасный read-only/feature-off или восстановление тестового backup, а не возврат к удалению ручных решений.

## 6. Дисциплина исполнителя и проверяющего

Один исполнитель пишет в рабочее дерево. До трёх помощников можно использовать для чтения: схема/данные, сбор/безопасность, интерфейс/тесты. Реальное число зависит от доступных инструментов. Независимый проверяющий не исправляет код, который одновременно меняет исполнитель. Изолированный worktree — только при наличии Git и явной необходимости; не создавать и не коммитить изменения автоматически.

Показывай найденные важные проблемы по мере работы. Не выдавай длинное внутреннее рассуждение; нужны решения, обоснования, затрагиваемые файлы и доказательства тестов. При нехватке контекста запиши handoff и остановись, не срезай тесты. Большое окно 1M не отменяет деление на этапы.

## 7. Проверки и статусы

Используй реальные scripts из package.json; отсутствующую команду сначала реализуй в текущем этапе. Транспиляция не заменяет semantic typecheck, unit-тесты — интеграцию PostgreSQL, а синтетический ответ LLM — проверку реальной модели. Для UI нужны smoke/e2e и фактический просмотр, если браузер доступен. Нет браузера — `UI_VISUAL=NOT_RUN`, а не «выглядит хорошо».

У каждой проверки: ID, команда, окружение, exit code, наблюдение, путь к логу. Статусы: PASS, FAIL, NOT_RUN, BLOCKED, NOT_APPLICABLE с причиной. Для этапа: PASS только при выполненных обязательных условиях; иначе BLOCKED/FAIL/IN_PROGRESS. Отдельный необязательный live-smoke может быть NOT_RUN при PASS локальных core-gates. Не приравнивать к PASS запланированные проверки, старые логи и слова другой модели.

Не удаляй тесты и не понижай пороги ради прохождения. Исправляй вызванные этапом регрессии. Не связанные старые дефекты фиксируй в BACKLOG с влиянием на gate, а не скрывай.

## 8. Обязательный результат этапа

В `docs/development/` веди STATE.md и HANDOFF.md, в `docs/development/stages/` — `<STAGE_ID>_REPORT.md`; подробные логи в `docs/development/evidence/<STAGE_ID>/` без секретов. Используй шаблоны из пакета, не копируй пустой шаблон поверх существующего отчёта.

STATE содержит текущий/последний прошедший этап, target БД в обезличенном виде, активные feature flags, неразрешённые действия, следующие условия. Отчёт: исходное состояние, изменения, миграции, тесты, ограничения, что не сделано, откат и перечень затронутых файлов. HANDOFF — краткий вход для новой сессии с реальными путями.

Финал: что изменилось для пользователя; какие гейты пройдены; что не проверено; безопасность данных; точное имя следующего промта. Не объявлять готовность production: цель пакета — подтверждённая локальная версия.
