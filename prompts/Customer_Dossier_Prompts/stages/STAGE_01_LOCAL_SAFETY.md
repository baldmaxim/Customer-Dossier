# Этап 01 — Безопасный локальный запуск и защита изменений

Ты — основной инженер Customer Dossier. Выполни только этот этап в существующем локальном проекте.

## Перед началом

Прочитай `COMMON_RULES.md`, `ROADMAP.md`, `reference/DATA_CONTRACTS.md`, `acceptance/TEST_MATRIX.md` из пакета. Проверь реальные инструкции репозитория, `docs/development/STATE.md`, `HANDOFF.md` и отчёты зависимостей: **00**. Отсутствующий отчёт не придумывай. Источник истины о реализации — рабочие файлы и фактические тесты.

Ниже приведены пути из inspected-архива. Если структура изменилась, найди эквиваленты поиском внутри проекта и зафиксируй соответствие, не создавай дубликаты модулей.

## Обязательные точки чтения

`backend/src/index.ts`, `app.ts`, `config/env.ts`, `config/env-check.ts`, `db/migrate.ts`, `__tests__/setup.ts`, `api/admin.routes.ts`, `api/manual.routes.ts`, `pipeline/cli-commands.ts`, `ingest/cli.ts`; `frontend/vite.config.ts`, `api/client.ts`, `pages/AdminPage.tsx`; CLAUDE.md; отчёты baseline/patch coverage.


## Цель

Сделать локальную разработку и просмотр портала безопасными до большой перестройки данных. Один оператор; никаких SSO и облачной инфраструктуры. Выполни изменения кода, тестов и минимального UI, а не только документ с рекомендациями.

## Реализация

**1. Воспроизводимое окружение.** Проверив scripts и lock-файлы, установи зависимости стандартной воспроизводимой командой проекта. Обоснуй любые изменения lock-файла; не запускай массовое обновление и автоматическое force-исправление зависимостей. Добавь явную конфигурацию unit/integration-тестов, которая не наследует рабочий DATABASE_URL. Отдельный test-target и проверка его идентичности обязательны до DML.

**2. Startup.** Введи раздельные явные флаги для ingest scheduler, bot, extraction worker и auto-metrics. По умолчанию выключены в безопасном локальном профиле; API/UI можно открыть без внешнего сбора. Парси boolean строго: false и 0 не становятся true из-за непустой строки. Неверное значение — понятная ошибка. Не включать задания автоматически миграцией, seed или импортом файла. Проверь loopback у API, Vite и preview; не разрешай `--host 0.0.0.0` как штатный сценарий.

**3. Локальный оператор.** Защити изменения source/review/merge/reprocess и выдачу закрытого досье серверной авторизацией. Выбери один простой механизм для одного оператора и кратко обоснуй: например, локальный bootstrap-token → короткая серверная сессия. Секрет не зашивать во frontend, URL, лог и localStorage; маскировать в ошибках. Проверять Origin/Host и CSRF для cookie-based записей; CORS не заменяет эти проверки. Проверяй logout/expiry. Не превращать задачу в регистрацию пользователей или RBAC. Флаг LAN/public не открывать до будущего отдельного этапа.

**4. Сетевая политика.** Создай единый клиент для внешних источников: разрешённые hosts, только нужные схемы/порты, ограничения времени и размера, проверка адреса назначения и каждого redirect; запрет служебных/локальных адресов и обходов через DNS. Не делай исключение «все адреса разрешены в development». Локальная LLM — отдельный фиксированный доверенный endpoint, который не получает URL из публикаций. Источники и LLM не используют общий безусловный allowlist. Конкретные проверки сверяй с официальным OWASP в reference/SOURCES.md.

**5. Допуск источников.** Добавь access_status и ai_processing_status, scope/allowed_operations, основание/ссылку на решение, ответственного, время и срок действия, журнал изменений. unknown/revoked/expired блокируют соответствующую операцию. Старый `active` не является approved. Для каждого входа — CLI, scheduler, bot, manual import, reextract — выполняется один и тот же gate. Операции, разрешённые на синтетическом test-source, не разрешают реальный source. Добавь минимальное отображение причин блокировки в админке; не заполняй реальные согласования за пользователя.

**6. Прежние опасные пути.** До нового apply заблокируй изменение legacy-канона через массовый reextract/renormalize и небезопасный merge. Также проверь одиночное переизвлечение: запрет массового режима не защищает от потери решения одного документа. Сохрани просмотр существующей базы, но запуск изменяющего pipeline требует безопасного пути, которого пока нет. Старый risk-score временно пометь legacy/непригодным для решения; не выдавай зелёный статус как надёжность.

**7. Runner и инструкции.** Сделай migration dry-run действительно не записывающим: отсутствие schema_migrations распознаётся чтением системного каталога, не CREATE TABLE до проверки dry. Не изменяй исторические 001–009; покажи предупреждение о destructive pending migration 009 и требуй отдельного согласования для рабочей БД. Устрани конкретные противоречия CLAUDE.md, но не удаляй полезные инструкции. Не запускай автоматический `--renormalize` после изменения нормализатора.

**8. PWA и baseline.** Убери кэширование auth/review/API досье через service worker; старые чувствительные caches должны очищаться контролируемо при обновлении. Системный шрифт допустим; сетевые шрифты не должны быть обязательны для offline UI. Восстанови отсутствующие адресные исправления старого патча из PATCH_COVERAGE с локальными регрессионными тестами, не применяя весь старый patch поверх изменённого дерева.

## Приёмка

Открытие UI не делает внешних запросов сборщика и не меняет канон. Запрос без авторизации не меняет источник/решение. Пустой allowed_user_ids не открывает бота всем. Запрещённый source не обходит gate через CLI. SSRF-фикстура блокируется, а явно настроенная локальная LLM не ломается. Dry-run миграций не меняет ни схему, ни строки. Тесты не подключаются к рабочей БД даже при заданном внешнем DATABASE_URL. Backend/frontend собираются либо имеются конкретные неустранённые блокеры; такие сборки не отмечать PASS.

## Откат и границы

Флаги выключены — безопасный fallback. Не возвращай старый удаляющий pipeline ради совместимости. Реальные секреты и рабочую БД не меняй. Полноценные SourceItem/revisions/assertions, HTML-парсер и новый рейтинг сюда не входят. При необходимости новой миграции применяй её только на изолированном стенде.


## Завершение

Запиши `docs/development/stages/01_REPORT.md`, обнови STATE.md и HANDOFF.md. Для каждого обязательного сценария укажи фактический результат и лог. Перечисли изменения файлов, новые миграции, активные флаги, остаточные риски и инструкции безопасного отката. Не меняй рабочую БД и не включай новые источники. Остановись после этого этапа; следующий промт должен отправить пользователь.
