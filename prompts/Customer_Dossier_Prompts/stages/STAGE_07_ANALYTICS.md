## Цель

Заменить смешанную формулу «надёжности» раздельными сигналами, которые можно объяснить до источника. Не ограничиваться переименованием RiskBadge при сохранении неверных агрегатов.

## Новая read-model

Сделай четыре независимых блока: идентификация и полнота данных; опыт по проектам/ролям/видам работ; медиасигналы и подтверждённые события; текущий контекст выбранного объекта. Внутри блока различай auto/text_grounded и reviewed. У каждого агрегата есть правило включения, временное окно, denominator, список underlying IDs и актуальность расчёта. API отдаёт computed_at/coverage/version, а не только число.

Отдельно показывай публикации, разные наблюдения, origin families и объединённые события. Пять перепечаток — пять публикаций, но не пять независимых подтверждений. Одинаковый текст — индикатор общей семьи, не абсолютное доказательство одного первоисточника; unknown origin не маркировать independent. Количество установленных первичных источников и неустановленное происхождение считай отдельно. Новостная активность не превращается в размер/надёжность компании.

Unknown event date не включать в окно «последние 12 месяцев» под видом сегодня. Можно отдельно показывать публикации последних 90 дней о событиях неизвестной даты, явно назвав окно публикаций. Будущая дата, неполный месяц и interval crossing boundary имеют явное правило/метку uncertainty. Нулевой denominator → null/insufficient_data, не 0% или 100%.

Суды — по процессуальной роли и стадии; истец не становится нарушителем. Участие на объекте с задержкой — контекст проекта, не вина подрядчика. Время участия должно пересекаться с событием для контекстного включения; даже пересечение не доказывает причинность. Автоматическую ответственность по графу не распространять.

Опыт: объект, корпус, роль, пакет работ и период. Не приписывай участнику стоимость всего объекта и не суммируй стоимость договора/иска/заявленных требований в одну «выручку». Раздели заявленные/подтверждённые данные и полноту выборки. Без новости «претензий не найдено в выборке», не «претензий нет».

## Технический переход

Новая миграция/read-model заменяет опасные правила; 007 исторически не переписывается. Старый company_risk больше не питаёт новую карточку/сортировку как надёжность. Если нужен legacy endpoint, он явно помечается deprecated и его значения не смешиваются с v2. Snapshot будущего досье должен фиксировать rules version и исходные IDs. Пересчёт детерминирован для одного среза данных и cutoff; текущее now берётся как явный параметр для тестов.

Выбери обычные SQL views/materialized views или таблицы read-model по фактическому объёму, не добавляй отдельный analytics stack. При refresh показывай последнюю успешную версию и stale state; ошибка не превращается в пустые данные. Исправь существующий metrics cli при необходимости. Плановые refresh пока только при явном включении флага.

## UI

Минимально обнови карточку и список подрядчиков: убрать финальный красно-зелёный verdict и сортировку по старому risk_score; добавить статус идентификации, ограничения покрытия, события/проекты и возможность drilldown. Для отрицательных/спорных сообщений использовать атрибутированную формулировку. Цвет не должен быть единственным носителем смысла. Сложное досье будет в 08A.

## Приёмка

При замороженных датах old-undated event не становится свежим; истец не «красный»; подрядчик, пришедший позже задержки, не наследует её; 5 перепечаток дают один event и корректную origin uncertainty; 0 публикаций — insufficient_data; rejected/disputed evidence не скрывается и не считается reviewed; refresh crash сохраняет предыдущую read-model; точные denominators и drilldown совпадают с SQL. Проверяй upgrade schema/views на тестовой копии.

## Вне этапа

Новая шкала 0–100, совет «заключать/не заключать договор», оценка вероятности банкротства, модели кредитного риска и юридические выводы. Откат — прежний безопасный read-only экран с пометкой legacy, не восстановление доверия к старой формуле.
