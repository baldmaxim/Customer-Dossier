## Цель

Превратить данные в удобный рабочий сценарий руководителя: найти компанию → выбрать конкретный объект и работу → увидеть её действительную роль/цепочку → проверить основания и спорные сведения → сохранить обращение. Не ограничиваться дашбордом общих чисел и графиком новостей.

## Пользовательский сценарий и API

Добавь DossierCase: выбранное юридическое лицо (либо явно provisional), объект/корпус, вид работ, заявленная роль, заявленная сторона договора, дата обращения, примечание оператора. Пользователь может описать обращение до идентификации компании, но UI должен показать «юрлицо не установлено» и не смешивать одноимённые candidates.

Поля, введённые оператором со слов контрагента, получают provenance `operator_recorded_claim`, не автоматическое reviewed evidence. Заявленная и установленная роли хранятся отдельно. Условия договора/аванс/цена — только ввод или источник с атрибуцией; неизвестное не досчитывать. Запись заметки не меняет канонический факт незаметно.

Сделай API case create/read/update/list с защитой, пагинацией и проверкой versions. Построение read-model досье не должно требовать нового запроса LLM при каждом открытии. Портал работает при выключенной модели: последние собранные/опубликованные данные доступны с датой актуальности.

## Экраны

**Поиск:** имя/алиас/ИНН/ОГРН; отличать brand/group/legal entity; показывать кандидатов с контекстом, а не открывать первую совпавшую строку. Выбор объекта учитывает город и корпус.

**Досье компании:** верхнее резюме, юридическая идентификация, роли/опыт, известные контрагенты и типы связей, события и общий фон, противоречия, ограничения выборки. Общее досье не должно терять сведения вне выбранного обращения; отдельный toggle/context уточняет предмет.

**Объект:** проект/очередь/корпус, состояние с датой, участники в выбранный период, роли/работы, документированные договорные связи и отдельно co-participation. По клику — основания, не только tooltip.

**Обращение:** сверху 3–5 значимых наблюдений с источниками, заявленная/подтверждённая роль, кто заказывает работы у кого, критические неопределённости и вопросы контрагенту. Рекомендованные вопросы формируются по реальным пробелам, не по выдуманным проблемам.

**Очередь проверки:** нерешённая идентификация, противоречие источников, изменилась публикация, изменилась доказательная база. Покажи две версии рядом, точный span и прошлый review. Действия: подтверждено в указанном объёме / отклонено / требуется проверка; причина обязательна там, где она нужна для воспроизводимости. Сервер хранит историю; optimistic locking защищает две вкладки.

**Источники:** статус допуска, покрытия и парсера; last success, lag и неполные документы. Не скрывать отсутствие источников красивым demo.

## Резюме и формулировки

Начни с детерминированных шаблонов поверх structured facts, работающих без LLM. Каждая существенная фраза содержит assertion/evidence IDs; «не установлено» и отсутствие сведений различаются. «Компания заявляет…», «в публикации сообщается…», «аналитиком проверено…» не смешиваются. Итог не является автоматическим решением о сотрудничестве.

Опциональное LLM-перефразирование не требуется для PASS. Если оно добавляется в пределах существующего runtime, оно читает только выбранный evidence set, не вызывает инструменты, проверяется на добавленные факты и имеет fallback к шаблону. Никакого нового облачного провайдера или массовой выгрузки досье.

## Визуальное решение

Сохрани узнаваемый стиль проекта и существующий стек, но обеспечь ясную иерархию: резюме → предмет обращения → доказательства → подробности. Русские полные подписи, читаемые суммы/даты, отсутствие горизонтального скролла основной карточки на типовом desktop. Таблицы деталей могут иметь собственный скролл. Цвет не заменяет текстовый статус. Важны loading/empty/error/stale/unauthorized states и клавиатурная доступность.

Не удаляй текущие полезные экраны и фильтры без замены. Не подключай дизайн-систему с полной переписью frontend. API types согласуй с backend, нельзя сгенерировать фиктивные JSON лишь для красивого экрана. Fixture demo — только явный тестовый режим/отдельная база.

## Приёмка

На тестовой БД выполни полный сценарий: два одноимённых юрлица → выбор нужного → объект/корпус → сохранение обращения → просмотр роли и цитаты → обнаружение противоречия → решение аналитика → повторное открытие и сохранность. Выключи LLM и сеть: карточка работает по сохранённым данным. Нет данных — честная пустая карточка. Ошибка API/просроченная сессия не показывает stale данные как свежие. Сохрани реальные UI-скриншоты/видеопроход, если доступен браузер; иначе пометь visual NOT_RUN.

## Вне этапа и откат

Граф, неизменяемые snapshots и экспорт выполняются в 08B. CRM с задачами/воронкой, отправка писем, телефонные базы и финансовый скоринг не нужны. Откат — route feature flag к прежнему безопасному интерфейсу при сохранении Cases; данные не удалять.
