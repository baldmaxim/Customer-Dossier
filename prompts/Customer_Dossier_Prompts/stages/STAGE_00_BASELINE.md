# Этап 00 — Инвентаризация и безопасная стартовая точка

Ты — основной инженер Customer Dossier. Выполни только этот этап в существующем локальном проекте.

## Перед началом

Прочитай `COMMON_RULES.md`, `ROADMAP.md`, `reference/DATA_CONTRACTS.md`, `acceptance/TEST_MATRIX.md` из пакета. Проверь реальные инструкции репозитория, `docs/development/STATE.md`, `HANDOFF.md` и отчёты зависимостей: **нет; это начальная инвентаризация**. Отсутствующий отчёт не придумывай. Источник истины о реализации — рабочие файлы и фактические тесты.

Ниже приведены пути из inspected-архива. Если структура изменилась, найди эквиваленты поиском внутри проекта и зафиксируй соответствие, не создавай дубликаты модулей.

## Обязательные точки чтения

`README.md`, `CLAUDE.md`, доступные родительские инструкции, существующие `AGENTS.md`/правила Cursor; `backend/package.json`, `frontend/package.json`, lock-файлы; `backend/src/index.ts`, `config/env.ts`, `db/migrate.ts`, `__tests__/setup.ts`; все применимые SQL-миграции; `reference/REPOSITORY_MAP.md` и исторические review/spec из пакета.


## Цель

Установить, что реально находится в рабочей папке, безопасно ли это запускать и где находятся расхождения с прежним анализом. Это **исследование без изменений кода и данных**. Разрешены только отчёты в `docs/development/`; если среда не позволяет писать, выдай их содержимое и явно отметь ограничение.

## Работа

1. Определи корень проекта, ОС/оболочку (Windows native, WSL или другое), Node/npm, доступность PostgreSQL и локальной модели. Не подменяй среду и не устанавливай системные службы. Не предполагается, что ранее указанная видеопамять или модель актуальны. Не читай секреты в вывод: сообщай наличие переменной и обезличенную категорию target.
2. Сними Git status, HEAD и список изменённых/неотслеживаемых файлов. Если Git отсутствует, сделай инвентарь с хешами без `.env`, дампов, персональных данных и `node_modules`. Никаких stash/reset/commit. Укажи, исходная ли это версия, reviewed-копия или собственные изменения; при отсутствии доказательств статус unknown.
3. Прочитай startup и тестовые setup-файлы до запуска. В inspected-архиве `npm run dev` стартует ingest, pipeline и метрики; `migrate --dry` сначала создаёт schema_migrations; тестовые defaults через `??=` могут сохранить уже установленный DATABASE_URL; миграция 009 обнуляет amount_rub. Проверь, сохранились ли эти риски здесь. Не запускай эти команды против неизвестной БД.
4. Сопоставь R01–R20 и точечные изменения reviewed-патча с локальными файлами. Для каждого: present / missing / partial / superseded / not_applicable, ссылки на строки, необходимый этап. Особое внимание: конфликт реквизитов, локальность цитаты, неполный chunk, immutable extraction payload, `includeGrey=false`, метрики.
5. Найди противоречия инструкций. В известном CLAUDE.md одновременно есть запрет массового reextract и старое «после смены промпта переразбирать всё». Также проверь «роль только растёт», «текущий вклад удаляем» и другие старые правила. Пока не редактируй; составь точечный список правок этапа 01.
6. Зафиксируй статический baseline: доступные зависимости, scripts и существующие тесты, причины возможных блокировок. На этапе 00 не запускай test/build scripts приложения, которые могут записывать файлы, обращаться к БД или сети; их первый изолированный запуск выполняется в этапе 01. Безопасные read-only команды вроде проверки версии среды допустимы. Отсутствие npm-зависимостей не даёт права менять lock-файл; подготовь команду воспроизводимой установки для этапа 01. Не запускай живой parser probe только потому, что его рекомендует старый README.
7. Спроектируй минимальный isolated test-target и порядок проверки миграций. Составь карту существующих API, таблиц, UI и вызовов модели. Определи места внедрения версий/утверждений без остановки чтения legacy. Новые физические схемы детально не реализуй.

## Артефакты

`00_REPORT.md`; `PATCH_COVERAGE.md`; `BACKLOG.md`; начальные STATE.md/HANDOFF.md; краткий план реализации этапа 01. Сохрани фактически выполненные команды и результаты. Для неработающих сервисов — NOT_RUN и причина, не воображаемый лог.

## Критерии перехода

Есть определённый repository baseline; перечислены побочные действия startup/tests/migrate; рабочая БД не изменена; есть план тестовой изоляции; видны старые и новые дефекты, а не только общие слова. Отсутствие живой модели/источников на этом шаге не блокирует следующий этап. Неизвестное расположение проекта или отсутствие доступа к исходникам — блокирует реализацию.

## Вне этапа

Установка зависимостей с lifecycle scripts, изменение кода/CLAUDE.md, запуск портала, миграции и DML, подключение/переподключение источников, переразбор, новые функции и автоматический переход к 01.


## Завершение

Запиши `docs/development/stages/00_REPORT.md`, обнови STATE.md и HANDOFF.md. Для каждого обязательного сценария укажи фактический результат и лог. Перечисли изменения файлов, новые миграции, активные флаги, остаточные риски и инструкции безопасного отката. Не меняй рабочую БД и не включай новые источники. Остановись после этого этапа; следующий промт должен отправить пользователь.
