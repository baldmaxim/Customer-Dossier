# Этап 05B — Разрешённый Telegram-сбор, курсоры и правки

Ты — основной инженер Customer Dossier. Выполни только этот этап в существующем локальном проекте.

Прочитай `COMMON_RULES.md`, `ROADMAP.md`, `reference/DATA_CONTRACTS.md`, `acceptance/TEST_MATRIX.md` из пакета. Проверь реальные инструкции репозитория, `docs/development/STATE.md`, `HANDOFF.md` и отчёты зависимостей: **05A**. Отсутствующий отчёт не придумывай. Источник истины о реализации — рабочие файлы и фактические тесты.

Ниже приведены пути из inspected-архива. Если структура изменилась, найди эквиваленты поиском внутри проекта и зафиксируй соответствие, не создавай дубликаты модулей.

## Обязательные точки чтения

`backend/src/ingest/telegramWeb.ts`, `telegramBot.ts`, `scheduler.ts`, `store.ts`, `cli.ts`; Telegram fixtures; реестр source policy и health; инструкции проекта о доступных способах Telegram. Для технических/платформенных деталей — первичные источники в reference/SOURCES.md с повторной проверкой на дату реализации.


## Цель

Сделать честный и устойчивый сбор из разрешённых публичных каналов без обещания недоступной истории. Нельзя считать публичность канала доказательством допустимости ИИ-обработки; фактическое основание фиксирует пользователь, а не агент.

## Границы доступа

Сначала инвентаризируй существующий способ доступа и реальные разрешения. В исходных инструкциях используется публичный web-preview и long-polling bot, без MTProto api_id/api_hash. Не внедряй MTProto, чужие сессии, закрытые каналы, массовое вступление, скрытый сбор участников/переписок или ротацию аккаунтов. При отсутствии допустимого метода разрабатывай на фикстурах; соответствующий live-адаптер отключён. Пересылка пользователем не означает автоматически право на все дальнейшие операции.

Не придумывай модель доступа «бот читает любой публичный канал». Bot получает только реально доступные обновления/сообщения при соответствующем подключении. Функции history/edit/delete зависят от транспорта; создай capability flags, а не универсальное обещание backfill. Условия и API меняются: сверяй официальную документацию при подключении, сохраняй дату проверки в source profile.

## Сохранение и идентичность

Устойчивый ID поста включает идентичность источника/канала и message/post ID. Переименование username не должно бесконтрольно склеивать разные каналы; неизвестный stable ID/смену владельца показывай как неопределённость. Forward origin сохраняется отдельно от переславшего оператора и source публикации. Bot update ID — транспортный offset, не бизнес-ID сообщения.

Текст/подпись, edit timestamp при наличии, publish timestamp, media group, forwarded metadata и coverage сохраняй без выдумывания недоступных полей. Вложение с подписью — caption_only до отдельного обработчика. Повтор/правка проходит revision storage; короткое важное исправление нельзя отбросить только по длине. Удаление учитывай только там, где транспорт действительно даёт такой сигнал.

## Курсоры и восстановление

Для web-preview реализуй ограниченный pagination/catch-up лишь если выбранный разрешённый интерфейс его фактически поддерживает. Не обходить всю историю без лимита. Последовательность «получить → сохранить атомарно → зафиксировать курсор». Max ID первой страницы не означает, что всё между checkpoint и max сохранено. Отмечай границы покрытия и причину остановки; missing ID может быть удалённым постом/служебным элементом, а не обязательно потерей — не делай вывод без основания.

Для bot используй persistent processed_updates/offset: commit записи сообщения и фиксации обработанного update согласован; при сбое повтор безопасен. Даже повтор одного update не плодит бизнес-событие. Раздели per-channel message IDs и глобальный update cursor. Таймаут long polling, restart и retry не должны скрывать возможный пробел. Предел хранения неполученных обновлений проверь по официальному API; не называй bot архивом канала.

Раздельные интервалы проверки новых и недавно редактированных сообщений допустимы при поддержке транспорта и допуске. Старые edits вне фактического recheck-window обозначаются как ограничение. Ограничивай concurrency, max pages/time, retry/backoff. blocked_by_policy не retry-ошибка. Allowed user IDs пустой — никого не принимать. HTML из Telegram показывай только как безопасный текст.

## Приёмка

Первая страница не покрывает backlog; сбой до/после сохранения страницы; replay update; edit существующего message; одинаковый текст разных каналов; короткое опровержение; forwarded post с отсутствующим origin; caption без вложения; пустой user allowlist; отзыв policy во время прохода; перезапуск long polling. Проверяются отсутствие потери, дубликатов и ложного full coverage.

В отчёте раздельно: адаптер на фикстурах, состояние каждой возможности и конкретный live-source smoke. Если допуск/ключи не подтверждены, live NOT_RUN и источник disabled; разработка зависимых этапов на синтетике допустима. Не проси ключи вставить в чат; покажи имена нужных локальных переменных без их значений.

## Откат

Pause адаптера, сохранение cursor/revisions и диагностического состояния. Не обнулять checkpoint для «чистого старта» и не запускать заново всю историю без отдельного действия.
