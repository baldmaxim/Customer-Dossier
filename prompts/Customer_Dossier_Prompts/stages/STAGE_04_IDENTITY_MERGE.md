# Этап 04 — Юридические лица, объекты и безопасное слияние

Ты — основной инженер Customer Dossier. Выполни только этот этап в существующем локальном проекте.

## Перед началом

Прочитай `COMMON_RULES.md`, `ROADMAP.md`, `reference/DATA_CONTRACTS.md`, `acceptance/TEST_MATRIX.md` из пакета. Проверь реальные инструкции репозитория, `docs/development/STATE.md`, `HANDOFF.md` и отчёты зависимостей: **03B**. Отсутствующий отчёт не придумывай. Источник истины о реализации — рабочие файлы и фактические тесты.

Ниже приведены пути из inspected-архива. Если структура изменилась, найди эквиваленты поиском внутри проекта и зафиксируй соответствие, не создавай дубликаты модулей.

## Обязательные точки чтения

`backend/src/resolve/company.ts`, `project.ts`, `identity.ts`, `normalize.ts`, `merge.ts`; `api/manual.routes.ts`, `api/companies.routes.ts`; entity-resolution миграции; новые mention/assertion/evidence/review связи.


## Цель

Не приписывать одной компании объекты другой и не склеивать ЖК только по названию. Ручное слияние должно иметь preview, историю и безопасную стратегию исправления ошибки.

## Идентификация

Раздели legal_entity, brand и group в данных. Выбери совместимое расширение существующей companies-модели или отдельный реестр, не делая две конкурирующие canonical базы. Для реквизитов нужны jurisdiction, identifier_type, value, validation_status, evidence и период при наличии. ИНН, ОГРН и иной национальный идентификатор — разные типы. Корректная контрольная сумма — только формат; реквизит должен относиться к тому же субъекту в цитате.

Exact alias/name никогда не обходят конфликт реквизитов. Совпадающее название без идентификатора не даёт права выбрать первый из нескольких candidates. Название бренда не получает автоматом реквизиты дочернего ООО. Разные ОПФ/реквизиты требуют раздельных candidates либо доказанного исторического изменения, не догадки. Общий телефон, домен, адрес и руководитель могут быть отдельными сигналами для ручной проверки, но не основанием автоматически считать компании одним юрлицом или группой. Бытовые/семейные сведения о людях не собирать.

Не создавать искусственно «пустые дубли» при каждом повторе: provisional entities имеют стабильные mention/evidence anchors, а ambiguous matching поступает в очередь. Сохрани единый нормализатор для поиска и записи. Ренормализацию реализуй как версионный/проверяемый backfill на копии, без автоматического запуска на рабочей базе.

## Объекты

Сохраняй project → phase → building/corpus, географию и адрес с источником. Одинаковый ЖК в разных городах, корпуса одного ЖК и одноимённые очереди не объединяются в одну запись. Неизвестный город не равен совпавшему. Географию не подставлять из прописки компании или профиля канала. Внешние project IDs/адресные нормализаторы использовать только реально подключённые, без нового платного сервиса. Общий участник проекта — вспомогательное evidence, а не доказательство идентичности объекта.

## Merge

Сделай preview: обе сущности, реквизиты, конфликты, число переносимых зависимостей, последствия для утверждений, review и исторических ссылок. Apply требует явного действия оператора, expected entity versions и idempotency key. Блокируй известный конфликт legal IDs. Получай блокировки в стабильном порядке, проверяй collision уникальностей до записи, сохраняй before/after mapping и actor. При конфликте откатывается вся операция, а не только последняя строка.

Не удаляй исходную сущность физически. Сохрани redirect/merge mapping, immutable original IDs и происхождение. Duplicated evidence объединяется только при совпадении своей идентичности, а conflicting evidence остаётся. Ручные decisions не теряют автора/времени и не переносятся безусловно на другой смысл.

Реализуй безопасную отмену merge при выполненных preconditions на неизменившемся наборе зависимостей. Если после merge появились новые данные, не обещай простой undo: покажи конфликт и подготовь компенсирующий split/reassignment plan без автоматического применения. Проверка rollback на копии обязательна. Исторические entity labels для будущих snapshots должны оставаться восстановимыми либо сохраняться в payload снимка.

## Приёмка

Разные известные ИНН при одном имени; одинаковый бренд/ООО; ambiguous exact alias; неизвестная география; одинаковые ЖК в двух городах; два корпуса; один объект с разными вариантами названия; merge duplicate evidence; merge с conflict FK/unique; две одновременные операции; повтор apply; undo без поздних изменений и отказ unsafe undo после них. Проверь также поиск по alias/типизированному идентификатору и отсутствие прежней ошибки выбора первой строки.

## Вне этапа

Автоматическое расследование собственников, поиск бытовых данных, внешние юридические реестры без подключения, массовые рабочие merges и отдельная Neo4j. Схема визуального графа — этап 08B. Откат — выключение apply merge при сохранённой истории и read mapping, не обратный destructive SQL.
