# Дорожная карта и зависимости

**Нумерация:** 00–09 — 10 крупных этапов. Этапы 03, 05 и 08 разделены на два отдельных запуска. Итого 13 промтов. Идти последовательно в указанном порядке; автоматической цепочки нет.

| Запуск | Зависит от | Результат, который должен существовать до перехода |
|---|---|---|
| 00 | Нет | Проверены рабочая папка и команды; определены безопасный стенд, старые дефекты, baseline |
| 01 | 00 | Безопасный локальный startup и тестовый target; защищённые операции; policy gate; устранены конфликтующие инструкции |
| 02 | 01 | SourceItem/Revision хранят историю и полноту; миграция не портит legacy |
| 03A | 02 | Утверждения/evidence/review имеют отдельную жизнь; есть минимальный API проверки |
| 03B | 03A | Append-only run/chunk; новый атомарный apply; reprocess не удаляет решения |
| 04 | 03B | Типизированные идентификаторы; различение бренда и юрлица; безопасный merge |
| 05A | 04 | RSS/HTML-адаптеры работают на фикстурах через безопасный клиент и версии |
| 05B | 05A | Telegram-адаптеры с честным покрытием и отдельной проверкой реальных источников |
| 06 | 05B | Семантическое извлечение, типы связей/событий, временные состояния и противоречия |
| 07 | 06 | Объяснимые сигналы, отдельные даты и происхождение, отсутствие старого risk-score в новой карточке |
| 08A | 07 | Досье компании/объекта/обращения, просмотр цитаты и ручная проверка в UI |
| 08B | 08A | Доказательная схема, фиксируемый снимок, экспорт без сети |
| 09 | 08B | Сквозной сценарий, backup/restore, описанные локальные ограничения |

## Почему такой порядок

До расширения сбора защищаем данные и историю. До красивой аналитики отделяем утверждения от фактов и правильно идентифицируем компании. До снимков обеспечиваем объяснимые read-models. Ранние этапы дают инфраструктуру данных, поздние — заметный результат в интерфейсе; не выдавать пустую новую таблицу за готовое досье.

## Три разных уровня готовности

- **LOCAL_FIXTURE_READY:** локальная БД, API и интерфейс работают на синтетических материалах; все обязательные core-gates пройдены.
- **LOCAL_MODEL_VALIDATED:** дополнительно реально проверена настроенная локальная модель на согласованной выборке; зафиксированы ошибки и фактические параметры.
- **LIVE_SOURCE_VALIDATED:** конкретный названный источник имеет допуск и прошёл отдельный живой smoke с журналом. Это отметка каждого источника, а не всего Интернета.

Неподключённый реальный источник не мешает проектировать следующий экран на фикстурах. Но провал целостности версий, сохранения ручных решений или изоляции тестовой БД блокирует зависимые изменения. Нельзя назвать релиз рабочим на живых источниках только по красивому seed-demo.

## Работа с предыдущим reviewed-архивом

Пакет подходит как к исходному проекту, так и к reviewed-копии и более новой локальной ветке. Этап 00 составляет patch coverage: присутствует / отсутствует / частично / изменён другим решением. Этап 01 устраняет обнаруженные P0-регрессии старого патча адресно. Ничего не применять повторно только по имени архива.

Исторические R01–R20 из анализа закрываются так:

| Риски | Основные этапы |
|---|---|
| R01–R04, R18–R20: точечные исправления старого патча | Проверка 00, адресное восстановление 01, развитие 04/06/07 |
| R05–R07: неполные разборы, provenance, утрата review | Защита 01, модель 02/03A, новый apply 03B |
| R08–R09: даты, суды, ответственность и risk-score | Временно маркировать legacy в 01, полностью заменить в 06/07 |
| R10–R11: доступ, сеть, допуск источников | 01; регрессия 05A/05B/09 |
| R12–R14: Telegram, правки, сайты | 02/05A/05B |
| R15–R16: время и слияние событий/упоминаний | 03B/04/06 |
| R17: опасный merge | Выключить небезопасную запись в 01, реализовать в 04 |

Полноценный SSO, публичный сервер и несколько операторов — отдельная будущая ветка, не скрытая часть этого плана.
