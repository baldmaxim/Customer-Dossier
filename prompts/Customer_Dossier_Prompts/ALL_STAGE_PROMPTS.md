# Общие правила исполнения каждого этапа

Прочитай этот файл заново в каждой новой сессии. Это задания для разработки **Customer Dossier**, не для других проектов пользователя. Не переносить сюда решения Quantor или «Нормирования».

## 1. Цель и доказательность

Компания/юрлицо → конкретный объект/корпус → роль/пакет работ/период → доказанные связи → события → досье по обращению. Совместное упоминание, совместное участие, прямой договор и корпоративная связь — разные сущности. Не выводить договор транзитивно. Не переносить неблагоприятные сообщения на группу, однофамильную компанию или всех участников объекта. Не изобретать реквизиты, географию, стоимость, НДС, сроки, авансы или причины задержки.

Цитата подтверждает, что написано в источнике, а не истинность сообщения. Отрицание, предположение, планы и оспаривание сохранять. Отсутствие информации не превращать в зелёную оценку. ИНН/ОГРН с корректным форматом не доказывает связь реквизита с упомянутой компанией.

## 2. Фактическая база важнее старого отчёта

Проверь cwd, доступные инструкции, Git status/HEAD/diff и реальные файлы. Если `.git` отсутствует, явно укажи и используй снимок файлов/хеши; не придумывай commit. Старые reference-документы — свидетельство о переданном архиве на 11.09.2026, не о сегодняшней рабочей папке. Наличие текста «исправлено» не доказывает установку исправления.

Не перезаписывай незакоммиченные изменения пользователя. Если они затрагивают ту же строку, интегрируй только после сравнения; неясный конфликт изолируй. Не запускай старые команды из CLAUDE.md автоматически. Конфликтующие указания сначала перечисли, затем устрани в рамках этапа 01, сохранив полезные правила. Не заменяй CLAUDE.md, AGENTS.md и правила Cursor целиком и не создавай постоянные настройки всех трёх инструментов без отдельного указания.

## 3. Разрешённый объём и режим работы

Отправленный пользователем этап разрешает исследовать и реализовать **только этот этап**, запускать безопасные проверки и писать отчёты. Не запрашивай повторное подтверждение каждого файла, индекса или теста. Сначала кратко обозначь план и затрагиваемые модули, затем работай. На границе этапа остановись.

Без отдельного разрешения запрещены: commit/push/merge/rebase/reset/clean/stash, публикация, внешние уведомления, новые платные сервисы, смена runtime LLM на облачный, запись в рабочую БД, массовый backfill/reextract/renormalize/merge рабочих данных, включение новых источников и изменение секретов. Тестовый merge как функция приложения разрешён на изолированных синтетических данных; Git merge — нет.

Не ослабляй защиту, чтобы пройти тесты. Не добавляй bypass permissions, автодеплой или фоновые задания вне локального приложения. Не запускай следующие этапы ради красивого итогового отчёта.

## 4. Локальная безопасность без избыточной архитектуры

Сохраняй текущий стек, если локальная проверка не выявила объективный блокер: TypeScript, Express, PostgreSQL с pg, React/Vite. Одно приложение и локальная БД допустимы. Не добавляй брокер, ORM, графовую БД и микросервисы только ради дизайна.

По умолчанию loopback, один оператор, изменяющие операции защищены, ingest/bot/pipeline/автопересчёт выключены до явного включения. Не полагайся на CORS как на авторизацию. Не кэшируй чувствительные API в PWA. Локальный режим не обещает защиту от вредоносной программы с доступом к компьютеру.

У парсера внешних сайтов и у доверенного клиента локальной LLM разные сетевые политики. Блокировка SSRF для источников не должна ломать разрешённый loopback LM Studio; исключение для LM Studio не должно открывать loopback произвольным ссылкам публикаций.

Разрешённый сбор и разрешённая ИИ-обработка проверяются отдельно на каждом входе: шедулер, CLI, бот, ручной импорт и повторная обработка. Неподтверждённое основание — отключённая соответствующая операция, не догадка агента. Код и синтетические тесты можно разрабатывать без новых внешних данных.

## 5. Данные и миграции

Рабочая БД не испытательный стенд. До DB-тестов проверь фактические host/port/database/роль без печати пароля. Одного суффикса `_test` мало: нужна явно выделенная цель и проверка несовпадения с рабочей. Если её нет, подготовь проверку и пометь NOT_RUN; не используй DATABASE_URL по умолчанию. Создание новой тестовой БД допустимо только в подтверждённо локальном тестовом контуре, без изменения системных служб или удаления существующих баз.

Проверяй тестовые setup-файлы, скрипты установки и startup до запуска. Не запускай `npm run dev` как безобидный просмотр, пока не доказано отключение фоновых обработчиков. Не печатай `.env`, bot token, пароль, DSN, персональные данные и полные тексты источников в отчёте. Значения секретов не передавай субагентам.

Применённые миграции 001–009 не переписывать. Новые номера определяй по актуальному реестру, а не жёстко считай следующий номер 010. Для изменения схемы: расширение → проверяемый backfill на копии → сверка → переключение совместимого read/write пути → старый путь выключен. Удаление старых таблиц в эти этапы не входит. Совместимость не означает запуск старого destructive apply параллельно новому.

Каждый backfill — явная отдельная команда с dry-run, пределом батча, контрольными количествами, идемпотентностью и checkpoint. Не запускать автоматически из migration/startup. Если исторических данных не хватает, сохранять unknown/legacy_unreviewed; не создавать фиктивные доказательства. Откат приложения после переключения — безопасный read-only/feature-off или восстановление тестового backup, а не возврат к удалению ручных решений.

## 6. Дисциплина исполнителя и проверяющего

Один исполнитель пишет в рабочее дерево. До трёх помощников можно использовать для чтения: схема/данные, сбор/безопасность, интерфейс/тесты. Реальное число зависит от доступных инструментов. Независимый проверяющий не исправляет код, который одновременно меняет исполнитель. Изолированный worktree — только при наличии Git и явной необходимости; не создавать и не коммитить изменения автоматически.

Показывай найденные важные проблемы по мере работы. Не выдавай длинное внутреннее рассуждение; нужны решения, обоснования, затрагиваемые файлы и доказательства тестов. При нехватке контекста запиши handoff и остановись, не срезай тесты. Большое окно 1M не отменяет деление на этапы.

## 7. Проверки и статусы

Используй реальные scripts из package.json; отсутствующую команду сначала реализуй в текущем этапе. Транспиляция не заменяет semantic typecheck, unit-тесты — интеграцию PostgreSQL, а синтетический ответ LLM — проверку реальной модели. Для UI нужны smoke/e2e и фактический просмотр, если браузер доступен. Нет браузера — `UI_VISUAL=NOT_RUN`, а не «выглядит хорошо».

У каждой проверки: ID, команда, окружение, exit code, наблюдение, путь к логу. Статусы: PASS, FAIL, NOT_RUN, BLOCKED, NOT_APPLICABLE с причиной. Для этапа: PASS только при выполненных обязательных условиях; иначе BLOCKED/FAIL/IN_PROGRESS. Отдельный необязательный live-smoke может быть NOT_RUN при PASS локальных core-gates. Не приравнивать к PASS запланированные проверки, старые логи и слова другой модели.

Не удаляй тесты и не понижай пороги ради прохождения. Исправляй вызванные этапом регрессии. Не связанные старые дефекты фиксируй в BACKLOG с влиянием на gate, а не скрывай.

## 8. Обязательный результат этапа

В `docs/development/` веди STATE.md и HANDOFF.md, в `docs/development/stages/` — `<STAGE_ID>_REPORT.md`; подробные логи в `docs/development/evidence/<STAGE_ID>/` без секретов. Используй шаблоны из пакета, не копируй пустой шаблон поверх существующего отчёта.

STATE содержит текущий/последний прошедший этап, target БД в обезличенном виде, активные feature flags, неразрешённые действия, следующие условия. Отчёт: исходное состояние, изменения, миграции, тесты, ограничения, что не сделано, откат и перечень затронутых файлов. HANDOFF — краткий вход для новой сессии с реальными путями.

Финал: что изменилось для пользователя; какие гейты пройдены; что не проверено; безопасность данных; точное имя следующего промта. Не объявлять готовность production: цель пакета — подтверждённая локальная версия.

# Этап 01 — Безопасный локальный запуск и защита изменений

## Обязательные точки чтения

## Реализация

**1. Воспроизводимое окружение.** Проверив scripts и lock-файлы, установи зависимости стандартной воспроизводимой командой проекта. Обоснуй любые изменения lock-файла; не запускай массовое обновление и автоматическое force-исправление зависимостей. Добавь явную конфигурацию unit/integration-тестов, которая не наследует рабочий DATABASE_URL. Отдельный test-target и проверка его идентичности обязательны до DML.

**2. Startup.** Введи раздельные явные флаги для ingest scheduler, bot, extraction worker и auto-metrics. По умолчанию выключены в безопасном локальном профиле; API/UI можно открыть без внешнего сбора. Парси boolean строго: false и 0 не становятся true из-за непустой строки. Неверное значение — понятная ошибка. Не включать задания автоматически миграцией, seed или импортом файла. Проверь loopback у API, Vite и preview; не разрешай `--host 0.0.0.0` как штатный сценарий.

**3. Локальный оператор.** Защити изменения source/review/merge/reprocess и выдачу закрытого досье серверной авторизацией. Выбери один простой механизм для одного оператора и кратко обоснуй: например, локальный bootstrap-token → короткая серверная сессия. Секрет не зашивать во frontend, URL, лог и localStorage; маскировать в ошибках. Проверять Origin/Host и CSRF для cookie-based записей; CORS не заменяет эти проверки. Проверяй logout/expiry. Не превращать задачу в регистрацию пользователей или RBAC. Флаг LAN/public не открывать до будущего отдельного этапа.

**4. Сетевая политика.** Создай единый клиент для внешних источников: разрешённые hosts, только нужные схемы/порты, ограничения времени и размера, проверка адреса назначения и каждого redirect; запрет служебных/локальных адресов и обходов через DNS. Не делай исключение «все адреса разрешены в development». Локальная LLM — отдельный фиксированный доверенный endpoint, который не получает URL из публикаций. Источники и LLM не используют общий безусловный allowlist. Конкретные проверки сверяй с официальным OWASP в reference/SOURCES.md.

Сохрани просмотр существующей базы, но запуск изменяющего pipeline требует безопасного пути, которого пока нет. Устрани конкретные противоречия CLAUDE.md, но не удаляй полезные инструкции. Не запускай автоматический `--renormalize` после изменения нормализатора.

Восстанови отсутствующие адресные исправления старого патча из PATCH_COVERAGE с локальными регрессионными тестами, не применяя весь старый patch поверх изменённого дерева.

## Модель и переход

Спроектируй и реализуй SourceItem с устойчивым `(source_id, external_id)` либо корректной canonical URL в пределах источника, DocumentRevision с номером/порядком версии и неизменяемым содержимым, отдельные наблюдения fetch/ingest. Хеш контента помогает дедупликации, но не подменяет личность публикации. Один текст в трёх каналах — три публикации/наблюдения, а не одна публикация с неизвестным владельцем.

Храни original/published/modified/fetched/observed даты отдельно; отсутствие даты оставь null. Сохраняй raw/cleaned text и версию очистки либо другое явно описанное представление, позволяющее воспроизвести цитату. Полнота: full, excerpt, caption_only, failed, unknown. Длина не доказывает полноту. Неподдержанное вложение отражается как неподдержанное, а не «прочитано».

При изменении текста появляется новая revision; при повторе последней версии — только наблюдение. Возврат текста A → B → A является новой наблюдаемой редакцией, а не возвратом ссылки на первую revision без истории. Параллельные fetch одного состояния не плодят версии; поздно пришедшее старое наблюдение не объявляется достоверно новым состоянием источника. Если источник не даёт reliable modified_at/order, сохраняй uncertainty вместо выдуманной chronology. Раздели latest_observed и source_effective_at.

Уточни политику canonical URL: не удалять параметры, от которых зависит статья; tracking-параметры только из известного списка. Одинаковый заголовок/lead не склеивает разные статьи. Неполная подпись и полный текст одной новости не уничтожают друг друга. Удаление, если оно реально наблюдалось, — отдельное состояние/tombstone, не физическое удаление источника и всех цитат. «Не получили в выборке» не доказывает удаление.

## Legacy

Новые миграции только расширяют схему. Подготовь идемпотентный backfill, связывающий raw_documents/document_sightings с source items/revisions, с отчётом сопоставления и неоднозначных наблюдений. История, которой раньше не было, не восстанавливается догадкой: `legacy_import`, `history_before_import=unknown`. Сохрани legacy IDs и provenance. Повтор backfill не удваивает строки. Рабочий backfill не выполнять.

Адаптируй сохранение документов так, чтобы новые версии записывались атомарно, но не попадали в старый destructive apply. Новый сбор пока остаётся выключенным для реальных источников. Existing read API продолжает читать legacy либо совместимый read-only bridge; текущий контент нельзя молча переписать, если к нему привязаны цитаты.

## Минимальные API

Чтение публикации, списка revisions, конкретной revision, полноты и source health. Строго ограниченный diff двух версий без исполнения HTML и внешних запросов из текста. Изменяющие операции проходят защиту этапа 01. Начальная UI-панель версии допустима, полный редизайн не нужен.

## Приёмка

На реальной тестовой PostgreSQL проверь: одинаковый external_id + новый текст; повтор последнего текста; A→B→A; гонку двух одинаковых inserts; одинаковый текст разных источников; caption/full; URL с содержательными query-параметрами; исправление без даты; «пропал из страницы» без ложного delete. Проверяй FK, уникальности и отсутствие потери старой ссылки на документ. Backfill запускается дважды с одинаковым итогом; несовпадения отражаются в отчёте, а не игнорируются ON CONFLICT DO NOTHING.

## Вне этапа и откат

Не вводить assertion truth status, новый risk-score, parser backfill Telegram или массовый переразбор. Откат: отключить новую запись, оставить старое чтение и новые неизменяемые таблицы; не удалять накопленные revisions. Старый apply остаётся выключенным.

# Этап 03B — Новый конвейер и безопасное переизвлечение

Ты — основной инженер Customer Dossier. Выполни только этот этап в существующем локальном проекте.

Проверь реальные инструкции репозитория, `docs/development/STATE.md`, `HANDOFF.md` и отчёты зависимостей: **03A**. Отсутствующий отчёт не придумывай. Источник истины о реализации — рабочие файлы и фактические тесты.

Ниже приведены пути из inspected-архива. Если структура изменилась, найди эквиваленты поиском внутри проекта и зафиксируй соответствие, не создавай дубликаты модулей.

## Обязательные точки чтения

`backend/src/pipeline/worker.ts`, `chunks.ts`, `apply.ts`, `compare.ts`, `recheck.ts`, `cli.ts`, `cli-commands.ts`, `llm/client.ts`, `llm/schema.ts`; новые Assertion/Evidence/Revision таблицы; исторические `clearDocumentContribution`, `recordExtraction`, `mergeChunkExtractions`.


## Цель

Перевести обработку на новый путь revision → immutable run/chunks → candidate assertions → проверяемая публикация набора. Удаление всех событий/ролей документа больше не допустимо. Это центральный этап сохранности данных, его нельзя закрыть unit-моками вместо PostgreSQL-интеграции.

## Реализация

Каждый запуск имеет новый run_id, revision_id, fingerprint версии prompt/schema/model/provider/параметров и версии chunker. Каждый chunk — собственный ID, диапазон в исходном представлении текста, response payload/hash, usage при доступности, error/status и число попыток. Исходные ответы не менять. Run-completed не наступает при одном failed chunk или непокрытом хвосте. Если модель/токенизатор не даёт достоверный лимит, указывай приближение и запас, а не выдумывай миллионный контекст локальной модели.

Покрытие считай по объединению реальных диапазонов, учитывай overlap. Идентификаторы mention_id внутри чанков должны быть namespaced; event/role ссылается на mention_id, а не только на строку name. Одинаковые названия с разными реквизитами не схлопываются при merge чанков ещё до резолвера. Два разных суда одной компании не объединяются по одному type/company/project. Перекрывающиеся чанки могут содержать одно утверждение — evidence должны сохранить обе позиции без умножения независимых фактов.

Сохраняй candidate set отдельно от опубликованного. Preview показывает добавления, снятые основания, противоречия, изменения сторон/периодов и влияние на review. Apply фиксирует ссылку на выбранный опубликованный набор транзакционно, с optimistic locking на ожидаемую версию/активный run. При падении читатель видит либо весь старый, либо весь новый набор, не половину. Повтор того же apply идемпотентен. Старый run, завершившийся позже нового, не переписывает актуальную публикацию без отдельного решения.

Нужны lease/claim с ограниченным сроком и fencing/эквивалент против двух worker на одном задании. Не держать DB-транзакцию во время долгого ответа LLM. Отключение или отзыв ai_processing между получением задания и apply перепроверяется; кандидат может быть сохранён технически, но не опубликован вопреки политике.

Сохрани ReviewDecision и evidence других документов. Нерелевантный новый разбор одного документа прекращает только его активный вклад: не удаляет каноническую компанию и чужие подтверждения. Изменение/отзыв source запускает пересмотр зависимостей и отражает статус, а не незаметный зелёный результат. История остаётся доступной в пределах политики хранения.

## Переключение

Реализуй feature-flag/cutover так, чтобы новый pipeline был единственным writer опубликованных facts. Для legacy clients — read adapter/projection из нового слоя, не второй независимый writer. Все CLI: --reextract, --retry, --doc, --recheck и одиночные проходы должны соблюдать новый контракт; частичный обход не должен вызывать старую очистку.

`backend/src/llm/prompt.ts`, `schema.ts`, `vocabulary.ts`, `pipeline/verify.ts`, `worker.ts`, `apply.ts`; новые assertions/evidence и entity model; current project stage logic; `acceptance/SYNTHETIC_CORPUS.json` и DATA_CONTRACTS.md.


## Цель

Превращать публикации в типизированные, проверяемые утверждения с временным смыслом, а не в набор имён и один sentiment. Портал должен отличать договор, участие и слух даже при одинаковой цитате.

## Связи и роли

Реализуй как разные predicates: прямое customer→general_contractor, gc→contractor, contractor→subcontractor, supply; участие компании в конкретном project/phase/building с ролью, work_package и периодом; корпоративное участие/контроль/принадлежность к группе; co_participates/co_mentioned. Названия predicates согласуй с общей схемой и ADR, не создавать дубли synonyms.

Для прямого договора нужно самостоятельное основание именно между этими сторонами. Если А и Б на одном ЖК, допустима co_participation, не contract. А→Б→В — путь из двух рёбер, не факт А→В. Владение и участие в группе не выводятся из общей стройки/домена. Один подрядчик может иметь разные роли и набор работ в разных корпусах/периодах; неизвестный пакет остаётся null. Роль не свойство компании вообще.

Раздели polarity (positive/negative), modality (reported fact/claim/planned/possible), evidence relation (supports/contradicts) и review status. Фраза «не является» не создаёт положительную роль. «Планирует заключить» — план, не договор. «По неподтверждённым данным» — атрибутированное сообщение, не утверждённый факт. Даже reviewed_supported означает подтверждение в указанном объёме, а не безусловную юридическую истину.

## Время и события

Храни отдельно время публикации/наблюдения, дату или интервал события, точность и период действия отношения. Не заполнять occurred_at сегодняшней датой. Для месяца/квартала/года не выдумывать точный день. У состояния объекта нужны valid time и время регистрации в системе; старая статья, полученная сегодня, не затирает более позднее основание. Допускай приостановку и возобновление, а не только движение вперёд по enum.

У суда: устойчивый номер при наличии, стороны и процессуальная роль, тип заявления/решения, стадия и результат только по источнику. Требования и присуждённая сумма различаются; отменённое/обжалуемое решение не считать окончательным автоматически. Банкротное намерение/заявление/процедура — разные события. Платёжная претензия хранит автора сообщения, предполагаемые стороны, договор/объект, статус подтверждения. Числовую оценку виновности не реализовывать.

Event clustering: точный внешний идентификатор при наличии, участники, предмет и даты с evidence. Два дела одной компании в одной статье сохраняются раздельно; перепечатки одного события группируются без потери наблюдений. Unknown case ID не даёт права склеить всё по type/company. Связанные стадии дела — история одного case, а не пять самостоятельных «негативных случаев».

Суммы — decimal/string через API, валюта, units, purpose (claim/award/contract), tax basis только по тексту. Не преобразовывать валюты и не вычислять НДС автоматически. Реквизит/сумма проверяются в собственном утверждении, включая нескольких участников внутри одной цитаты; само наличие числа в цитате не доказывает привязку.

## Проверка и локальная модель

Расширь схему и prompt версиями, совместимыми с реально настроенной моделью. Старые extractions не править. Наличие mention names/quote — обязательная текстовая проверка, но недостаточная семантическая. При неоднозначности candidate/needs_review, а не принудительный positive edge. Добавь приоритетную очередь противоречий: идентичность, конфликт ролей/периодов, исправление, оспаривание. Очередь не требует второй LLM по умолчанию.

Внешний текст — недоверенные данные. Инструкции внутри новости не меняют системные правила, не вызывают инструменты и не открывают URL. Unit/fixtures тестируют verifier независимо от генератора. Отдельно запусти benchmark настроенной локальной модели на разрешённой/синтетической выборке; при отсутствии модели отчёт NOT_RUN, не придуманные precision/recall. Размер модели/квантование и пороги не менять ради отчёта без измерения.

## Приёмка

Отрицание, план, слух, co-mention без договора, два договора на разные корпуса, судебные стадии и разные дела, company plaintiff, старое событие без даты, restart стройки, поздняя статья, нового подрядчика нет в период старой задержки, чужая сумма в соседнем предложении, prompt injection. Общий risk-score, самостоятельная правовая экспертиза, автоматический поиск владельцев, fine-tuning и массовая обработка рабочей базы. Откат — предыдущий prompt/schema для новых кандидатов с сохранением всех run, без удаления старых данных.

## Резюме и формулировки

Начни с детерминированных шаблонов поверх structured facts, работающих без LLM. Каждая существенная фраза содержит assertion/evidence IDs; «не установлено» и отсутствие сведений различаются. «Компания заявляет…», «в публикации сообщается…», «аналитиком проверено…» не смешиваются. Итог не является автоматическим решением о сотрудничестве.

Опциональное LLM-перефразирование не требуется для PASS. Если оно добавляется в пределах существующего runtime, оно читает только выбранный evidence set, не вызывает инструменты, проверяется на добавленные факты и имеет fallback к шаблону. Никакого нового облачного провайдера или массовой выгрузки досье.

## Визуальное решение

Сохрани узнаваемый стиль проекта и существующий стек, но обеспечь ясную иерархию: резюме → предмет обращения → доказательства → подробности. Русские полные подписи, читаемые суммы/даты, отсутствие горизонтального скролла основной карточки на типовом desktop. Таблицы деталей могут иметь собственный скролл. Цвет не заменяет текстовый статус. Важны loading/empty/error/stale/unauthorized states и клавиатурная доступность.

Не удаляй текущие полезные экраны и фильтры без замены. Не подключай дизайн-систему с полной переписью frontend. API types согласуй с backend, нельзя сгенерировать фиктивные JSON лишь для красивого экрана. Fixture demo — только явный тестовый режим/отдельная база.

# Этап 08B — Доказательная схема связей, снимки и экспорт

Ты — основной инженер Customer Dossier. Выполни только этот этап в существующем локальном проекте.

## Обязательные точки чтения

## Схема связей

Узлы: юридические лица/бренды/группы и объекты с корпусами. Рёбра имеют тип, направление, объект/пакет работ/период и статус. Договорные, корпоративные и информационные связи визуально и текстом различаются; co_mentioned по умолчанию скрыто. Не использовать толщину/цвет как вероятность надёжности. Путь А→Б→В не рисует прямого договора А→В.

Фильтры: проект/корпус, период, тип связи, только проверенные/включая сообщения, глубина и лимит узлов. Ограничивай запросы и рекурсивный обход, обрабатывай cycles. Вместо нечитаемого «облака» — приоритет текущему обращению и раскрытие соседей. Есть табличная альтернатива для доступности и больших графов. Выбор ребра открывает exact evidence/revision/quote и противоречия. Не создавай отдельную графовую БД. Библиотека визуализации — минимальная, с объяснением причины и проверенной совместимостью; текущий стек предпочтительнее.

## Снимок

Создай DossierSnapshot с immutable payload, schema_version, case_id, generated_at, data_cutoff/knowledge_cutoff, effective-date filter, rules version, selected assertion/evidence/review IDs и воспроизводимыми labels. Если summary создаёт модель, хранить готовый текст + provenance/config fingerprint; повторный просмотр не генерирует его заново.

Различай: «что система знала к дате T» и «события за период T, которые мы знаем сейчас». Создание исторического knowledge-as-of требует реальных recorded_at/history; если legacy не хранит нужную историю, не обещай точный срез прошлого. Снимок, созданный сегодня, воспроизводим с этого момента; старый effective_date filter не превращает его в документ, существовавший в прошлом.

Снимок хранит замороженную структуру/формулировки/разрешённые цитаты и ссылки на точные revision. Одних FK на mutable company name/active review недостаточно. Merge/новая публикация/пересчёт метрик/переименование компании не меняют payload старого снимка. Сохраняй hash по явно определённой canonical serialization; hash показывает целостность payload, не нотариальную/квалифицированную подпись и не истинность фактов.

Права на хранение/выдачу продолжают действовать: при отзыве доступа не раздавать snapshot в обход policy. Раздели immutable content и current availability/revocation state. При обязательном удалении защищённых фрагментов действуй по утверждённой политике, сохраняя разрешённые tombstones; не обещай «никогда нельзя удалить» вопреки правилам. Экспорт не делает сайт-источник свободным для перепубликации.

## Экспорт

Обязательный минимум: Markdown, JSON и самодостаточная HTML-версия для локальной печати в PDF через браузер. Это не равно нативному серверному PDF-export; подпиши действие честно «Версия для печати». Нативный PDF можно отложить без провала этапа. Не добавляй cloud render service и обязательные внешние шрифты. Все выгрузки строятся из выбранного snapshot, не из текущей БД.

Включи заголовок, компанию/реквизиты, предмет обращения, дату создания/среза, существенные выводы, таблицы ролей/событий, вопросы и ограничения, список источников с цитатами/версиями. Escape/sanitize HTML/Markdown-ссылки, разрешённые URL schemes; в экспорт не попадают tokens, stack traces и технический контекст модели. HTML не исполняет scripts и не тянет внешние ресурсы. JSON имеет явно документированную схему и decimal strings. При выдаче защищённого экспорт-файла проверяй доступ; не клади его в публичную static папку.

## Приёмка

Построй snapshot S1 → измени исходную публикацию/имя компании/merge/rules → S1 показывает прежний payload, S2 — новое состояние. Сохрани различие knowledge/effective dates. Review conflict и missing evidence отражаются в снимке. Graph не делает транзитивный договор. Каждый edge и важное предложение открывает основания. Экспорт HTML/MD/JSON совпадает по существенному содержанию, работает без сети и не исполняет вредоносный фрагмент источника. Проверяй доступ после logout и отзыва source policy. Распечатка не обрезает таблицы/русский текст, если доступен браузер.

## Откат

Отключить новые graph/export routes, не изменяя ранее созданные snapshots. Недоступный evidence показывает понятное ограничение, а не заменяется цитатой из свежей версии. Рассылка досье внешним адресатам не входит в этап.
