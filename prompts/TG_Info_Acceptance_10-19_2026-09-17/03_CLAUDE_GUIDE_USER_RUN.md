# Промт 03 — сопровождать пользовательскую приёмку по одному шагу

Ты сопровождаешь владельца локального TG_Info / Customer Dossier. Не исполняй вместо него Docker, PostgreSQL, миграции/seed, DB-интеграцию, browser/Playwright, dump/restore, benchmark/EXPLAIN, реальную модель и источники. Ограничение сохраняется, даже если соответствующий tool технически доступен.

Прочитай baseline/coverage и консолидированную инструкцию, все относящиеся USER_RUN этапов 10–19, README этого пакета и независимое ревью. Если инструкция ещё не подготовлена, сначала выполни только документальную часть промта 01, не выдумывай shell-команды.

## Правило общения

Дай ровно один следующий шаг или одну неделимую безопасную группу команд. Для него: зачем; в каком терминале/каталоге; точная цель; что будет изменено; команда; что считать успехом; какой обезличенный вывод прислать. После этого остановись до результата. Не выдавай сразу несколько страниц команд с записью.

Пользователю не нужно самому выбирать схемы или угадывать переменные. Разрешай это чтением проекта. Если существенная безопасная цель реально неизвестна, не запускай и не предлагай угадывать её. Можно продолжить независимую read-only подготовку.

Отпечаток, имена scripts и пути берутся из рабочей папки. Не добавляй watch-флаги, нестандартные параметры или пакетные команды, которых нет в установленной версии. Не считать `npm test` автоматически безопасным. Не включать .env/пароли/cookies в команды для пересылки или сообщения.

## A. Baseline и допуск к проверкам

Сверить actual HEAD и релевантный diff, lock hashes, runtime/tool versions, перечень файлов тестов и актуальные логи. Уже имеющиеся полноценные логи того же состояния можно зачесть; не требовать повторять ради счётчика. При сомнении — один полный финальный offline-прогон безопасными scripts.

Разобрать sharp по подготовленному решению для следующих действий. Нерешённый путь обработки недоверенных изображений не включать. Сетевой npm audit запускает пользователь отдельно, он не даёт разрешения на живые источники.

Установить тестовую цель штатным guard. Его отказ — остановка, а не рекомендация поставить APPROVED/маркер вручную на неизвестную БД. Начало инфраструктурных действий требует подтверждённой выделенной цели.

## B. Синтетические данные и сохранность

1. На отдельной тестовой цели свежая установка: весь актуальный набор миграций. Проверить фактическую последнюю версию, не предполагать, что любая схема уже 023. Повторный запуск и dry-run — по существующему контракту.
2. Синтетический upgrade: создать реальную предшествующую схему утверждённым способом, заполнить подходящими legacy-данными, затем 021–023 или фактический новый диапазон. Не имитировать старую базу одним изменением номера в таблице миграций. Это не тест реальных исторических данных пользователя.
3. Полная DB-интеграция итогового кода: охват 10–19 и общая регрессия, а не только новые тесты 15A–19. Фиксировать найденные/запущенные/успешные/пропущенные тесты и exit-code. Не выбирать только зелёные файлы.
4. Проверить критический сквозной сценарий на синтетике: идентичность → область участия → решение → изменения → snapshot/export. Включить отказ позднего чанка, stale preview, одновременные операции и отзыв policy по актуальным тестам.
5. На подготовленном непустом наборе остановить писателей, дождаться завершения активных заданий, снять baseline/manifest, сделать dump и восстановить в другую явно выделенную цель. Сравнить схему/содержимое/снимки/последовательности по контракту. Только после compare — чтение через приложение и контрольная запись. Замеры не запускать между baseline и dump.
6. Реальный restart отдельного процесса и контролируемая недоступность выделенной тестовой БД — только по безопасной инструкции. Не останавливать общий контейнер с чужими базами, не завершать все node-процессы.

Дамп не пересылать. Бинарный dump сохранять штатным выходным файлом инструмента/в контейнере и переносить без текстового конвейера. Проверять exit-code непосредственно после каждой внешней команды, не после следующего успешного Write-Host. Эти детали должны быть уже адаптированы к версии PowerShell в инструкции проекта.

## C. Настоящий рабочий маршрут и замеры

Браузерный сценарий должен идти в действующий локальный API с синтетической БД. Если Playwright перехватывает API и отдаёт fixtures, это UI-проверка с mock, а не реальная сквозная проверка; отразить различие.

Пользователь проходит login → поиск одноимённых компаний → выбор правильного юрлица → конкретные объект/корпус/работы → неоднозначность → актуальный preview → действие → «Запуски» → кандидаты/цитаты → досье → snapshot → HTML/MD/JSON → logout. Негативные ветки: stale preview, отсутствие прав/CSRF, API/DB error, неполные данные.

Печать в PDF, обычная ширина и 390 px проверяются отдельно. Сохранить синтетический пример без обрезки смысловых блоков, легенды и оснований. Скриншот mock-страницы не выдавать за успешную работу API.

Затем отдельно ограниченный большой synthetic dataset, валидный benchmark и планы запросов. До запуска зафиксировать seed, размер, лимиты ресурсов, iterations и критерии; не снимать benchmark на меняющихся данных. EXPLAIN ANALYZE реально выполняет запрос: только в тестовом контуре и по проверенному SQL, не как безусловно read-only команду.

Успешные измерения и ошибки считать отдельно. Показывать N для p95, прогрев, число попыток, аппаратную среду. Одна удача при остальных ошибках не закрывает стабильность. Ускорение не требуется само по себе, если измеренные времена приемлемы; не придумывать SLA после просмотра лучших попыток.

## D. Модель и источники

D1: использовать текущий evaluation path и полную identity конфигурации; не переключать модель самостоятельно. Согласованный размеченный корпус, dev/holdout без перепечаток между ними, параметры и пороги — до оценки. Все провалы, timeout и обрезания остаются в отчёте. Mock safety и actual-model safety раздельны. Закрывать 14B можно подготовкой, но не утверждением качества без эксперимента.

D2: если источники не названы и оснований нет, оставить этот блок NOT_RUN. Не заполнять их из поисковой выдачи. Когда владелец предоставил допущенный перечень, проверить по одному bounded профилю: получение полного текста, правки, дубли, пагинацию, пропуски и политику. Допуск на сбор и на ИИ раздельны. Статус источника относится к конкретному профилю/версии/окну, не ко всему Telegram.

D1 и D2 могут готовиться независимо. Материалы реального источника нельзя использовать для evaluation без подходящего допуска.

## E. Рассмотрение пилота

Прочитать фактический manifest этапа 19 и код pilot:check. Сопоставить обязательные gates с реальными evidence, не только boolean в JSON. Проверка файла — не реальный пилот и не разрешение на его запуск.

Перед пилотом нужны named sources, основания, цель, объём/период, конфигурация модели, ручная проверка, границы хранения/доступа, условия остановки и явное решение владельца. Отсутствующее поле — блокер именно пилота, не причина выдумывать данные.

Не включать автосбор/автослияние/автопубликацию. При чужом ИНН/договоре, нарушении policy, потере решения, изменении старого snapshot, silent partial publish остановить связанные записи и сохранить evidence.

## Ошибки и завершение

Ошибка инфраструктуры, ошибка теста, дефект продукта и невалидное измерение — разные категории. Не ослаблять assertion, guard или порог ради PASS. При подтверждённом дефекте — отдельный промт 04; после исправления новый fingerprint и обоснованный объём регрессии.

После каждого пользовательского результата обновлять только форму evidence с фактическим выводом. В конце использовать промт 05. Пока нет запуска, соответствующие поля остаются NOT_RUN. Старые логи не удалять. Commit/push и изменение статусов готовности не выполнять без отдельно установленного права.
