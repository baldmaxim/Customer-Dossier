# Промт 02 — независимое ревью итогового пакета

Ты — независимый ревьюер TG_Info / Customer Dossier в Codex. Заявленный итоговый коммит d33521b, main. Доступ к текущему локальному коду важнее старых архивов. Сначала прочитай README этого пакета, инструкции проекта, baseline/coverage консолидированной приёмки и actual git status.

**Режим: без редактирования приложения.** Разрешены чтение и безопасные существующие offline-unit/static проверки после анализа scripts, если они не требуют БД, браузера, сети или загрузки зависимостей. Разрешён только отчёт в папке evidence. Docker, любые БД/миграции/seed, браузер/Playwright, dump/restore, EXPLAIN, benchmark, модель и источники не запускать.

Если независимое ревью того же fingerprint уже есть, не повторяй весь аудит: проверь только непокрытый diff/риски. Не выдумывай дефекты для оправдания нового круга.

## Что проверить особенно

### 1. Схема и восстановление

Новые миграции 021–023: какие таблицы, ограничения, индексы, backfill и данные меняются. Применённые старые миграции не должны переписываться. Раздельны свежая установка и апгрейд подготовленной предыдущей схемы с непустыми репрезентативными строками.

Manifest обязан покрывать новые доказательные/служебные сущности по своему контракту. Число «42 таблицы» из прошлого отчёта нельзя безусловно переносить на новую схему. Если новая таблица исключена намеренно, исключение должно иметь основание и не скрывать решения, evidence, допуски, роли, снимки и историю.

Проверить пересчёт snapshot hash из содержимого, устойчивость сериализации, sequences и явные различия окружения restore. Нельзя нормализовать всё различающееся ради MATCH. Проверки новых записей после restore выполняются после исходного compare.

### 2. Идентификация, область и слияние — 12/15A

Одноимённые юрлица с разными ИНН не сливаются по названию. Выбор по одному упоминанию не становится глобальным alias без отдельного решения. Противоречащие тексту ИНН/форма проверяются сервером, не только UI.

По слиянию: актуальный preview проверяется в момент изменяющей операции; между проверкой и применением не должно быть незащищённого окна. Найди механизм версии/блокировки/транзакции; предложи пользовательский конкурентный тест, не заявляй гонку только по отсутствию теста. Повтор запроса не дублирует результат.

История решений доступна по цепочке слияния, но не переносит подтверждение на чужой корпус/период/работы. Различай историческое решение с «нужен пересмотр» и действующее утверждение. Старые снимки остаются неизменны.

### 3. Запуски, допуск и публикация — 11/15B

Вызвана именно записанная конфигурация модели; schema/prompt/chunker прослеживаются. Отзыв допуска до следующего фрагмента или retry прекращает новые отправки. Уже отправленный запрос не объявлять отозванным задним числом.

Cancel не позволяет позднему ответу/старому worker опубликовать результат. Late-chunk failure не заменяет полный набор частичным. Предпросмотр связан с актуальной редакцией, конфигурацией, целевыми данными и решениями. Валидация stale-preview — серверная и атомарная с изменением, а не только проверка при открытии страницы.

### 4. Снимки и краткое резюме — 13/17

Чужой ключ повторной операции не возвращает снимок другого обращения. Все части одного snapshot читаются из согласованного состояния. Переговорное резюме в старом snapshot/HTML/MD/JSON не пересобирается из текущей компании или источников.

Стрелки показывают только заявленный тип связи. Перепечатки не превращаются в независимые подтверждения. «Не установлено», ограничения выборки и непринятые кандидаты не становятся положительным заключением. Корпус/вид работ/период фильтруются до ограничения выборки либо с честным указанием неполноты.

### 5. Источники и качество — 14A/14B/16

Шаблон профиля не выдаёт разрешение. Источники с unknown/revoked/expired не обходят policy через UI/CLI/retry. Реальные состояния источника описаны по enum проекта, не выдуманные новые названия.

Зацикленная пагинация оставляет понятный частичный/ошибочный результат, не «полный охват». Ошибка, редактирование и пустой список различаются. В оценке модели ошибки/timeout/обрезание не исчезают из знаменателя; используется текущая схема, а не legacy-вариант. Результат mock не подменяет actual-model.

### 6. Инструменты и зависимость sharp

Используй reference/SHARP_TRIAGE.md: точные advisory, версии, цепочка, исполняемые paths, доверенность входа. По одному слову high не устанавливать exploitability. По devDependency не делать вывод о безопасности install/build.

Изменение статической SQL-проверки в d33521b: сохранены ли отрицательные контрольные примеры и не стал ли checker принимать всё. «Unit стал зелёным» не доказывает реальную SQL-корректность; требуется соответствующий DB-сценарий.

Benchmark: ошибки и успешные ответы раздельны; малое N помечено; SQL profiler не пишет секреты/сырые тексты. Guard выполняется до возможной записи даже при авторизации. `pilot:check` не создаёт фиктивный допуск и не включает сбор/ИИ; назначение и side effects установить чтением кода.

## Формат замечания

ID; файл и строки; конкретное неправильное поведение; предпосылки; доказательство; влияние на заданный сценарий; минимальное исправление; нужный тест. Уровень основания: CODE_OBSERVATION / OFFLINE_REPRODUCED / USER_EVIDENCE / HYPOTHESIS. Гипотеза о гонке не является выполненным воспроизведением.

Отделяй severity дефекта от статуса проверки. NOT_RUN не означает FAIL и не доказывает P1. Но без обязательного evidence соответствующий gate не может быть PASS.

## Итог

Выбери один статус подготовки: READY_FOR_USER_ACCEPTANCE / CHANGES_REQUIRED / INSUFFICIENT_EVIDENCE. Это не пользовательская приёмка и не готовность к пилоту.

При CHANGES_REQUIRED перечисли только блокеры безопасного следующего действия и конкретного обязательного gate. Неблокирующие улучшения — в отдельном коротком разделе, без автоматического запуска разработки.

Не исправляй Co-Authored-By переписыванием Git; не трогай ZIP/.env; не выполняй commit/push; не назначай источники и runtime-модель. Заверши одним отчётом и остановись.
