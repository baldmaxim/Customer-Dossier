# Промт 05 — разобрать фактические журналы и вынести ограниченное решение

Ты анализируешь результаты пользовательской приёмки TG_Info / Customer Dossier. Не запускай отсутствующие действия вместо пользователя и не исправляй приложение в этом проходе.

## Сначала установить область

Прочитай actual baseline/fingerprint, COVERAGE, USER_RUN_CONSOLIDATED, исходные stage USER_RUN, security triage и полученные журналы. У пользователя не запрашивать дамп, .env, cookies, токены и исходные конфиденциальные публикации. Для оценки отдельных примеров достаточно разрешённой обезличенной выборки; отсутствие доступа отметить.

Сопоставь по каждому файлу: время, команда, cwd, full commit/fingerprint, зависимости/схема, среда, набор данных, exit-code и завершение. Лог без окончания или без привязки к версии — недостаточное доказательство, а не автоматически FAIL.

Исходные 46 файлов/613 backend и 14 frontend — сведения отчёта, не жёсткая квота. Используй фактический полный discovered/executed/pass/fail/skip реестр. Смена версии во время приёмки требует анализа влияния; не объединяй удачные части разных реализаций в один якобы чистый прогон.

## Разделение уровней

1. Offline-code: типы, unit, сборка, build-secret canaries.
2. Fixture DB: fresh install, upgrade, SQL, транзакции, policy/identity/scope/review/snapshot, общая интеграция.
3. Recovery: фактический dump/restore в отдельную цель, содержательное сравнение, чтение и новая контрольная запись по контракту.
4. Operator/UI: настоящий API/browser, 390 px, print, logout, ошибки.
5. Performance: корректность ответов, N, ошибки, прогрев, среда, ограниченный dataset, профили.
6. Model: конкретный fingerprint модели/шаблона/схемы/валидаторов, корпус, реальные ответы и правила оценки.
7. Sources: поимённый перечень, версия профиля, проверенное окно, основания и отдельные допуски.
8. Pilot: фактический ограниченный прогон с ручной проверкой и явным решением владельца.

Проверка `pilot:check` может подтвердить только то, что реально проверяет её код. Успешная валидация структуры файла не означает доказанную истинность заполненных полей, живую работу источника, запуск или разрешение владельца.

## Как оценивать ошибки

- Отказ guard на неправильной цели — ожидаемый успешный негативный контроль, если записей не было.
- NOT_RUN — проверка не выполнена; BLOCKED — нельзя продолжить конкретное действие; FAIL — выполненный сценарий нарушил ожидаемое поведение. Не смешивай.
- Неправильная команда/недоступная среда — отдельная причина, не обязательно дефект приложения.
- High в audit требует конкретного advisory и scope; severity не понижать по желанию. Документированное исключение не равно устранённой уязвимости.
- Ошибки benchmark не включать в «успешный latency» и не прятать за p95.
- Синтетический upgrade не подтверждает реальные исторические данные; mocks не подтверждают реальную модель; component tests не подтверждают браузер.

## Решение

Используй templates/RESULTS_TEMPLATE.md. По каждому gate укажи PASS / FAIL / NOT_RUN / BLOCKED / NOT_APPLICABLE с основанием и областью. NOT_APPLICABLE не применять к обязательному пилотному gate для обхода требований.

Не создавай новые значения runtime enum readiness. В проектном RELEASE_READINESS используй существующий контракт. В отчёте допустимы отдельные человекочитаемые выводы:
- подготовка реализации завершена по имеющимся свидетельствам;
- синтетическая локальная приёмка подтверждена или не подтверждена;
- готовность к рассмотрению ограниченного пилота;
- PILOT_NOT_RUN / полученные фактические результаты конкретного пилота.

GO_LIMITED возможен только для объявленной области по правилам проекта и после решения владельца; не означает PRODUCTION_READY, юридическую достоверность или разрешение на постоянный сбор. Нельзя авторизовать пилот вместо владельца.

Сформируй мини-резюме для руководителя: что уже можно демонстрировать/использовать в согласованных пределах, какие данные пока нельзя считать проверенными, что блокирует следующий конкретный шаг. Затем таблицу проблем с evidence и минимальным действием.

При недостающих логах дай одну точную следующую проверку. Не отправляй владельца проходить весь пакет заново, если остальное подтверждено. Код, статусы и Git не менять автоматически; подготовленный вывод — основание для отдельного утверждения.
