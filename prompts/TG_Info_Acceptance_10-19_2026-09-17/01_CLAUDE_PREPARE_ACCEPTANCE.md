# Промт 01 — собрать одну приёмку итогового кода

Ты работаешь в локальном репозитории TG_Info / Customer Dossier. Используй этот промт в Claude, независимо от выбранной в среде версии модели разработки. Не меняй runtime-модель портала.

## Задача

Подготовь одну воспроизводимую приёмку этапов 10–19. Не реализовывай их повторно и не открывай этап 20. Этот проход — чтение кода и документов плюс подготовка консолидированной инструкции. Код приложения, тесты, миграции, зависимости, настройки и статусы готовности не изменять.

Прочитай README этого пакета и действующие инструкции проекта. Сообщённое состояние: main, d33521b; backend 46/613 unit и frontend 14 PASS; миграции 021–023, DB-интеграция, браузер, restore, модель, источники и пилот NOT_RUN. Эти числа — исходное сообщение, не обязанность подгонять тестовый набор.

## 1. Установи исходную точку

Безопасно прочитай локальные Git HEAD/branch/status, историю изменений 10–19, версии Node/npm/PostgreSQL-клиента, если их чтение не запускает сервисы. Не делай fetch/pull/checkout/reset/clean/stash/rebase и не переписывай историю. Не требуй удалить неизвестные ZIP ради чистого status.

Если HEAD отличается от d33521b, установи причину из доступной локальной истории и зафиксируй фактическую редакцию. Не откатывай рабочую папку. Код после согласованной точки требует нового fingerprint; не приписывай ему логи старой редакции.

Проверь package scripts и pre/post-hooks до любых рекомендаций запуска. `npm test` может означать не одноразовый unit; не копируй флаги между backend и frontend без проверки их runner. Ничего из scripts на этом подготовительном шаге не выполняй.

Прочитай существующий `release:fingerprint` до использования. Установи, какие файлы покрыты, в том числе новые тесты и helpers; не должен самопроизвольно меняться от собственных отчётов. Не переписывай эталон для маскировки несовпадения.

## 2. Сопоставь все этапы с доказательствами

Найди актуальные STATE/HANDOFF, RELEASE_READINESS, BACKLOG, LOCAL_RUNBOOK, CONTENT_MANIFEST и отчёты 10,11,12,13,14A,14B,15A,15B,16,17,18,19. Прочитай все соответствующие `docs/development/evidence/NN/USER_RUN.md`; по отсутствующему файлу напиши MISSING, не выдумывай команды.

Особенно не пропусти этапы 10–14B из-за того, что последний краткий отчёт перечислял в таблице только 15A–19. Отсутствие строки в сообщении не означает отсутствия кода.

Разложи исходную матрицу T10…T19 и относящиеся TC-074…TC-078 на существующие тесты/ручные действия. Используй reference/ACCEPTANCE_MATRIX.md этого пакета как индекс рисков, а не как замену исходным критериям. Повторяющийся сценарий запускать один раз на итоговом коде и ссылаться на результат из нескольких этапов.

Для каждого пункта различай:
- заявлено в сообщении;
- подтверждено прочитанным кодом;
- тест написан, но NOT_RUN;
- фактически выполнено с логом и fingerprint;
- не относится к выбранному ограниченному сценарию, с объяснением.

Backend build не считать выполненным только по typecheck, если отдельного лога нет. Frontend component test не заменяет настоящий browser. SQL-проверка не заменяет применение SQL в PostgreSQL.

## 3. Проверь готовность команд к безопасному запуску

Прочитай guard тестовой цели и все пути до первой записи. Включая авторизацию, тестовый helper, migrations --upto, seed, snapshot benchmark, генератор большого набора и restore. Выполнение соединений оставь пользователю.

Составь роли существующих тестовых целей: новая установка, синтетический апгрейд, интеграция, восстановление, браузер/нагрузка. Не обязательно создавать пять БД: допускается подтверждённое последовательное переиспользование выделенной цели, но restore всегда в другую цель. Не придумывай имя существующего контейнера, роль, пароль, версию СУБД или переменную окружения.

Инструкция должна объяснять конфликт между `DATABASE_URL` в окружении и `backend/.env`. Переопределение переменной процесса не изменяет содержимое файла. Не предлагай обходить отказ guard или автоматически редактировать `.env`. Нужна положительно установленная тестовая цель, не название со словом test.

Любой bootstrap тестовой базы/роли/маркера — отдельный пользовательский шаг с проверкой именно вновь создаваемой выделенной цели. Агент его не выполняет.

## 4. Ограниченный security-triage

Прочитай reference/SHARP_TRIAGE.md. По lock-файлу, import/call sites и имеющемуся audit-JSON установи цепочку sharp и входные данные генератора. Нельзя объявлять её безопасной по фразе «dev-only»; нельзя считать весь портал эксплуатируемым по одному слову high.

Если свежего advisory-отчёта нет, подготовь команды пользователю и оставь NOT_VERIFIED. Никаких npm audit fix / install / update. Запуск audit передаёт сведения о зависимостях в registry; отметить это в инструкции. Точный advisory сначала определяется по отчёту, а не по наиболее свежей записи в интернете.

Составь решение для КОНКРЕТНОГО следующего действия: безопасно ли продолжать чтение, офлайн-тесты с доверенной синтетикой, сборку, обработку внешних изображений. Не блокируй всё по недоказанной гипотезе, но не разрешай путь с достижимой непроработанной high-уязвимостью. Исключение риска утверждает владелец, не агент.

## 5. Порядок прогона

A — baseline/fingerprint, инструкции, security и статические результаты.
B — guards; свежая установка; синтетический апгрейд с реального предшествующего номера миграции; полный интеграционный набор; backup/restore и чтение через приложение.
C — браузер и рабочий маршрут аналитика; затем ограниченная нагрузка и EXPLAIN.
D1 — оценка действующей конфигурации модели по 14A/14B.
D2 — проверка названных и разрешённых источников по 16.
E — рассмотрение манифеста и отдельного разрешения на ограниченный пилот.

Безопасные независимые ветки можно выполнить при наличии своих предпосылок. Например, отсутствие разрешённых каналов не запрещает синтетические тесты UI или модели. Но незавершённые обязательные gates нельзя превратить в успешный пилот.

## 6. Выходные документы

Используй уже существующую сводную папку приёмки; если её нет, разрешено создать только документы в `docs/development/evidence/acceptance_10_19/`:

- BASELINE.md: фактическая редакция, релевантный diff, dependency hashes, заявленные и прочитанные доказательства.
- COVERAGE.md: этап/критерий → тест/шаг → область/модель → результат → лог → fingerprint.
- USER_RUN_CONSOLIDATED.md: минимальный общий маршрут со ссылками на действующие USER_RUN и без повторных destructive setup.
- SECURITY_TRIAGE.md: sharp, зависимости, применимость и неизвестное.
- DECISION_DRAFT.md: только текущие ограничения, без повышения RELEASE_READINESS.

Не создавай новый runtime-manifest пилота: существует формат этапа 19. Допускается список отсутствующих полей/оснований, без подстановки источников, лимитов и согласий от себя.

## Формат каждой команды для пользователя

Цель → терминал и рабочая папка → проверка тестовой цели → точная команда из фактического проекта → что она меняет → где журнал → ожидаемый код/содержимое → условие остановки. PowerShell-флаги и проверка exit-code должны соответствовать установленной версии. Для бинарного dump не использовать текстовые перенаправления.

Список ожидаемых результатов не заполнять как фактический. Никаких обещаний выполнить проверки позднее или в фоне.

## Остановка

После документов выведи перечень блокеров безопасности, требующих решения до записи, и один первый безопасный пользовательский шаг. Не запускай Docker/БД/browser/модель/сеть; не делай commit/push; не меняй readiness. Если подготовка обнаружила дефект, передай описание для промта 04, не чини его в этом проходе.
