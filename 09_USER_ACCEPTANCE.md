# Пользовательская приёмка этапа 09

Дата: 16.09.2026. Это последовательность и критерии; актуальные точные команды должен подготовить Claude из вашей рабочей папки после исправлений. Содержание разделов A1–A5 и N1–N8 текущего TESTING_LOCAL.md в предоставленном сообщении не раскрыто, поэтому здесь оно не выдумывается.

## Перед прогоном

Проверять конкретное состояние кода: HEAD и незакоммиченные изменения. Не смешивать успешный старый лог со свежими правками. Сохранить краткую не-секретную информацию о версии Node/npm, PostgreSQL, ОС, CPU/RAM, флагах и составе тестовых данных. Логи не должны содержать пароли, cookies, DSN и тексты реальных закрытых материалов.

Рабочая БД не участвует. Явно выделяются тестовая исходная база и другая restore-цель. Одного `test` в имени недостаточно: должны быть известны и проверены endpoint/база/роль и признаки изоляции. Не останавливать общий PostgreSQL-контейнер, если в нём есть другие пользовательские базы. Для отказов необходим отдельный тестовый экземпляр либо другой безопасный механизм, отражённый в инструкции.

## Последовательность

### A. Исправления и статические проверки

Claude выполняет ограниченный `09_CLOSURE_PROMPT.md`, затем Codex проводит read-only ревью. После исправлений получаем typecheck/backend build при наличии, frontend semantic check/build и полный unit gate. Не принимать 405 успешных тестов вместо полного набора только потому, что оставшийся файл не запустился.

Полный последовательный прогон по файлам допустим, если есть реестр всех файлов, логи и единое состояние кода. Новые тесты не обязаны сохранять прежние числа 29/421 и 18/196. Нельзя снижать число тестов ради совпадения с отчётом.

### B. Интеграционные тесты

Сначала идентификация test-target, затем fresh install и synthetic-legacy upgrade, затем новые тесты 09 и полный интеграционный прогон по актуальной инструкции. Все выполняете вы.

Исходное ожидание из отчёта: 18 файлов / 196 тестов. После hardening оно может увеличиться. Проверяем отсутствие неоговорённых skip, полный состав матрицы, exit code и отсутствие скрытых подключений к рабочей БД/внешним источникам.

У synthetic-legacy результата правильная формулировка: «миграции прошли на построенной базе до 009 с подготовленными legacy-строками». Неправильная: «подтверждена миграция моих исторических данных».

### C. Синтетический пользовательский сценарий

Создать demo только безопасным test-only seed из текущего кода. Найти два одноимённых юрлица; выбрать нужное по реквизиту; открыть роль именно по нужному корпусу; перейти к цитате; увидеть отрицание и решение аналитика; создать обращение и снимок; выгрузить досье. Правка публикации, новое evidence и merge не изменяют старый снимок и не скрывают корректную атрибуцию review в новом досье.

Отдельно проверить доступ после отзыва display/export policy: исторический снимок не является обходом текущего доступа. Не менять настоящие допуски реальных источников ради теста; это синтетический сценарий.

### D. Перезапуск, браузер и отказы

Остановить и заново запустить именно процесс приложения по проверенной инструкции. Открыть существующий снимок и сравнить payload/hash/export с исходным. Пересоздание Express-приложения в одном процессе не заменяет этот шаг.

Пройти браузерный сценарий на обычной ширине и 390 px. Проверить чтение/раскрытие доказательств, явную разницу «данных нет» и «сервис недоступен», вход/выход, отсутствие исполнения опасного текста, печать в PDF через браузер и восстановление после безопасно имитированного отказа тестовой БД. Это не серверный PDF-экспорт.

Отдельно подтвердить отсутствующие в автоматике отказные сценарии из матрицы. Не заполнять диск и не ломать сеть всей машины. Контролируемая инъекция ошибки записи проверяет приложение, но не физический диск.

### E. Backup/restore без изменений между контрольными точками

1. Завершить подготовительные действия и зафиксировать данные. Остановить все писатели: сбор, pipeline, бота, пересчёт, benchmark, ручное создание снимков. Дождаться завершения активных задач либо документировать безопасное состояние очереди.
2. Снять inventory + содержательный manifest + отдельные допустимые параметры окружения. Это точка «до».
3. Создать `pg_dump -Fc` тестовой исходной базы по проверенным командам. Записать успешный exit code и безопасные метаданные дампа; сам dump не отправлять в чат/Git.
4. Подготовить новую изолированную restore-цель. Не удалять существующую базу и не использовать `--create` без разбора его назначения. Restore должен останавливаться при ошибке, а не давать частично пригодную копию за успешную.
5. До запуска меняющих состояние HTTP-действий снять manifest восстановленной базы и сравнить: доменные fingerprints, количества, схема/миграции, sequences, source state, review, snapshot integrity, invariants. Имя restore-базы и время проверки не обязаны совпадать; содержимое доменных строк обязано.
6. С выключенным фоном запустить приложение на восстановленной тестовой цели. Проверить сохранённые досье, ручные решения, историю редакций, старый snapshot и экспорт. Не включать реальные источники или модель.
7. Зафиксировать результат функционального восстановления отдельно от manifest comparison.

Успешное сравнение количеств недостаточно, а успешное сравнение содержимого не заменяет чтение через приложение. Нужны оба вида свидетельств.

### F. Benchmark отдельно от backup-сравнения

Запускать после завершения E либо на третьей выделенной тестовой копии. Он создаёт snapshots, поэтому меняет БД. Учитывать прогрев и прирост данных.

В отчёте: версия кода, машина, объём, размер графа, число повторов, определение прогрева, тип HTTP-харнесса, реально проверенный payload/status, медиана/min/max, число ошибок, изменившийся объём. Отказ авторизации не считается быстрым успешным ответом.

Если измеряется только HTTP с детерминированной моделью, это не скорость реального извлечения. Pipeline fixture измеряется отдельно и помечается как synthetic. Реальная модель остаётся непроверенной на этом этапе.

## Матрица решения

| Gate | Что необходимо | Текущий статус по исходному сообщению |
|---|---|---|
| G01 — состояние кода | HEAD + diff/fingerprint, версии и безопасный target | Требует фиксации для итогового прогона |
| G02 — unit/build | Все объявленные unit-файлы на итоговом коде; typecheck/build | Unit частично BLOCKED_ENV; остальное PASS по отчёту |
| G03 — интеграция | TC-074/076/077 и полный актуальный набор | NOT_RUN |
| G04 — backup/restore | Реальный dump/restore, содержательное сравнение, функциональное чтение | NOT_RUN; метод сравнения требует проверки |
| G05 — UI/restart/failure | Пользовательский сценарий, отдельный процесс, безопасный отказ БД, 390 px/print | NOT_RUN |
| G06 — performance | Честный HTTP baseline и явно выделенный fixture pipeline при наличии | NOT_RUN |
| G07 — эксплуатационные документы | Инструкции соответствуют фактически выполненным действиям, ограничения явны | Написаны по отчёту; требуют подтверждения |

Названия G01–G07 — удобные группы этой проверки, не замена исходным TC-074…TC-078. Каждый original TC должен остаться прослеживаемым.

## Что передать ревьюеру

Один комплект без секретов: итог typecheck/build/unit; полный вывод интеграции и список файлов; manifests и вывод compare; логи успешного dump/restore без содержимого дампа; benchmark JSON; протокол UI/restart/DB failure; актуальные 09_REPORT, RELEASE_READINESS и BACKLOG. Файл логов с неполным концом не считать успешным, пока не известен код выхода.

После исправления дефекта повторяются затронутые сценарии; итоговый регрессионный комплект должен быть привязан к одному конечному состоянию кода. Отчёты разных прогонов не складывать в фиктивный единый PASS.

## Условия завершения

LOCAL_FIXTURE_READY становится PASS после полного выполнения обязательных core-gates, без открытых дефектов целостности, изоляции test-target или обхода доступа. Отсутствие допуска живых источников не мешает этому ограниченному статусу.

LOCAL_MODEL_VALIDATED остаётся NOT_VALIDATED. LIVE_SOURCE_VALIDATED остаётся пустым списком до отдельных разрешённых проверок. Проверка реальной пользовательской миграции — NOT_RUN. PRODUCTION_READY не заявляется.
