# CLAUDE.md — TG_Info

Дополняет корневой `Odintsov/CLAUDE.md`. При конфликте приоритет здесь.

## Что это

Портал деловой разведки по строительному рынку России: «быстро проверить, как дела у Заказчика».
Сырые тексты из Telegram-каналов и сайтов → извлечение локальной LLM → канонические
сущности (компании, объекты, роли, события) → карточка Заказчика и статистика подрядчиков.

## Структура

```
docs/migrations/   нумерованные SQL, применяются раннером (не psql вручную)
backend/           Express + TS, pg.Pool без ORM
frontend/          Vite + React + TS: поиск, карточки компании и объекта, обращения и досье, проверка, снимки, подрядчики, админка
```

**Не запускать старые команды автоматически.** Живой `--probe`, сбор, разбор,
`migrate` без `--dry` и любые изменяющие CLI — только осознанно и против
подтверждённой цели. `--probe` показывает, сколько узлов нашёл каждый селектор
(`wrap = 0` при большой странице = вёрстка `t.me/s/` изменилась), но это живой
запрос: сначала допуск источника, потом проба. Фикстура в `__fixtures__/` написана
по известной разметке, а не скачана с живого Telegram — тесты проверяют логику
разбора, но не актуальность селекторов.

**План развития — пакет `prompts/Customer_Dossier_Prompts/`**, состояние —
`docs/development/STATE.md` и `HANDOFF.md`. Этапы строго по одному.

## Рынок

Россия. Изначально проект строился под Казахстан — отсюда казахские буквы
в нормализаторе и формы ТОО/ЖШС в списке ОПФ: они оставлены намеренно, чтобы
пересланный пост про компанию из РК не ломал разбор. Идентификатор компании —
ИНН/ОГРН с проверкой контрольной суммы (`tax_id`), суммы в рублях (`amount_rub`).
Географического фильтра в промпте больше нет: отсекается только то, что не
относится к стройке и недвижимости.

## Ключевые решения (не менять без причины)

- **Telegram читаем без MTProto API**: `https://t.me/s/<канал>` — обычный GET, без ключей.
  Закрытые каналы — только через форвард-бота (BotFather, бот в личке, права админа не нужны;
  long polling, а не webhook — публичный HTTPS-адрес локальной машине не нужен).
  Никаких api_id/api_hash: они пользователю недоступны.
- **Курсоры Telegram (этап 05B, ADR-007).** Web-preview: `cursor.tg` = {lastPostId, gap, historyBefore,
  lastRecheckAt}; посты страницы и курсор — одна транзакция, допуск перепроверяется в ней. Максимум первой
  страницы не означает, что всё до прошлой отметки сохранено: разрыв записывается и догружается не более
  `maxPagesPerRun` страниц. Первый запуск историю не собирает. Пропущенный номер поста — не удаление.
  Канал в `data-post` не совпал с ключом — `identity_changed`, без записи. Бот: `update_id` — транспортный
  offset, журнал `bot_processed_updates` (одна транзакция на обновление, offset из журнала); `edited_message` —
  новая редакция; `forward_origin` хранится в `transport_meta` отдельно от переславшего. Возможности
  транспортов — `ingest/telegram/capabilities.ts`, не обещание истории. Курсор и журнал не обнулять.
- **Имя канала — со страницы канала (этап 22).** `parseChannelTitle` (`ingest/telegramWeb.ts`): og:title →
  шапка канала → `<title>` без « – Telegram»; username и слово «Telegram» именем не считаются. Обходчик пишет
  имя в `sources.title` только там, где его ещё нет (`title = key`), и только после проверки идентичности
  канала: название, заданное оператором, не перетирается. Пока имени нет, экран показывает «@ключ»
  (`sourceLabel` в `labels.ts`), а не голый технический ключ.
- **Курсор лент — только `utils/keysetCursor.ts`.** pg отдаёт `timestamptz` объектом `Date`, и `${date}|${id}`
  давал `Date.toString()`, который PostgreSQL не разбирает: «Показать ещё» падало на второй странице.
  Неразборчивый курсор — как отсутствующий (лента сначала), а не 500.
- **`TG_BOT_ALLOWED_USER_IDS` пустой = не принимать никого.** Не наоборот. Бот, открытый
  всем, — это прямой канал вливания произвольного текста в LLM и в карточки компаний.
- **Дедуп срезает подпись канала только с начала строки.** Срезать «источник»/«подписывайтесь»
  из середины строки нельзя: тем же движением съедается остаток настоящей новости.
  Размен осознанный: пропущенный дубль стоит одного вызова LLM, а склейка разных
  новостей теряет новость.
- **Роль — свойство связи, а не компании.** Одна компания бывает заказчиком на одном
  объекте и подрядчиком на другом. Роль живёт в `project_participants`.
- **Ничего не попадает в канон без дословной цитаты**, проверенной вхождением в `body`
  (`pipeline/verify.ts`). Имя сущности обязано встречаться внутри своей цитаты.
- **Слияние компаний асимметрично**: слить легко, разлить почти невозможно. Поэтому
  в серой зоне score (0.75–0.92) создаём новую компанию и кладём пару в `merge_queue`,
  а не сливаем. Автослияние только от 0.92 и никогда при конфликте ИНН/ОГРН.
- **Идентичность (этап 04, ADR-005).** Юрлицо, бренд и группа — `companies.entity_type`
  (одна каноническая таблица); реквизиты — реестр `entity_identifiers` по типу (ИНН ≠ ОГРН ≠
  ОГРНИП), `companies.tax_id` — совместимая проекция. Точное имя никогда не обходит
  реквизиты: упоминание с ИНН не прикрепляется к одноимённой компании без него, упоминание
  без формы и реквизитов — к юрлицу с реквизитами (бренд не получает ИНН дочернего ООО).
  Для упоминаний без реквизитов — одна стабильная provisional-сущность на имя; несколько
  равноправных кандидатов — `resolution_ambiguities`, не выбор первого и не новый дубль.
  Объекты: комплекс → очередь → корпус (`parent_project_id`), неизвестный город не равен
  совпавшему, общий участник — не довод идентичности, география — только из текста.
- **Слияние — только через `resolve/entityMerge.ts`** (ADR-005): предпросмотр, ожидаемые
  версии обеих сущностей, ключ идемпотентности, блокировки в стабильном порядке, коллизии
  до записи, журнал `entity_merges`/`entity_merge_moves`, tombstone вместо удаления.
  Утверждения неизменяемы: основания копируются на утверждение живой сущности, решения
  аналитика остаются в истории. Отмена — только при неизменившихся зависимостях, иначе
  план без автоприменения. Применение — флаг `MERGE_APPLY_ENABLED` (по умолчанию false).
  Новая таблица, ссылающаяся на компанию или объект, обязана попасть в перенос и в
  `dependencyState`, иначе слияние оставит висячие ссылки.
- **`resolve/normalize.ts` — единственный источник правды по нормализации.**
  Вызывается и на записи, и на поиске. Разойдутся — резолвер перестанет находить
  существующие компании и начнёт плодить дубли. Правки — только вместе с тестами.
  **После правки нормализатора старые ключи расходятся с новыми.** Ключи поиска
  вычисляются один раз при вставке. Так «ГК Консоль» (записана до того, как «ГК»
  попало в список форм) и «Консоль» жили двумя карточками. Смотреть расхождение —
  `--renormalize --dry`; запись ключей в рабочую базу — массовая правка канона,
  — версионный backfill `npm run backfill:identity -- --renormalize` (dry-run по умолчанию,
  запись только `--apply --confirm-copy` на копии). Правка нормализатора = bump
  `NORMALIZER_VERSION`. Автоматически не запускается.
- **Переразбор — только новым конвейером (этап 03B, ADR-004).** Старый `apply` с
  `clearDocumentContribution` удалял вклад документа вместе с тем, что подтвердил
  другой источник; он и слияние по-прежнему выключены в коде (`pipeline/guard.ts`),
  не возвращать. Новый путь: неизменяемый запуск с отпечатком параметров → чанки
  с диапазонами и append-only ответами → набор кандидатов → публикация одной
  транзакцией с ожидаемой версией. Снимается только вклад этой же публикации
  (evidence → `superseded`), решения аналитика и чужие доказательства остаются.
  Completed — только при всех чанках ok и полном покрытии текста. **Автопубликация включена
  по умолчанию (`REPROCESS_AUTO_PUBLISH=true`, решение владельца 21.09.2026):** набор уходит
  в карточки сразу после полного разбора, ручной предпросмотр — запасной путь. Проверки этим
  не ослаблены: `partial`/`failed`/неполное покрытие не публикуются ни при каком флаге
  (`publish.ts::runComplete`), `allowStale` исполнитель не ставит, требование `previewToken`
  относится к HTTP-пути и осталось. Отказ публикации — исход набора, а не падение запуска
  (`worker.ts`, журнал `publication_history` виден в админке). Массовый переразбор рабочей
  базы — не одной командой: `--reextract` требует `--limit` (≤ 200).
  Карточки читают проекции `card_participations_v` / `card_events_v`; сигналы — снимок этапа 07.
- **Поток не останавливается молча (этап 22).** Модель не отвечает — проход конвейера не делается
  вовсе (`probeModel` в `reprocess/worker.ts`, `checkLlmConnection` перед постановкой): иначе постановка
  создаёт запуски, они падают, и редакция выпадает из автопотока навсегда — автопостановка берёт только
  редакции без единого запуска. Упавший запуск возвращается в поток сам (`retryFailedRuns` → `retryRun`,
  новый запуск со ссылкой на прежний) с паузой `REPROCESS_RETRY_BACKOFF_MIN` и потолком
  `REPROCESS_RETRY_MAX` неудач на редакцию; `cancelled` не повторяется — это отзыв допуска, решение
  оператора. Экран `/admin` считает состояние последних редакций (`no_ai_permission`, `in_queue`,
  `failed_retrying`, `failed_exhausted`, `published`, …), а не `raw_documents.status`: ту колонку новый
  конвейер не меняет, и счётчик «в очереди» не менялся никогда.
- **Обработка идёт без оператора (21.09.2026, решение владельца).** Портал не публикует — он показывает
  собранное. Из интерфейса убраны постановка разбора, повтор, отмена и публикация набора: `/admin/process`
  и карточка запуска — только чтение («почему текст не попал в карточки»), панель набора —
  `CandidateSetPanel`. Серверные пути (`POST /api/reprocess/...`, `publish.ts`, CLI) не тронуты: это
  восстановление после сбоя, а не рабочий сценарий. Слово «публикация» как действие из экранов убрано;
  «публикация» осталось только в смысле «пост источника». Возвращать кнопки — отдельная задача, а не правка текста.
- **Тема публикации — машинная подпись, не заголовок (этап 21, headline@1).** `llm/headline/*` +
  `headline/service.ts`, миграция 027 (`revision_headlines`, append-only, одна строка на редакцию+модель+промпт).
  Отдельный короткий вызов модели после разбора, а не поле в extract@3: иначе смена схемы потребовала бы
  переразбора всей базы. Идёт тем же заданием, что и разбор (`HEADLINE_ENABLED`, но без `PIPELINE_ENABLED`
  не запускается): два параллельных запроса делят VRAM. Допуск — тот же `ai_processing`, проверяется до вызова
  и после ответа. Тема не доказательство, в цитаты не идёт, заголовок источника не подменяет и на экране всегда
  подписана как составленная моделью. Правка промпта — bump `HEADLINE_PROMPT_VERSION`, старые строки не удаляем.
- **«Что взято из текста» — API, а не экран (этап 21; экран снят 23.09.2026 решением владельца).**
  `GET /api/items/:id/extraction` (`reprocess/itemOutcome.ts`, только чтение): состояние словами
  (`ITEM_STATE_LABELS`) различает «не о стройке», «связей не найдено», «нет ИИ-допуска», «не разбиралось»,
  «разбор не удался». Со страницы публикации блок и таблица редакций убраны: оператор приходит прочитать
  новость, а не разбор. Эндпоинты, CLI (`--doc`) и данные целы; вернуть экран — отдельная задача.
- **Конфигурация запуска неизменна (этап 11, ADR-004 дополнение).** `execution-identity@1` в `reprocess/provider.ts`:
  эффективные сообщения (с `/no_think`), шаблон, схема, параметры, политика повторов, `CANDIDATE_BUILD_VERSION`, нарезка;
  не сообщённое сервером — `unknown`. Запуск модели A моделью B не выполняется (`blocked`, вызовов 0); смена конфигурации —
  новый запуск с `previous_run_id`. Перед каждым вызовом и повтором — своя аренда и действующий ИИ-допуск, иначе `cancelled`
  без набора. Правка проверки/сборки кандидатов = bump `CANDIDATE_BUILD_VERSION`. Миграция 021.
- **Смысл связей и событий (этап 06, ADR-008).** Схема extract@3 (`llm/semantic/*`,
  `EXTRACT_SCHEMA_VERSION`, откат — extract@2): связь участия, прямой договор и корпоративная связь —
  разные предикаты, у каждой своя цитата с обеими сторонами в одном предложении; совместное участие и
  упоминание — представления, не договор; транзитивный договор не выводится. Полярность, модальность и
  статус проверки — три поля. Ответ модели, противоречащий цитате (положительное при отрицании, «факт»
  при плане или слухе, договор без признака договора), остаётся кандидатом «на проверку» и не
  публикуется (`reprocess/semantic/verify.ts`). Дата — с точностью, подтверждённой цитатой; сумма — во
  фрагменте со стороной и денежной единицей, без пересчёта валют и НДС. Отрицание добавляет `contradicts`
  к положительному утверждению, решение аналитика остаётся (`needs_revalidation`). Карточка берёт роль
  только из положительного reported_fact, событие — из reported_fact/claim. Состояние объекта — по
  действительной дате (`project_current_state_v`), не по последней записанной статье; стадии дела —
  по номеру (`legal_case_events_v`); очередь проверки — `review_queue_v`. Словесные признаки — эвристика:
  ошибка в сторону «на проверку», а не ложной связи.
- **Рабочее досье (этап 08A, ADR-010).** Обращение (`dossier_cases`) — запись оператора с provenance
  `operator_recorded_claim`: заявленная роль, заказчик и условия не становятся утверждениями и доказательствами.
  Юрлицо — выбранное из кандидатов или явно «не установлено» с названием; одноимённые не подставляются.
  Изменение — с ожидаемой версией, каждая версия в неизменяемой истории, удаление запрещено. Досье обращения,
  объекта и резюме компании строятся шаблонами (`dossier/*`) при открытии, без модели и сети; каждая фраза несёт
  атрибуцию («в публикации сообщается» / «проверено аналитиком» / «со слов обратившегося» / «не установлено в
  выборке») и id утверждений и доказательств. Вопросы контрагенту — только по реальным пробелам. Причина решения
  аналитика обязательна для отклонения, спора и возврата. Новые экраны — за `VITE_DOSSIER_UI` (откат — `false`).
- **Применимость к обращению (этап 12, ADR-010 дополнение).** `dossier/scope.ts` (`scope-match@1`): объект, корпус, тема
  работ, роль, дата обращения → match/compatible/unknown/conflict. Null в утверждении — не «весь объект» и не подтверждение;
  роль и цепочка documented — только без конфликтов и с известным корпусом при выбранном; остальное — `context` и
  `scope_unknown`. Отрицание по объекту без корпуса — противоречие с пометкой; отклонённое аналитиком — только история.
  Досье, схема и новые снимки — одно правило; старые снимки не пересобираются.
- **Схема связей и снимки (этап 08B, ADR-011).** Схема — ограниченный обход опубликованных утверждений (`graph/*`:
  глубина ≤ 3, узлов ≤ 150, циклы не повторяются); путь А→Б→В не даёт ребра А→В, совместное упоминание скрыто по умолчанию,
  тип ребра — штрих и подпись, не цвет надёжности. Снимок (`dossier_snapshots`, миграция 020) — неизменяемая копия досье,
  цитат с редакциями, подписей, решений и схемы; hash `sha256-canonical-json@1` — целостность, не подпись и не истина.
  Срез знаний — только «сейчас» (прошлое → 422), фильтр дат относится к событиям и ролям. Текущий допуск источника
  применяется при выдаче (payload не меняется); вымарывание — единственный путь правки payload, с журналом hash.
  Выгрузки MD/JSON/HTML строятся из снимка, HTML без скриптов и внешних ресурсов («Версия для печати», не PDF).
  Новая таблица снимка не переносится слиянием — снимок намеренно заморожен. Откат — `GRAPH_EXPORT_ENABLED=false`.
- **Снимок согласован и честен по полноте (этап 13, ADR-011 дополнение).** Ключ снимка сверяется с запросом
  (`snapshot/requestIdentity.ts`, `request_hash`, миграция 022): другое обращение/период с тем же ключом — 409. Все чтения
  построения — через client транзакции REPEATABLE READ (в т. ч. `refreshState(client)`); новый чтитель для снимка обязан брать
  executor параметром. Лимиты выборок не снимаются, но отдают `coverage@1` (`loaded/total/truncated`); усечённая выборка не
  говорит «сведений нет». Сигналы — от редакции-основания доказательства, новая неразобранная правка — `pendingRevision`.
- **Локальная эксплуатация (этап 09).** Портал — одна машина, один оператор, loopback; промышленной
  готовности не заявляем. **Старт API запускает сбор допущенных источников, разбор и публикацию**
  (`jobs.ts`); рубильники — те же флаги, `=false` выключает. Живого запроса к источнику без
  подтверждённого допуска не будет при любом флаге (`ingest/policy.ts`), новые источники заводятся
  `paused`, тестовая цель гасит флаги принудительно (`testTargetBootstrap.ts`). Проверку
  восстановления запускать с выключенными фоновыми флагами — иначе `release:manifest --compare`
  даст ложный `BACKGROUND_ENABLED`. Резервная копия — дамп всей базы целиком: редакции, доказательства, решения аналитика,
  обращения и снимки связаны между собой и по отдельности не восстанавливаются. Восстановление проверяется
  только в отдельной цели: писатели остановлены → baseline → дамп → restore с `--exit-on-error --single-transaction`
  → `release:check --compare` (количества) **и** `release:manifest --compare` (содержимое строк, схема, миграции,
  последовательности, пересчитанные hash снимков; `docs/development/CONTENT_MANIFEST.md`) → чтение через приложение.
  Совпадение количеств содержимое не доказывает. Новая таблица в миграции обязана попасть в `release/manifestSpec.ts`
  (иначе `UNCLASSIFIED_TABLE`) и в `COUNTED_TABLES`. Автоматической очистки нет: снимки и решения не удаляются,
  безопасный ручной порядок — в `docs/development/LOCAL_RUNBOOK.md`. Времена работы — измеренные
  (`npm run release:bench`: выборка засчитывается только при ожидаемом коде и содержимом), а не обещанные.
- **Запись в тестовую цель — только через общий preflight** (`db/testTargetBootstrap.ts`, закрытие приёмки 09):
  интеграционные тесты, сиды, `release:bench`, `migrate --upto`. Адрес — только `TEST_DATABASE_URL`, без запасного
  `DATABASE_URL`; имя `tg_info_test[_суффикс]`, loopback, роль; не совпадает с `DATABASE_URL` оболочки и `backend/.env`;
  после подключения — база, `current_user` и маркер `tg_info:test-target`, всё до первой записи. Слово `test` в имени
  ничего не разрешает. Новая записывающая команда обязана вызывать preflight до импорта пула.
- **Пилот — только по манифесту (этап 19).** `pilot-manifest@1` + `npm run pilot:check` (`release/pilotManifest.ts`, только чтение):
  без утверждённого манифеста, названных источников с действующим допуском, совпадающей базы и выключенного фона — BLOCKED.
  Запреты (автопубликация, применение слияний, миграция рабочей базы, публичный доступ, внешняя передача) и ручная проверка —
  литералы схемы. Агент пилот не запускает и источники не подбирает; порядок, остановки, копии и хранение — `docs/development/pilot/`.
- **Краткое досье для переговоров (этап 17, ADR-010 дополнение).** `brief` (`negotiation-brief@1`, `dossier/brief.ts`) строится
  из досье `dossier-template@3` без модели: статус словами, scope, свежесть, происхождение (перепечатки — одно подтверждение, разные
  тексты — независимость не доказана), новая редакция, ограничения данных в самом резюме. Общий фон — отдельно. Запрещены оценки
  надёжности, «ничего плохого не найдено», долг из суммы иска, «проверенный договор» (`brief.test.ts`). `LOCAL_MODEL_VALIDATED` в
  `brief.ts` меняется только решением по оценке модели.
- **Подключение источника (этап 16, ADR-006 дополнение).** Профиль = настройки адаптера + `meta` (`source-profile@1`,
  `ingest/profileMeta.ts`): всё неизвестное — unknown, основания — ссылки; профиль допуск не выдаёт. `allowedPathPrefixes`
  только сужает обход. Состояние для оператора — `source-health@1` (`ingest/sourceHealth.ts`): never_run / healthy / degraded /
  policy_blocked / temporary_error / partial_history, общая полнота истории всегда неизвестна. Шаблоны, контракт и runbook —
  `docs/development/sources/`; `VALIDATED_SOURCES.md` заполняется только по прогону пользователя.
- **Рабочее место запусков (этап 15B, ADR-004 дополнение).** `/runs` и `reprocess/workbench.ts` — поверх тех же запусков;
  действия только по одному id (enqueue редакции, retry — повтор команды не плодит запусков, cancel — fencing +1, ушедший
  запрос не отзывается). Публикация через API — только с `previewToken` предпросмотра (`publish-preview@1`, иначе 409
  `preview_stale`), неполный запуск — 422 при любом флаге. Неизвестные токены/время — `null`, не досчитывать. Массовой
  кнопки переразбора и включения исполнителя из UI нет.
- **Неоднозначное упоминание ≠ слияние (этап 15A, ADR-005 дополнение).** Решение по упоминанию (`ambiguity_decisions`,
  миграция 023) — одна (вид, ключ, редакция): причина, `expectedVersion`, ключ идемпотентности, append-only; выбор против
  реквизита или формы из текста — 422, исключения нет. Резолвер применяет его только к той же редакции (`analyst_mapping`,
  без алиаса), канон меняется лишь новым запуском разбора. Выбор юрлица не подтверждает участие/договор/долг. Слияние
  применяется только с `previewToken` предпросмотра (`merge-preview@1`, иначе 409 `merge_preview_stale`); новая таблица со
  ссылкой на сущность — и в `dependencyState`.
- **Решение аналитика при слиянии не переносится, но видно.** Досье читает линию слияния
  (`dossier/facts.ts::loadPriorDecisions`: `evidence.copied_from_evidence_id` + неотменённый `merge_id`) и показывает
  решение по исходному утверждению в `priorDecisions` с пометкой «нужен пересмотр»; статус и атрибуция перенесённого
  утверждения не меняются. Массовый перенос решений UPDATE-ом не делать.
- **Роль `not_participant` — не редкость, а частый случай.** Без неё модель обязана
  выбрать строительную роль для любой упомянутой компании: аналитики из пресс-релизов
  становились «проектировщиками» (15 при 1 генподрядчике). Если в `--audit`
  проектировщиков больше, чем подрядчиков, — это сигнал именно этой ошибки.
- **`prompt_version` / `model` / `schema_version` в каждой строке `extractions`.**
  Переизвлечение = bump `PROMPT_VERSION`, старые строки не удаляем.
- **`published_at` (дата поста) ≠ `occurred_on` (дата события).** Не смешивать.
- **Пайплайн умеет добавлять факты, но не отзывать их.** Резолвер переиспользует
  существующую сущность и не затирает поля, о которых новый документ промолчал —
  и это правильно: молчание одного поста не опровергает сведения из другого.
  Цена — значение, записанное сломанной версией кода, живёт вечно. Для таких
  случаев есть `--recheck`: снимает города и адреса, которые не подтверждаются
  ни одним документом. Добавляя новое проверяемое поле, добавьте его и туда.
- **Объяснимые сигналы вместо светофора (этап 07, ADR-009; правила `signals@2`).** Итоговой оценки, шкалы и сортировки
  «по риску» нет. Снимок `company_signal_snapshots` считается правилами `signals@1` (`signals/rules.ts`,
  чистая функция) на явный срез: `npm run metrics:refresh [-- --cutoff]`, по расписанию — только
  `METRICS_AUTO_REFRESH=true`. Ошибка пересчёта оставляет прежний снимок и помечает его устаревшим.
  У каждого числа — правило, окно, знаменатель и исходные id; нулевой знаменатель — `insufficient_data`.
  Событие без даты не входит в окно событий; перепечатки — публикации, а не независимые подтверждения
  (семья текста, происхождение established/named/unknown); суд — роль компании в деле и стадия;
  событие объекта — контекст участия, не вина; суммы не складываются. Отклонённое и спорное видно, но не
  reviewed. `company_risk` (007) не удалён и читается только deprecated-эндпоинтом `/legacy-risk`.
  Новые правила — новая версия `SIGNAL_RULES_VERSION`, не правка чисел молча. `signals@2` (21.09.2026) добавил
  договоры, корпоративные связи, контрагентов, пакеты работ, события по видам, число дел и края выборки по датам;
  прежние правила не менялись. Старый снимок новых чисел не содержит — карточка говорит это словами и ничего
  не досчитывает; числа появляются после `npm run metrics:refresh`.
- **Доступ: один локальный оператор, без входа.** Вход по токену снят на время
  разработки (`api/guards.ts` — всё, что осталось): API слушает только loopback и
  отклоняет чужой Host (DNS rebinding) и чужой Origin. CORS авторизацией не является.
  Портал не выставляется наружу; вернуть вход — отдельная задача, а не правка флага.
- **Допуск источника — отдельно для сбора и для ИИ-обработки** (`access_status`,
  `ai_processing_status`). `active` означает только «опрашивать по расписанию».
  Один gate (`ingest/policy.ts`) на всех входах: шедулер, CLI, бот, ручная вставка,
  очередь модели, теневой прогон. Допуск ставит оператор с основанием; агент
  согласований не заполняет.
- **Сетевые запросы к источникам — только через `net/safeFetch.ts`**: allowlist хоста
  источника, запрет внутренних адресов с проверкой в момент соединения, повторная
  проверка каждого редиректа, лимиты времени и размера. Локальная модель — отдельный
  доверенный адрес, исключений для loopback в политике источников нет.
- **Сайты — по проверенному профилю (этап 05A, ADR-006).** RSS предпочтителен (лента редко
  меняет формат и опубликована для машин), HTML-список с пагинацией — только со своим
  профилем (`ingest/sites/profile.ts`: строгая схема, без кода и неизвестных ключей).
  Полнота по происхождению: content:encoded полон только по контракту профиля, статья — по
  совпавшему `bodySelector`, сбой статьи — честный анонс, известная полная версия анонсом не
  затирается. Записи страницы и курсор — одной транзакцией. 304/429/403/политика/oversize и
  смена вёрстки (`parser_degraded`) — разные исходы, не «новостей нет». Сид-сайты — без допуска
  и профиля; проба (`--probe-site`) ничего не пишет. Тесты — внедрённый транспорт `safeFetch`.
- **Реестр — снимок записи, а не новость (этап 20A, ADR-012).** `mode: registry_api` в профиле
  (`ingest/registry/*`), `sources.kind` остаётся `website` — допуск, здоровье, журнал и кнопка «Проба»
  работают без правок. Адреса эндпоинтов и карта полей живут в профиле, а не в коде: после пробы
  правится JSON. Текст редакции строит `registry-render@1` и он детерминирован — ни времени сбора, ни
  названия источника в тексте нет, иначе каждый повторный сбор выглядел бы как «данные изменились».
  Связь застройщика и группы компаний — самодостаточной строкой с обеими сторонами и реквизитом:
  цитата должна проходить проверку. Снимок — одна строка `registry_records` на редакцию; повтор без
  изменений редакции не создаёт. Модель к реестру не подпускаем: ИИ-допуск не выдаётся, разбор
  детерминированный. Что изменчиво (цена, распроданность, сроки, стадия банкротства) — остаётся
  снимком на дату и в канон не пишется: отозвать утверждение конвейер не умеет.
- **Канон из реестра — только неизменчивое (этап 20B, ADR-012).** `registry/publish.ts`: юрлицо
  застройщика с реквизитом, объект, роль `developer` и связь с группой компаний — и больше ничего.
  Происхождение `registry` (не `manual` и не `extraction`) в `assertions`, `evidence` и
  `entity_identifiers`: атрибуция на экране строится по нему. Роль `developer` добавлена в CHECK,
  схема extract@3 и `PROMPT_VERSION` не тронуты — модель выбирает из прежних восьми ролей.
  Цитата — целая строка рендера, найденная в редакции однозначно; не нашлась — утверждения нет,
  причина в `source_runs.error`. Публикация — отдельной транзакцией после записи редакции: отказ
  публикации не уносит собранное. Рубильник — `REGISTRY_PUBLISH_ENABLED`. Разница снимков считается
  на чтении (`registry/changes.ts`), таблицы изменений нет. На экране — дата сведений и атрибуция
  «проектная декларация застройщика, а не проверенный факт»; слова «проверено» в панели нет.
- **Реестр собирает только названное оператором (этап 20C).** Обхода каталога нет и настроить его
  нельзя — он удалён из схемы профиля, а не выключен флагом. Записи берутся из `objectIds`/
  `developerIds` или приходят импортом файла (`--registry-import`, `ingest/registry/importFile.ts`):
  источник отвечает браузеру и не отвечает программе (наш.дом.рф — 403), поэтому оператор сохраняет
  ответ сам. Импорт — тот же профиль, рендер, снимок и канон, что и сбор; допуск на сбор обязателен
  и для него. Отдельного списка наблюдения нет: отслеживается то, что собрано (`--registry-objects`).
  Не совпала карта полей — и проба, и импорт печатают `availablePaths` (имена ключей, без значений).
- **Удаление источника запрещено, если по нему есть документы.**
  Каждое утверждение в карточке прослеживается до источника; удалить источник,
  оставив документы, значит разорвать эту цепочку. Удаление вместе с документами
  тоже выключено: каскад уносит упоминания и события, а роли остаются без
  доказательств. Нужна пауза, а не удаление.
- **Публикация ≠ текст.** Личность публикации — `(source_id, item_key)` в `source_items`
  (external_id → канонический URL → хэш текста). Правка поста — новая неизменяемая редакция
  в `document_revisions` (UPDATE/DELETE запрещены триггером), повтор — только наблюдение.
  Один текст в трёх каналах — три публикации. `raw_documents.body` не переписывается никогда:
  legacy-документ создаётся только для первой редакции, к нему привязаны цитаты. Полнота
  (`full/excerpt/caption_only/failed/unknown`) — по происхождению текста, не по длине. См. ADR-002.
- **Утверждение ≠ факт, решение аналитика ≠ вывод модели.** `assertions` (смысл неизменяем,
  новый смысл — новое утверждение), `evidence` (редакция + span в code points, проверяется базой;
  supports/contradicts/mentions; отзыв — статусом), `review_decisions` (append-only, версия и хэш набора
  доказательств на момент решения). `text_grounded` — «так написано», не «правда». Изменился набор
  доказательств — `needs_revalidation`, решение не удаляется. Решение пишется с `expectedVersion`
  и `idempotencyKey`. Legacy-статусы без обоснования — `legacy_unknown` + `provenance_gap`. См. ADR-003.
- **Цитата подтверждает, что написано в источнике, а не истинность.** ИНН, сумма,
  город и адрес принимаются только из собственной подтверждённой цитаты сущности;
  стороны события обязаны быть названы в его цитате. Неполный разбор (хвост текста
  вне чанков, упавший чанк, повтор на укороченном тексте) не применяется как полный.

## LM Studio

OpenAI-совместимый `/v1`, адрес в `LMSTUDIO_BASE_URL`. Модель — `Qwen3-8B` Q4_K_M
(ctx 8192, Flash Attention, KV-cache Q8) под 8 ГБ VRAM.
**`/no_think` в system-промпте обязателен** — иначе Qwen3 сожжёт `max_tokens`
на рассуждение и вернёт пустой `content`.
`response_format: json_schema` со `strict: true` требует: все свойства в `required`,
`additionalProperties: false` в каждом объекте, nullable как `["string","null"]`.

Переезд на RTX 6000 — только смена `LMSTUDIO_BASE_URL` и `LMSTUDIO_MODEL`, код не трогаем.

Размер чанка — `EXTRACT_CHUNK_SIZE` / `EXTRACT_MAX_CHUNKS` (по умолчанию 3500/6,
подобрано на живой нагрузке: 6000/4 давали таймауты). Подбирать под модель
и видеокарту через env, не правкой кода.

**Контекст в LM Studio не раздувать.** 16K на 8B не помещается в 8 ГБ вместе
с весами — модель уезжает в RAM и таймаутит. При чанке 3500 хватает 8192.

**Модель — Qwen3-8B, не 4B. Решено на данных (legacy extract@2, до этапа 14A), не менять без повторной оценки.**
На «Строительной газете» (промпт p2, 39 общих документов) согласие моделей по
релевантности — 36 %. 4B быстрее в 9 раз (4.6 с против 40.9 с), но признаёт
релевантными лишь 21 % отраслевых статей против 85 % у 8B. В 25 расхождениях
из 39 права 8B: 4B отбрасывала статьи про КРТ, новостройки и инфраструктуру,
отвечая пустышкой за секунду. Портал при этом не ломается и не ругается — он
молча теряет факты. Соблазн «ускорить поток на 4B» стоит проверить заново,
а не принимать на веру.

**Выбор модели — измерением, а не на глаз.** `--shadow`/`--compare` — **legacy-путь extract@2**
(`pipeline/compare.ts`, `llm/client.ts`): он не измеряет текущий конвейер extract@3 и после этапа 14A
не используется для выбора конфигурации. Теневой прогон пишет только в `extractions`: канон не трогается.
Смешать в карточках результаты двух моделей нельзя — откатить такое нечем.

## Ингест: этика и осторожность

Читаем только публичные страницы. Публичность и локальность модели не заменяют
основания для сбора и ИИ-обработки. Троттлинг: 1 запрос / 4 с на канал, потолок
~10 req/min, backoff на 429. Источники в сидах и новые источники заводятся как
`paused` с неподтверждённым допуском — включать вручную после решения оператора.

Экраны: главная (компании / публикации), карточка компании, объект, связи, очередь проверки, публикация,
запуски, админка. **Главная — переключатель «Компании / Публикации» и одна строка поиска (этап 22):** в
«Компаниях» поиск по названию (`/api/companies?q=`) заменяет каталог, в «Публикациях» — подстрокой по тексту,
теме и названию канала (`/api/feed?q=`, ILIKE с экранированием `%`/`_`, индекса по тексту нет — при росте
базы нужен `gin_trgm_ops`). Режим и запрос живут в адресе (`?view=publications&q=`), чтобы «Назад» из
карточки возвращал туда же. В строке каталога под названием ничего нет — город своей колонкой.
**Экран «Подрядчики» снят (этап 22):** он показывал тот же `/api/contractors` с теми же
фильтрами, что каталог на главной, — два пункта меню вели к одному списку; `/contractors` ведёт на главную.
Каталог на главной — пять колонок: остальные числа живут в карточке, где у каждого есть правило и знаменатель.
Строка каталога и строка ленты «Последнее» кликаются
целиком: ссылка накрывает строку псевдоэлементом
(`.row-link` / `.row-link-target` в `src/index.css`), соседние цели поднимаются `row-link-above`. `onClick`
на `<tr>` не вешаем — ссылка должна оставаться ссылкой (средний клик, Ctrl+клик, фокус с клавиатуры).
Показатели компании — во всю ширину над колонками: в узкой колонке плитки рвали подписи. Фильтры схемы
связей свёрнуты там, где схема — боковая панель (`defaultOpen` раскрывает их на экране «Связи»); пояснения
к схеме печатаются один раз — `graph.notes` внизу панели дублировались.
**Карточка компании — три вкладки (этап 22).** «Обзор» — сводка (`CompanyBrief`, ни одного нового числа)
и контрагенты (`CompanyPartners`) рядом. «Публикации» — `PublicationBrowser`: список слева, пост справа в
виде Telegram (`TelegramPost`), карточка списка — одна кнопка целиком, дата крупнее всего; на телефоне пост
открывается вместо списка, «← К списку» возвращает место и фокус. «Подробно» — сигналы, резюме досье,
объекты, события, упоминания старого разбора, схема связей. Ни одно число не изменилось. Лента компании читает `/api/companies/:id/publications` (публикации +
опубликованные утверждения), а не `mentions`: **в `mentions` пишет только legacy `pipeline/apply.ts`,
заблокированный `pipeline/guard.ts`, поэтому на данных нового конвейера прежний блок «Упоминания» был пуст
всегда.** Контрагенты (`/api/companies/:id/partners`) различают договор, корпоративную связь и совместное
участие на объекте и не сводят их в одно «связана с»: две фирмы на одном объекте могут не иметь отношений.

**Страница публикации — только сам пост (этап 22, решение владельца 23.09.2026).** `DocumentPage` рисует
тот же `TelegramPost`, что и списки; одна новость в нескольких каналах — переключатель источника. Разбора
(«что портал взял из текста») и редакций на экране нет — они в API. Возврат — `BackBar` в `Layout`: на
каждой странице, кроме главной; без истории (прямая ссылка) ведёт на главную, а не выбрасывает из портала.

**Обращения, досье обращения и снимки сняты с портала (2026-09-21, решение владельца):** экраны удалены,
маршруты `/cases/*` и `/snapshots/*` ведут на главную, бэкенд-модули `dossier/*`, `snapshot/*` и таблицы
не тронуты — данные целы, дампы сравнимы. Флага `VITE_DOSSIER_UI` больше нет.

**Дизайн-система (2026-09-21).** Отступы, размеры шрифта, высоты контролов, ширины и слои — шкалами
в `src/index.css` (`--sp-*`, `--fs-*`, `--ctl-*`, `--gutter`, `--prose`, `--z-*`); значение вне шкалы —
только с комментарием «почему». Кнопки, переключатели, ярлыки, карточки и таблицы — примитивы
`src/components/ui/` (`Button`, `Segmented`, `Badge`, `Section`, `EmptyState`, `TableScroll`), свой
`.button` в модуле страницы больше не пишем. Подсказка по наведению — `useHint`/`Hint`/`Term`: пузырь
рендерится только открытым, иначе его текст ломает поиск по тексту в тестах. Машинное значение на экране —
через `Term` со словарём из `labels.ts`, не `{row.status}` напрямую; проверяет `npm run check:labels`
(ложное срабатывание снимается пометкой `/* raw-ok */`, когда сервер прислал готовую фразу).

- Цвета только через токены в `src/index.css`. Хардкод hex в компонентах запрещён.
- Подписи машинных значений — только в `src/lib/labels.ts`, иначе одна роль

- Итоговой оценки надёжности и светофора нет (ADR-009). Любой статус — с текстовой подписью: цвет один нечитаем при дальтонизме.
