# CLAUDE.md — TG_Info

Дополняет корневой `Odintsov/CLAUDE.md`. При конфликте приоритет здесь.

## Что это

Портал деловой разведки по строительному рынку России: «быстро проверить, как дела у Заказчика».
Сырые тексты из Telegram-каналов и сайтов → извлечение локальной LLM → канонические
сущности (компании, объекты, роли, события) → карточка Заказчика и статистика подрядчиков.

## Структура

```
docs/migrations/   нумерованные SQL, применяются раннером (не psql вручную)
backend/           Express + TS, pg.Pool без ORM
frontend/          Vite + React + TS, четыре экрана MVP
```

## Команды

```bash
cd backend
npm ci                   # воспроизводимая установка по lock-файлу
npm run typecheck        # tsc --noEmit
npm test                 # unit, без сети и БД; внешний DATABASE_URL не используется
TEST_DATABASE_URL=postgresql://tg_test:tg_test@127.0.0.1:55433/tg_info_test \
  npm run test:integration   # только размеченная локальная tg_info_test (guard в src/db/testTarget.ts)
npm run migrate -- --dry # план без записи в БД, destructive помечены
npm run migrate          # применить; destructive (009) — только с --allow-destructive
npm run dev              # API на 127.0.0.1; фоновые задания — только флагами в .env

# Ингест (живой запрос к источнику — только при sources.access_status = approved)
npm run ingest:once -- --add <канал>      # добавить канал (на паузе, допуск не подтверждён)
npm run ingest:once -- --probe <канал>    # сверить селекторы с живой вёрсткой t.me/s/
npm run ingest:once -- --env-check        # какие ключи видит программа в .env
npm run ingest:once -- --bot-check        # проверить форвард-бота
npm run ingest:once -- --stats            # документы, очередь, доля дублей

# Пайплайн: запуск → чанки → набор кандидатов → публикация (этап 03B)
npm run pipeline:once -- --check          # LM Studio поднят?
npm run pipeline:once -- --reextract --limit N [--source key] [--doc id]  # поставить запуски
npm run pipeline:once -- [--loop]         # выполнить поставленные запуски (карточки не меняются)
npm run pipeline:once -- --runs           # запуски, покрытие, наборы
npm run pipeline:once -- --preview <набор> / --publish <набор> [--allow-stale]
npm run pipeline:once -- --retry          # новые запуски вместо failed/partial
npm run pipeline:once -- --errors         # последние отказы с текстом ошибки
npm run pipeline:once -- --skipped        # тексты, признанные нерелевантными
npm run pipeline:once -- --doc <id>       # документ целиком: текст, разбор, канон
```

**Не запускать старые команды автоматически.** Живой `--probe`, сбор, разбор,
`migrate` без `--dry` и любые изменяющие CLI — только осознанно и против
подтверждённой цели. `--probe` показывает, сколько узлов нашёл каждый селектор
(`wrap = 0` при большой странице = вёрстка `t.me/s/` изменилась), но это живой
запрос: сначала допуск источника, потом проба. Фикстура в `__fixtures__/` написана
по известной разметке, а не скачана с живого Telegram — тесты проверяют логику
разбора, но не актуальность селекторов.

**План развития — пакет `prompts/Customer_Dossier_Prompts/`**, состояние —
`docs/development/STATE.md` и `HANDOFF.md`. Этапы строго по одному.

## Рынок

Россия. Изначально проект строился под Казахстан — отсюда казахские буквы
в нормализаторе и формы ТОО/ЖШС в списке ОПФ: они оставлены намеренно, чтобы
пересланный пост про компанию из РК не ломал разбор. Идентификатор компании —
ИНН/ОГРН с проверкой контрольной суммы (`tax_id`), суммы в рублях (`amount_rub`).
Географического фильтра в промпте больше нет: отсекается только то, что не
относится к стройке и недвижимости.

## Ключевые решения (не менять без причины)

- **Telegram читаем без MTProto API**: `https://t.me/s/<канал>` — обычный GET, без ключей.
  Закрытые каналы — только через форвард-бота (BotFather, бот в личке, права админа не нужны;
  long polling, а не webhook — публичный HTTPS-адрес локальной машине не нужен).
  Никаких api_id/api_hash: они пользователю недоступны.
- **`TG_BOT_ALLOWED_USER_IDS` пустой = не принимать никого.** Не наоборот. Бот, открытый
  всем, — это прямой канал вливания произвольного текста в LLM и в карточки компаний.
- **Дедуп срезает подпись канала только с начала строки.** Срезать «источник»/«подписывайтесь»
  из середины строки нельзя: тем же движением съедается остаток настоящей новости.
  Размен осознанный: пропущенный дубль стоит одного вызова LLM, а склейка разных
  новостей теряет новость.
- **Роль — свойство связи, а не компании.** Одна компания бывает заказчиком на одном
  объекте и подрядчиком на другом. Роль живёт в `project_participants`.
- **Ничего не попадает в канон без дословной цитаты**, проверенной вхождением в `body`
  (`pipeline/verify.ts`). Имя сущности обязано встречаться внутри своей цитаты.
- **Слияние компаний асимметрично**: слить легко, разлить почти невозможно. Поэтому
  в серой зоне score (0.75–0.92) создаём новую компанию и кладём пару в `merge_queue`,
  а не сливаем. Автослияние только от 0.92 и никогда при конфликте ИНН/ОГРН.
- **Идентичность (этап 04, ADR-005).** Юрлицо, бренд и группа — `companies.entity_type`
  (одна каноническая таблица); реквизиты — реестр `entity_identifiers` по типу (ИНН ≠ ОГРН ≠
  ОГРНИП), `companies.tax_id` — совместимая проекция. Точное имя никогда не обходит
  реквизиты: упоминание с ИНН не прикрепляется к одноимённой компании без него, упоминание
  без формы и реквизитов — к юрлицу с реквизитами (бренд не получает ИНН дочернего ООО).
  Для упоминаний без реквизитов — одна стабильная provisional-сущность на имя; несколько
  равноправных кандидатов — `resolution_ambiguities`, не выбор первого и не новый дубль.
  Объекты: комплекс → очередь → корпус (`parent_project_id`), неизвестный город не равен
  совпавшему, общий участник — не довод идентичности, география — только из текста.
- **Слияние — только через `resolve/entityMerge.ts`** (ADR-005): предпросмотр, ожидаемые
  версии обеих сущностей, ключ идемпотентности, блокировки в стабильном порядке, коллизии
  до записи, журнал `entity_merges`/`entity_merge_moves`, tombstone вместо удаления.
  Утверждения неизменяемы: основания копируются на утверждение живой сущности, решения
  аналитика остаются в истории. Отмена — только при неизменившихся зависимостях, иначе
  план без автоприменения. Применение — флаг `MERGE_APPLY_ENABLED` (по умолчанию false).
  Новая таблица, ссылающаяся на компанию или объект, обязана попасть в перенос и в
  `dependencyState`, иначе слияние оставит висячие ссылки.
- **`resolve/normalize.ts` — единственный источник правды по нормализации.**
  Вызывается и на записи, и на поиске. Разойдутся — резолвер перестанет находить
  существующие компании и начнёт плодить дубли. Правки — только вместе с тестами.
  **После правки нормализатора старые ключи расходятся с новыми.** Ключи поиска
  вычисляются один раз при вставке. Так «ГК Консоль» (записана до того, как «ГК»
  попало в список форм) и «Консоль» жили двумя карточками. Смотреть расхождение —
  `--renormalize --dry`; запись ключей в рабочую базу — массовая правка канона,
  — версионный backfill `npm run backfill:identity -- --renormalize` (dry-run по умолчанию,
  запись только `--apply --confirm-copy` на копии). Правка нормализатора = bump
  `NORMALIZER_VERSION`. Автоматически не запускается.
- **Переразбор — только новым конвейером (этап 03B, ADR-004).** Старый `apply` с
  `clearDocumentContribution` удалял вклад документа вместе с тем, что подтвердил
  другой источник; он и слияние по-прежнему выключены в коде (`pipeline/guard.ts`),
  не возвращать. Новый путь: неизменяемый запуск с отпечатком параметров → чанки
  с диапазонами и append-only ответами → набор кандидатов → публикация одной
  транзакцией с ожидаемой версией. Снимается только вклад этой же публикации
  (evidence → `superseded`), решения аналитика и чужие доказательства остаются.
  Completed — только при всех чанках ok и полном покрытии текста. Автопубликация —
  флаг `REPROCESS_AUTO_PUBLISH` (по умолчанию false). Массовый переразбор рабочей
  базы — не одной командой: `--reextract` требует `--limit` (≤ 200).
  Карточки читают проекции `card_participations_v` / `card_events_v`; метрики
  светофора пока считаются по legacy-таблицам (этап 07).
- **Роль `not_participant` — не редкость, а частый случай.** Без неё модель обязана
  выбрать строительную роль для любой упомянутой компании: аналитики из пресс-релизов
  становились «проектировщиками» (15 при 1 генподрядчике). Если в `--audit`
  проектировщиков больше, чем подрядчиков, — это сигнал именно этой ошибки.
- **`prompt_version` / `model` / `schema_version` в каждой строке `extractions`.**
  Переизвлечение = bump `PROMPT_VERSION`, старые строки не удаляем.
- **`published_at` (дата поста) ≠ `occurred_on` (дата события).** Не смешивать.
- **Пайплайн умеет добавлять факты, но не отзывать их.** Резолвер переиспользует
  существующую сущность и не затирает поля, о которых новый документ промолчал —
  и это правильно: молчание одного поста не опровергает сведения из другого.
  Цена — значение, записанное сломанной версией кода, живёт вечно. Для таких
  случаев есть `--recheck`: снимает города и адреса, которые не подтверждаются
  ни одним документом. Добавляя новое проверяемое поле, добавьте его и туда.
- **Светофор — устаревший эвристический индекс, не оценка надёжности.** Веса 40/30/30
  не калиброваны, неизвестная дата события считается сегодняшней, суд без роли
  стороны считается тяжёлым событием. В UI он помечен legacy; «сигналов не найдено»
  не означает «проблем нет». Замена объяснимыми сигналами — этап 07. Состояние `grey`
  при `mentions_90d < 3` сохраняется: без него новая компания с одним негативным
  постом мгновенно краснеет.
- **Доступ: один локальный оператор.** API слушает только loopback, изменяющие
  операции и выдача досье — после входа по токену (серверная сессия, HttpOnly-cookie,
  проверка Host/Origin и CSRF). CORS авторизацией не является.
- **Допуск источника — отдельно для сбора и для ИИ-обработки** (`access_status`,
  `ai_processing_status`). `active` означает только «опрашивать по расписанию».
  Один gate (`ingest/policy.ts`) на всех входах: шедулер, CLI, бот, ручная вставка,
  очередь модели, теневой прогон. Допуск ставит оператор с основанием; агент
  согласований не заполняет.
- **Сетевые запросы к источникам — только через `net/safeFetch.ts`**: allowlist хоста
  источника, запрет внутренних адресов с проверкой в момент соединения, повторная
  проверка каждого редиректа, лимиты времени и размера. Локальная модель — отдельный
  доверенный адрес, исключений для loopback в политике источников нет.
- **Сайты читаем через RSS, а не разбором вёрстки.** Лента редко меняет формат,
  дизайн сайта переделывают ежегодно. Плюс это интерфейс, опубликованный для
  машин, а не обход чужого оформления. Полный текст статьи добираем отдельным
  запросом, только если в ленте один анонс.
- **Удаление источника запрещено, если по нему есть документы.**
  Каждое утверждение в карточке прослеживается до источника; удалить источник,
  оставив документы, значит разорвать эту цепочку. Удаление вместе с документами
  тоже выключено: каскад уносит упоминания и события, а роли остаются без
  доказательств. Нужна пауза, а не удаление.
- **Публикация ≠ текст.** Личность публикации — `(source_id, item_key)` в `source_items`
  (external_id → канонический URL → хэш текста). Правка поста — новая неизменяемая редакция
  в `document_revisions` (UPDATE/DELETE запрещены триггером), повтор — только наблюдение.
  Один текст в трёх каналах — три публикации. `raw_documents.body` не переписывается никогда:
  legacy-документ создаётся только для первой редакции, к нему привязаны цитаты. Полнота
  (`full/excerpt/caption_only/failed/unknown`) — по происхождению текста, не по длине. См. ADR-002.
- **Утверждение ≠ факт, решение аналитика ≠ вывод модели.** `assertions` (смысл неизменяем,
  новый смысл — новое утверждение), `evidence` (редакция + span в code points, проверяется базой;
  supports/contradicts/mentions; отзыв — статусом), `review_decisions` (append-only, версия и хэш набора
  доказательств на момент решения). `text_grounded` — «так написано», не «правда». Изменился набор
  доказательств — `needs_revalidation`, решение не удаляется. Решение пишется с `expectedVersion`
  и `idempotencyKey`. Legacy-статусы без обоснования — `legacy_unknown` + `provenance_gap`. См. ADR-003.
- **Цитата подтверждает, что написано в источнике, а не истинность.** ИНН, сумма,
  город и адрес принимаются только из собственной подтверждённой цитаты сущности;
  стороны события обязаны быть названы в его цитате. Неполный разбор (хвост текста
  вне чанков, упавший чанк, повтор на укороченном тексте) не применяется как полный.

## LM Studio

OpenAI-совместимый `/v1`, адрес в `LMSTUDIO_BASE_URL`. Модель — `Qwen3-8B` Q4_K_M
(ctx 8192, Flash Attention, KV-cache Q8) под 8 ГБ VRAM.
**`/no_think` в system-промпте обязателен** — иначе Qwen3 сожжёт `max_tokens`
на рассуждение и вернёт пустой `content`.
`response_format: json_schema` со `strict: true` требует: все свойства в `required`,
`additionalProperties: false` в каждом объекте, nullable как `["string","null"]`.

Переезд на RTX 6000 — только смена `LMSTUDIO_BASE_URL` и `LMSTUDIO_MODEL`, код не трогаем.

Размер чанка — `EXTRACT_CHUNK_SIZE` / `EXTRACT_MAX_CHUNKS` (по умолчанию 3500/6,
подобрано на живой нагрузке: 6000/4 давали таймауты). Подбирать под модель
и видеокарту через env, не правкой кода.

**Контекст в LM Studio не раздувать.** 16K на 8B не помещается в 8 ГБ вместе
с весами — модель уезжает в RAM и таймаутит. При чанке 3500 хватает 8192.

**Модель — Qwen3-8B, не 4B. Решено на данных, не менять без повторного `--compare`.**
На «Строительной газете» (промпт p2, 39 общих документов) согласие моделей по
релевантности — 36 %. 4B быстрее в 9 раз (4.6 с против 40.9 с), но признаёт
релевантными лишь 21 % отраслевых статей против 85 % у 8B. В 25 расхождениях
из 39 права 8B: 4B отбрасывала статьи про КРТ, новостройки и инфраструктуру,
отвечая пустышкой за секунду. Портал при этом не ломается и не ругается — он
молча теряет факты. Соблазн «ускорить поток на 4B» стоит проверить заново,
а не принимать на веру.

**Выбор модели — через `--shadow` и `--compare`, а не на глаз.** Теневой прогон
пишет только в `extractions`: канон и статус документа не трогаются. Смешать
в карточках результаты двух моделей нельзя — откатить такое нечем.

## Ингест: этика и осторожность

Читаем только публичные страницы. Публичность и локальность модели не заменяют
основания для сбора и ИИ-обработки. Троттлинг: 1 запрос / 4 с на канал, потолок
~10 req/min, backoff на 429. Источники в сидах и новые источники заводятся как
`paused` с неподтверждённым допуском — включать вручную после решения оператора.

## .env

Заводит пользователь вручную (`backend/.env.example` — образец). Не редактировать,
секреты в чат и логи не выводить.

## Фронтенд

```bash
cd frontend
npm install
npm run dev              # :5173, /api проксируется на :4100
npm run build            # tsc -b && vite build
npm run icons:generate   # PNG из public/favicon.svg, руками не правим
```

Четыре экрана: поиск, карточка Заказчика, статистика подрядчиков, админка.
Всё остальное — за границей MVP.

- Цвета только через токены в `src/index.css`. Хардкод hex в компонентах запрещён.
- Подписи машинных значений — только в `src/lib/labels.ts`, иначе одна роль
  называется по-разному на разных экранах.
- Светофор всегда с текстовой подписью: один цвет нечитаем при дальтонизме.
- Тема ставится инлайн-скриптом в `index.html` до отрисовки, иначе мигает светлым.
- Service worker — `registerType: 'prompt'`. Молчаливый `skipWaiting` подменяет
  чанки под открытой вкладкой и даёт белый экран посреди работы.
- **`/api` в service worker не кэшируется** (переопределяет правило «NetworkFirst для
  /api/» из корневого `Odintsov/CLAUDE.md`): досье — закрытые данные, после выхода
  они не должны читаться офлайн. Старые кэши `api` и шрифтов удаляются при старте.
- Внешних шрифтов нет — системный стек; dev и preview слушают только 127.0.0.1.
- Токен оператора и CSRF-токен не хранятся в localStorage, URL и логах.
