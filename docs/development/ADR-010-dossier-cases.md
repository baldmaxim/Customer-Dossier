# ADR-010 — Рабочее досье: обращения, шаблонные резюме, досье объекта

Дата: 2026-09-15. Этап 08A. Статус: принято.

## Контекст

После этапа 07 портал показывал объяснимые сигналы компании, но не отвечал на рабочий вопрос: «к нам
обратилась компания по конкретным работам на конкретном корпусе — что известно, что заявлено, что проверить».
Поиск открывал первую совпавшую строку, одноимённые юрлица различались только в карточке, заявления
обратившегося негде было записать отдельно от сведений источников.

## Решение

### Обращение (DossierCase) — запись оператора, не факт

- Миграция 019: `dossier_cases` и неизменяемая `dossier_case_versions`. Поля: выбранное юрлицо или явное
  «юрлицо не установлено» с названием со слов (CHECK), объект или название со слов, корпус, вид работ
  (подпись и нормализованный пакет), заявленная роль, заявленный заказчик (из базы или со слов), условия со слов,
  дата обращения, примечание, статус. `provenance = operator_recorded_claim` — константа.
- Запись обращения не создаёт утверждений и доказательств; установленная роль берётся из опубликованных утверждений.
- API: `GET/POST /api/cases`, `GET/PUT /api/cases/:id` (ожидаемая версия → 409; ключ идемпотентности на создание),
  keyset-пагинация, удаление запрещено триггером (закрытие статусом). Слияние компаний и объектов переносит
  `company_id`, `claimed_client_company_id`, `project_id` и учитывает их в `dependencyState` (ADR-005).

### Досье строится шаблонами при открытии, без модели

- `dossier/caseDossier.ts` (`dossier-template@1`) — чистая функция загруженных фактов (`dossier/facts.ts`:
  утверждения с активной поддержкой и их доказательства). LM Studio и сеть не нужны; дата сборки, срез сигналов
  и дата последней публикации в основаниях отдаются вместе с досье.
- Каждая фраза (`IStatement`) несёт атрибуцию и id: «в публикации сообщается» (text_grounded), «проверено
  аналитиком в пределах основания» (reviewed_supported), «спорно / отклонено по решению аналитика», «со слов
  обратившегося» (запись оператора), «не установлено в выборке» (отсутствие сведений — не факт отсутствия), «контекст».
- Разделы: предмет обращения (с одноимёнными юрлицами, чьи сведения не смешиваются) → 3–5 наблюдений
  (противоречия, установленная роль, документированный договор, суды, события объекта в периоде участия) →
  роль: заявленная отдельно от установленной, статус reviewed / reported / contradicted / not_established →
  кто заказывает работы: договоры с прямым основанием отдельно от совместного участия → условия: со слов и из
  источников, ничего не рассчитывается → контекст объекта с пересечением периодов → неопределённости → вопросы
  контрагенту только по реальным пробелам (нет юрлица, нет реквизитов, роль не установлена или противоречит,
  цепочка не документирована или отличается от заявленной, корпус, объём работ, условия, судебные дела).
- Резюме компании (`/api/companies/:id/dossier-summary`) и досье объекта (`/api/projects/:id/dossier?from&to`)
  — по тем же правилам: участники в выбранном периоде (пересечение по датам участия), договоры отдельно от
  совместного участия, история состояния по действительной дате, обращения по объекту.
- Необязательное перефразирование моделью не добавлялось.

### Выбор и проверка

- Поиск компаний отдаёт вид сущности, реквизиты, число объектов из снимка, совпавшее написание и число
  одноимённых; поиск объектов (`/api/projects/search`) — город, уровень и родителя.
- Решения аналитика: причина обязательна для отклонения, спора и возврата на проверку (сервер — 400
  `reason_required`, форма не отправляется). Очередь проверки показывает обе стороны противоречия рядом
  с цитатами и историей решений; отрицание роли без корпуса противоречит утверждению о любом корпусе
  (миграция 019 заменяет `review_queue_v`).
- Экран источников: отставание с последнего успеха, публикации и публикации с неполной текущей редакцией.

### Интерфейс и откат

- Новые экраны: «Обращения» (список и форма), обращение, объект, «Проверка»; в карточке компании — резюме,
  контрагенты по типу связи, противоречия, ограничения выборки и «Создать обращение».
- Ошибка API и истёкшая сессия не показывают прежние данные как свежие: страница показывает ошибку, 401 очищает
  кэш запросов и возвращает на вход; service worker `/api` не кэширует.
- Откат — сборка с `VITE_DOSSIER_UI=false`: маршруты и пункты меню досье скрыты, прежние экраны работают,
  обращения в базе сохраняются.

## Последствия

- Досье пересобирается при каждом открытии: при сотнях утверждений компании запрос тяжелее карточки 07.
- Снимок досье, граф и экспорт — этап 08B; снимок должен сохранить `templateVersion`, `rulesVersion`, срез и id.

## Дополнение этапа 12 (2026-09-17): применимость по предмету обращения

`dossier-template@2`, контракт `scope-match@1` (`backend/src/dossier/scope.ts`). Утверждение сравнивается с обращением по объекту,
корпусу, виду работ (нормализованная тема), роли и дате обращения: `match | compatible | unknown | conflict`. Неизвестное в
источнике не подтверждает обращение. Роль установлена только без конфликтов и с известным корпусом при выбранном; цепочка
documented — только договор по этому объекту без конфликтов. Остальное — `role.context` / `chain.context` с причиной и
статус `scope_unknown`. Противоречие — неотклонённое отрицание без конфликтов; отрицание по объекту без корпуса остаётся
противоречием с пометкой (асимметрия в сторону проверки). Отклонённое аналитиком — в истории, вывод не определяет.
Схема связей нормализует корпус тем же правилом и помечает рёбра без корпуса. Снимки до @2 не меняются.
