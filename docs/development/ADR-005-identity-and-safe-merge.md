# ADR-005 — Юрлица, бренды, объекты и безопасное слияние

Статус: принято на этапе 04 (2026-09-14). Термины DATA_CONTRACTS: Entity/Identifier, Project/Participation.

## Контекст

Резолвер хранил компанию одной строкой с `tax_id`: ИНН и ОГРН в одной колонке, бренд и юрлицо не различались,
упоминание без реквизитов прикреплялось к одноимённому юрлицу с реквизитами. Одноимённые ЖК с неизвестным
городом плодили дубль на каждый повтор, корпуса одного ЖК не отличались от комплекса. Слияние
(`resolve/merge.ts`) не проверяло реквизиты, удаляло роли без журнала и не имело отмены — с этапа 01 выключено.

## Решение

Миграция `014_identity_merge.sql`; модули `resolve/identifiers.ts`, `hierarchy.ts`, `company.ts`, `project.ts`,
`entityMerge.ts`, `merge.ts`, `identityBackfill.ts`.

1. **Одна каноническая таблица компаний.** `companies.entity_type` (`legal_entity/brand/group/unknown`) и `version`.
   Из текста выводится только то, что в нём есть: форма ГК — группа, форма или реквизит — юрлицо, иначе unknown.
   Бренд ставит оператор (`PATCH /api/entities/companies/:id/type`).
2. **Реестр реквизитов** `entity_identifiers`: юрисдикция, тип (`inn/ogrn/ogrnip/kpp/bin/other`), значение строкой,
   `validation_status` (контрольная сумма — только формат), происхождение (`extraction/legacy_import/manual`),
   редакция/доказательство, период. Активный реквизит уникален. Конфликт — тот же тип и юрисдикция с разными
   значениями. `companies.tax_id` остаётся совместимой проекцией; перенос legacy — `backfill:identity -- --identifiers`.
3. **Связи** `company_relations` (`brand_of/member_of_group/successor_of`, candidate/confirmed/rejected). Общий
   телефон, домен, адрес, руководитель — не связь и не довод слияния.
4. **Точное совпадение имени** (`decideExact`, чистая функция):
   - упоминание с реквизитом, не найденным в реестре, создаёт юрлицо; одноимённые с другим реквизитом того же
     типа — запрет в очереди, без реквизита — пара на решение;
   - с формой без реквизита: ровно один совместимый по форме кандидат — он; несколько — неоднозначность;
   - без формы и реквизита: ровно одна provisional-сущность (без реквизитов, unknown/brand) — она; нет — одна
     новая provisional и пары; несколько — неоднозначность;
   - неоднозначность пишется в `resolution_ambiguities` с якорем-редакцией (повтор увеличивает счётчик), резолвер
     возвращает null: публикация 03B не публикует такие кандидаты.
   Автослияние по похожести запрещено, если реквизит есть только у одной стороны.
5. **Объекты.** `project_level` (`complex/phase/building`), `parent_project_id`, `level_label`; уникальность ребёнка —
   (родитель, уровень, обозначение). `parseProjectPath` распознаёт только явные «очередь/корпус/строение/дом N» и
   порядковые формы с окончанием. Комплекс: известный город — только равный; неизвестный — одна стабильная
   запись без города; город в чужую запись не подставляется. Общий участник — пояснение в reasons, не балл.
   География — `geo_source='text'` + редакция; legacy — NULL.
6. **Слияние** (`applyEntityMerge`) — одна транзакция:
   - блокировки сущностей по возрастанию id; ключ идемпотентности (повтор — прежний результат, другой запрос с тем
     же ключом — 422); ожидаемые версии обеих сторон (иначе 409);
   - предпросмотр внутри транзакции; блокирующие конфликты до записи: реквизиты, вид сущности, форма,
     подтверждённая связь, противоположные стороны события, город, уровень/родитель, вложенность, коллизии
     уникальности legacy-событий и корпусов;
   - tombstone `merged_into_id`, перенос алиасов (дубликат — сумма счётчиков), упоминаний (дубликат того же
     документа и цитаты — удаление с образом строки), событий, ролей (дубликат открытой роли — удаление с образом),
     реквизитов, связей, дочерних объектов; пары очереди с исходной сущностью — rejected;
   - утверждения неизменяемы: для каждого утверждения с активными основаниями создаётся/находится утверждение с
     той же семантикой о живой сущности (`supersedes_assertion_id`), основания копируются
     (`copied_from_evidence_id`, `merge_id`), совпавшее по идентичности — не дублируется, снятое позицией —
     реактивируется; оригиналы — `superseded`; ссылки наборов публикаций 03B дополняются копиями. Решения
     аналитика не переносятся: остаются на исходном утверждении, изменение оснований даёт пересмотр;
   - `entity_merges` (снимки обеих сторон для исторических подписей, счётчики, состояние зависимостей после
     слияния) и `entity_merge_moves` (append-only: таблица, строка, колонка, было/стало, образ удалённой строки).
7. **Отмена** (`undoEntityMerge`): состояние зависимостей обеих сторон сравнивается с сохранённым; при любом
   изменении — `UnsafeUndoError` с планом (что добавилось/изменилось, шаги ручного разнесения), без записи. Иначе
   ходы откатываются в обратном порядке: значения колонок, вставка удалённых строк с исходными id, копии
   оснований — `superseded`, оригиналы — `active`; журнал `applied → undone` (единственное разрешённое изменение).
8. **Ренормализация** — `NORMALIZER_VERSION` и `normalizer_version` у строк; `backfill:identity -- --renormalize`
   пересчитывает строки другой версии пакетами с checkpoint; совпавшие после пересчёта ключи — пары в очередь.
9. **Включение.** `MERGE_APPLY_ENABLED=false` по умолчанию: предпросмотр, журнал и чтение работают; применение и
   отмена в API/CLI отвечают 423. API: `GET /api/entities/merge-preview`, `POST /api/entities/merge`,
   `GET/POST /api/admin/merges/:id/preview|merge`, `GET /api/entities/merges`, `POST /api/entities/merges/:id/undo`,
   `POST /api/entities/companies/:id/identifiers`, `POST /api/entities/relations`, `GET /api/entities/ambiguities`.

## Последствия

- Одинаковое имя с разными реквизитами, бренд и юрлицо, одноимённые ЖК разных городов, корпуса одного ЖК остаются
  раздельными; неоднозначное — в очереди, не в произвольной сущности.
- Слитая сущность восстановима, пока после слияния не появилось новых данных; после — только ручное разнесение.
- Legacy-метрики (`company_metrics`) пересчитываются после слияния/отмены; их логика не менялась (этап 07).
- Резолвер 03B может вернуть null при неоднозначности — кандидат не публикуется, пока оператор не разберёт очередь.
- Новая таблица со ссылкой на компанию или объект обязана попасть в перенос (`moveLegacyRows`/`moveAssertions`),
  в `MOVABLE` и в `dependencyState`.

## Откат

`MERGE_APPLY_ENABLED=false`: применение выключено, история и tombstone-переадресация читаются. Отдельные слияния —
отмена при неизменных зависимостях. Строки 014 не удалять, обратный destructive SQL не выполнять.

## Дополнение этапа 15A (2026-09-17): решение по упоминанию, устаревший предпросмотр, линия решений

- **Четыре разных действия.** Решение по одному упоминанию (`ambiguity_decisions`, миграция 023), provisional/неустановленное
  (`kept_unknown`), не упоминание (`dismissed`) и глобальное слияние (`entityMerge`, флаг + предпросмотр) — разные операции.
  Выбор кандидата в одном тексте не сливает одноимённые сущности, не добавляет алиас и не ставит пару в очередь слияний.
- **Контракт решения** `ambiguity-decision@1`: причина обязательна, `expectedVersion` неоднозначности (409), ключ идемпотентности
  с hash запроса (повтор — прежний результат, другой запрос — 422), журнал append-only. Кандидат обязан входить в набор и быть
  живым; реквизит (10/12/13/15 цифр) в окне ±200 code points вокруг упоминания, принадлежащий другому кандидату или
  расходящийся с реквизитом выбранного, и правовая форма упоминания, отличная от формы кандидата, — 422 `choice_blocked`.
  Исключения по умолчанию нет. Город не сверяется: у неоднозначности нет подтверждённого цитатой города (ограничение).
- **Действие решения.** Резолвер (`analystMapping`) выбирает сущность только для той же (вид, ключ имени, редакция) и только если
  она (через tombstone) всё ещё среди текущих кандидатов. Решение канон не переписывает: выбор проявится при новом запуске
  разбора этой редакции (03B). Смена набора кандидатов повышает `version` неоднозначности — старая форма получает 409.
- **Устаревший предпросмотр.** `merge-preview@1`: `previewToken` = sha256 состояния зависимостей обеих сущностей
  (`dependencyState`, включая доказательства, решения аналитика и решения по упоминаниям). API слияния требует токен;
  иное состояние при применении — 409 `merge_preview_stale`, без записи. CLI передаёт токен своего предпросмотра.
- **Линия решений.** Решения остаются на исходных утверждениях; `loadPriorDecisions` обходит цепочку слияний (глубина ≤ 10,
  `UNION` не зацикливается) и отдаёт каждое решение один раз (`DISTINCT ON`, ближайшее слияние). Автор, время, решение и
  исходное утверждение не подменяются; утверждение цели статус review не получает.
- `ambiguity_decisions.entity_id` слиянием **не переносится** (журнал неизменяем): решение читается через tombstone.
  Таблица учтена в `dependencyState`, манифесте (`history`) и контрольных числах.
- Откат: не вызывать `POST /api/entities/ambiguities/:id/decisions` (UI — вкладка «нерешённая идентификация»); таблица и история
  остаются, резолвер без решений ведёт себя как до 15A. Удалять решения нельзя.

## Дополнение 02.10.2026: пары «возможный дубль» разбирает модель (решение владельца)

Очередь слияния копила сотни пар (225 компаний и 79 объектов на сервере), и каталог показывал по три
«Донстроя». Владелец решил: разногласия разбирает модель.

1. **Вердикт.** `entity-match@1` (`llm/entityMatch/*`, `resolve/modelReview.ts`): по паре — `same` / `different` /
   `unsure` и причина, на строке `merge_queue` (миграция 041: `model_verdict`, `model_reason`, `model_name`,
   `model_prompt_version`, `judged_at`, `decision_note`). Модель видит то же, что оператор в «Проверка → Дубли»:
   названия, формы, вид, реквизиты, написания, объекты с ролями, группу компаний, запись ДОМ.РФ. Ошибка допустима
   только в сторону `unsure`. Смена модели или промпта — новый вердикт.
2. **Правила раньше модели.** Разные ИНН/ОГРН (`identifier_conflict` предпросмотра) — `different` без вызова; две
   разные записи ДОМ.РФ у объектов — `different` без вызова.
3. **Применение** — флаг `MODEL_REVIEW_APPLY` (вердикты без применения — `MODEL_REVIEW_ENABLED`): `same` — слияние
   тем же `entityMerge` (предпросмотр этого направления, версии, `previewToken`, журнал, отмена) от имени
   `model:<модель>` и только при `MERGE_APPLY_ENABLED` и `canApply`; иначе пара ждёт с причиной в `decision_note`.
   `different` — пара отклонена от имени модели с причиной. `unsure` — ждёт оператора. Направление — к карточке
   с реквизитами или сведениями ДОМ.РФ.
4. **Прозрачность.** Вердикт и причина — рядом с парой на экране; в истории слияний — «модель (<имя>)»; отменить
   слияние можно, пока зависимости не менялись (п. «Откат»). Консоль: `npm run review:model -- [--limit N] [--apply]`
   — отчёт «что решено, кем, почему».

## Дополнение 06.10.2026: одно название в разной записи

«Сминекс» (без ИНН) жил отдельно от «Sminex» и «Смайнекс»: транслитерация давала ключи `smineks`, `smaineks`,
`sminex`, а балл резолвера у имён в разных алфавитах (`s_norm = 0`) не доходит до серой зоны 0.75 — пара не попадала
в очередь, и модель её не видела.

1. **Звуковой ключ** — `normalize.ts::soundKey` от `key`: свёртка сочетаний (x→ks, c→k/s, ph→f, ts→s, kh→h …),
   гласные после первой буквы отбрасываются, повторы схлопываются; ключ короче 4 или имя короче 5 — не участвует.
   В базе не хранится: правка правил не требует `NORMALIZER_VERSION` и backfill.
2. **Ключ не решает.** `resolve/soundPairs.ts` ставит пару в `merge_queue` (pending, score 0.8, `reasons.key =
   'sound_key'`), вердикт выносит модель (`entity-match@2`: правило «одно название в разной записи — довод за, если
   отличительное слово то же; похожее звучание разных слов — не довод»), применение — прежними флагами.
3. **Не ставятся:** обе стороны с действующим реквизитом (разные юрлица), карточка «не компания», временное имя по ИНН,
   ключ, общий для 6+ компаний (шум, а не одно имя). Отклонённая пара не всплывает (уникальность пары в очереди).
4. **Запуск:** в тике модели (`MODEL_REVIEW_ENABLED`) до вердиктов, до 50 пар за проход, каталог без изменений не
   перечитывается; консоль — `npm run review:model -- --sound-pairs [--apply]` (без `--apply` — план).
5. **Видимость:** плашка «Похожие компании» показывает и ждущие пары очереди (вердикт «разные» — нет, «та же» —
   первой и с подписью); в «Дублях» у такой пары вместо процента — «звучит одинаково».
