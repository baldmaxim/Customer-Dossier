# Первое настоящее досье — короткий порядок

Только то, что нужно для одного полезного досье по одной компании: источник → сбор → разбор → проверка
человеком → досье и снимок. Это не приёмка и не тестирование: проверка установки — `TESTING_LOCAL.md`,
эксплуатация целиком — `LOCAL_RUNBOOK.md`.

## 0. Один раз: рабочая база

- Настоящим материалам — **отдельная постоянная база**. `tg_info_test` не использовать: интеграционные
  тесты выполняют `DROP SCHEMA public CASCADE` и уносят всё, что там лежало. Маркер тестовой цели рабочей
  базе не ставить.
- Базу создаёт пользователь и сам вписывает `DATABASE_URL` в `backend/.env` (образец — `backend/.env.example`).
  Агент `.env` не редактирует и базы не создаёт.
- Схема: `npm run migrate -- --dry` (план) → `npm run migrate`. Старую неизвестную базу не мигрировать.
- Резервная копия до первой ценной записи — `LOCAL_RUNBOOK.md` §5.

## 1. Обычный запуск

```powershell
.\start-portal.ps1        # два окна: backend и frontend; больше ничего не делает
```

Или вручную: `cd backend; npm run dev` и `cd frontend; npm run dev`. `npm ci`, миграции и тесты при каждом
открытии не нужны — только после обновления кода или схемы.

- LM Studio: модель из `LMSTUDIO_MODEL` загружена, сервер на `LMSTUDIO_BASE_URL`. Проверка —
  `npm run pipeline:once -- --check`.
- Вход: токен из `backend/.local/operator-token`.
- Портал сам ничего не собирает и не разбирает: `INGEST_ENABLED`, `PIPELINE_ENABLED`, `BOT_ENABLED`,
  `METRICS_AUTO_REFRESH` по умолчанию выключены.

## 2. Источник: сначала допуск, потом сбор

```powershell
cd backend
npm run ingest:once -- --add <канал>       # завести канал (на паузе, без допуска)
npm run ingest:once -- --probe <канал>     # живой GET: сверить селекторы с вёрсткой t.me/s/
npm run ingest:once -- --source <канал>    # собрать один источник
```

- Допуск на **сбор** и, отдельно, на **ИИ-обработку** ставит оператор: Админка → Источники → «Допуск»,
  с основанием и ответственным. Без допуска CLI откажет и ничего не сохранит; основание в манифесте или
  в этой инструкции допуска не выдаёт.
- Первый проход берёт одну страницу `t.me/s/<канал>` (обычно около 20 публикаций) и историю глубже не
  собирает — в отчёте `stopReason: history_not_collected`. У Telegram ограничение по страницам, а не точное
  число постов: «ровно 10 материалов» здесь не гарантируется, объём ограничивается на следующем шаге.
- Ручная вставка (Админка → «Вставить текст вручную») — для закрытых каналов и статей, до которых парсер не
  добирается. Это тот же вход сбора: источнику «Ручная вставка текста» (`manual:form`) нужен такой же допуск,
  новых прав на материал вставка не даёт.

## 3. Разбор: постановка и исполнение — разные действия

```powershell
npm run pipeline:once -- --check                                  # LM Studio отвечает?
npm run pipeline:once -- --runs                                   # что уже стоит в очереди
npm run pipeline:once -- --reextract --limit 10 --source <канал>  # поставить ограниченный набор
npm run pipeline:once                                             # выполнить поставленное
```

- `--limit` обязателен (1…200): переразбор без лимита запрещён.
- Исполнение берёт **всю** очередь, а не только что поставленное: фильтр предыдущей команды на него не
  распространяется. Перед запуском посмотрите `--runs` и убедитесь, что очередь относится к вашей подборке.
- Из интерфейса: «Сохранить текст» → «Поставить на разбор» (одна редакция), либо Документ → Редакции →
  «Поставить на разбор». Кнопка только ставит задание; при выключенном исполнителе так и написано —
  выполнит `npm run pipeline:once`. Постановка не вызывает модель.
- Карточки компаний не меняются, пока набор кандидатов не опубликован.

## 4. Проверка человеком и публикация

- «Запуски» в навигации → карточка запуска: чанки, отказы модели, кандидаты с цитатами, покрытие текста.
  Неполный запуск не публикуется.
- Предпросмотр набора → публикация (или `--preview <набор>` / `--publish <набор>`).
- Сверять не только цитаты кандидатов, но и исходный текст: пропущенный факт сам о себе не сообщит.
  Обязательный минимум проверок — чужой ИНН рядом в тексте, отрицание («не является подрядчиком»),
  другой корпус или очередь объекта.
- Публикация набора — не решение аналитика. «Проверено аналитиком» ставится отдельно в «Проверке».
- Автопубликации нет (`REPROCESS_AUTO_PUBLISH=false`), слияния не применяются (`MERGE_APPLY_ENABLED=false`).

## 5. Досье

Обращения → новое обращение (заявленная роль, объект, корпус, вид работ, дата) → досье: «Кратко для
переговоров», вопросы контрагенту, пробелы → снимок → выгрузка MD/JSON/HTML. Снимок неизменяем; HTML —
«Версия для печати», не PDF.

## 6. После прогона

- Перезапустить портал и открыть снимок: данные и выгрузка на месте.
- Резервная копия выбранной базы (`LOCAL_RUNBOOK.md` §5). Дамп делается и восстанавливается целиком.
- Что реально прошло по источнику — вписать в `sources/VALIDATED_SOURCES.md`. Статус модели от одного
  прогона не повышается: `LOCAL_MODEL_VALIDATED` остаётся «нет», пока оценка не проведена.

## 7. Если это пилот

Манифест по шаблону `pilot/pilot-manifest.template.json`, проверка — `npm run pilot:check -- --manifest <файл>`:

- `qualityDecision: "pending"` — предупреждение и обязательная ручная проверка, а не запрет; `rejected`
  блокирует ИИ-шаги;
- нет допуска названного источника, включённый фон, чужая база, неприменённые миграции — BLOCKED;
- в манифесте только `website` и `telegram`: ручная вставка им не описывается;
- `pilot:check` читает `DATABASE_URL` из окружения и `backend/.env` (открытый дефект ACC-03) — убедитесь,
  что окно смотрит в нужную базу.

## Чего здесь нет

Полной оценки модели, автономного сбора рынка, массового исторического наполнения, автопубликации, слияний
и печати в PDF. Один успешный прогон не меняет `LOCAL_MODEL_VALIDATED`, `LIVE_SOURCE_VALIDATED`
и `PRODUCTION_READY`.
