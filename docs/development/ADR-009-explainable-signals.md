# ADR-009 — Объяснимые сигналы вместо индекса риска

Дата: 2026-09-15. Этап 07. Статус: принято.

## Контекст

Карточка и список подрядчиков читали `company_risk` (миграция 007): одно число 0–100 и цвет из смеси
тональности упоминаний (40), доли объектов с задержкой (30) и наличия суда или банкротства за год (30).
Неизвестная дата события считалась сегодняшней, задержка объекта приписывалась всем текущим участникам,
суд считался тяжёлым событием независимо от роли стороны, перепечатки множили «негатив».
Сортировка «по риску» превращала это число в рейтинг.

## Решение

### Read-model — снимок на явный срез

- `signals/rules.ts` (`signals@1`) — чистая функция входа и среза (`cutoff`). Системные часы внутри
  правил не используются; одинаковые данные и срез дают одинаковый снимок.
- `signals/load.ts` берёт только записанное до среза: утверждения, активные доказательства, публикации,
  наблюдения, реквизиты. Ограничение: статус доказательства, сменившийся после среза, не восстанавливается.
- Миграция 018: `signal_refreshes` (журнал: срез, версия правил, статус, ошибка) и
  `company_signal_snapshots` (payload и столбцы списка). Пересчёт — `signals/refresh.ts`: запись
  `running` → снимки и `succeeded` одной транзакцией → при ошибке `failed` с текстом. Карточка читает
  последний успешный снимок (`signal_active_refresh_v`) и показывает `stale` с причинами: неудачный
  последний пересчёт, данные после среза, другая версия правил. Advisory lock не даёт двум пересчётам идти
  одновременно; зависший `running` старше часа закрывается как проваленный. Хранятся снимки трёх последних
  успешных пересчётов, журнал — весь.
- Запуск: `npm run metrics:refresh [-- --cutoff ISO]`; по расписанию — только `METRICS_AUTO_REFRESH=true`.

### Дополнение (2026-09-21): правила `signals@2`

Карточка компании показывала девять чисел и держала их в узкой колонке. По задаче владельца
добавлены числа, которые раньше были только списками: договоры и корпоративные связи (по тому же
правилу «положительно, как факт, не отклонено»), названные контрагенты, пакеты работ, события по
видам, число судебных дел и края выборки по датам публикаций (`IDateSignal`: дата неизвестна —
`insufficient_data`, а не «давно»). Правила прежних чисел не менялись.

Версия поднята до `signals@2`, потому что состав снимка изменился: старые снимки остаются
`signals@1` и новых чисел не содержат. Карточка в этом случае говорит, что снимок считан прежними
правилами, и не досчитывает ничего сама. Числа появляются после `npm run metrics:refresh`.

### Три блока снимка и контекст по запросу

У каждого числа `IAggregate`: значение, правило словами, окно (по дате события или публикации),
знаменатель, исходные id (до 200) — drilldown совпадает с SQL. Нулевой знаменатель — `insufficient_data`
и `null`, не 0 % и не 100 %.

1. **Идентификация и полнота**: статус (реквизит с контрольной суммой / не проверен / только имя /
   неоднозначность), реквизиты по типу, публикации, источники, полнота текстов, legacy-канон, не
   перенесённый в утверждения (он в сигналах не учитывается и об этом сказано).
2. **Опыт**: объекты из положительных утверждений об участии о состоявшемся (не отклонённых); разбивка
   по роли и пакету работ, доля проверенных аналитиком. План, возможность, заявление и отрицание — отдельный
   список «не учтено». Договоры — перечнем со стороной и суммой как написано; суммы не складываются,
   стоимость объекта участнику не приписывается.
3. **Публикации и события**: публикации (перепечатки отдельно), публикации за 90 дней по дате публикации,
   без даты; семьи одинакового текста и их происхождение — `established` (первоисточник в выборке),
   `named` (пересылки называют источник, его нет), `unknown` (не установлено, не считается независимым).
   События, где компания — сторона: окно 12 месяцев по дате события; без даты — не в окне, отдельно
   «без даты, опубликованы за 90 дней» (окно публикаций); будущая дата и интервал через границу — метки.
   Уровень проверки: reviewed / text_grounded / legacy_unreviewed / disputed / rejected — отклонённое
   и спорное видны, но не reviewed. Суды — дела по номеру, роль компании в деле и стадии; истец не
   «негатив». Отрицательные, плановые и слуховые события — «не учтено». Все события — «по сообщению источника».
4. **Контекст объекта** (`/api/companies/:id/context?projectId=`) — живой запрос на срез: участие
   компании (роль, корпус, пакет, период) и события объекта с пометкой пересечения периодов и корпуса.
   Событие объекта без компании в её события не попадает; пересечение — контекст, не причинность.

### Интерфейс и совместимость

- Карточка: без вердикта, цветной полосы и индекса; блоки сигналов с раскрытием правила и исходных id,
  переход к утверждению и контексту объекта. Список подрядчиков: идентификация, объекты, роли, события
  с датой и без, роли в судах, публикации и семьи; сортировка только по объектам или названию.
- `company_risk` / `company_metrics` (007) не переписаны. Новая карточка и список их не читают;
  `GET /api/companies/:id/legacy-risk` — только для сравнения, с заголовком `Deprecation: true`.
  Значения v2 и legacy не смешиваются.
- Снимок будущего досье (08B) фиксирует `rulesVersion`, `cutoff` и исходные id из payload.

## Последствия

- Карточка без пересчёта показывает «сигналы ещё не рассчитывались», а не пустые хорошие значения.
- Размер снимка пропорционален числу компаний; расчёт — пакетами по 200 в одной транзакции записи.
  На больших объёмах транзакция может быть долгой — пересмотреть при росте.
- Без шкалы, рекомендаций «работать/не работать», вероятности банкротства и юридических выводов.

## Откат

Фронтенд и API прежнего этапа (git) читают `company_risk`, который не удалялся; таблицы 018 не мешают.
Откат не восстанавливает доверие к формуле: экран остаётся с пометкой legacy.

## Дополнение: signals@3 (05.10.2026)

Владелец попросил графики на карточке компании. Чтобы график не выдумывал чисел, ряды посчитаны правилами снимка,
а не на клиенте:

- **`media.publicationsByMonth`** — публикации по календарному месяцу даты публикации (UTC, как окно 90 дней),
  24 месяца по месяц среза включительно. Не входят: без даты, раньше окна, позже среза и **снимки реестра ДОМ.РФ**
  (`registry_records`: их дата — дата сбора, а не публикации; иначе ряд показывал бы работу обходчика как активность
  компании). `media.publications` прежний — снимки в нём остаются, правило не менялось.
- **`media.eventsByMonth`** — неотклонённые события по месяцу начала даты события; только точность до дня или месяца.
  Квартал и год в месяц не раскладываются (`excluded.coarse`): разложить — значит выдумать месяц.
- Ряд — `IAggregate` (value — сумма месяцев, denominator — всё рассмотренное, ids — учтённые id на итоге) плюс
  `buckets`, `excluded` по причинам и `partialLast` (месяц среза не закончился). Инвариант: value = Σ месяцев,
  denominator = value + Σ excluded. id по месяцам не хранятся — drilldown идёт по итогу.
- **Исправление доли (`share`)**: числитель — число разных id (`value`), а не длина списка `ids`, урезанного до 200.
  До signals@3 доля выше 200 утверждений занижалась. Числа меняются — поэтому только в составе новой версии.

На экране: «Публикации и события по месяцам» — два графика на одной оси месяцев, у каждого своя шкала (не две шкалы
на одном), что не вошло — словами, числа — таблицей под раскрытием; неполный последний месяц светлее и назван.
Снимок прежних правил рядов не содержит — карточка говорит «появятся после следующего расчёта» и ничего не досчитывает.
Ряд — форма потока сведений, а не оценка: ни шкалы, ни «роста/падения» в словах нет.
