## Что изменилось для пользователя

- Компании с одним названием и разными ИНН, бренд и его ООО, одноимённые ЖК в разных городах, корпуса одного ЖК больше
  не склеиваются. Упоминание без реквизитов не получает ИНН одноимённого юрлица.
- Повтор одного и того же названия без реквизитов не создаёт новую «пустую» компанию каждый раз; при нескольких
  равноправных кандидатах упоминание уходит в очередь уточнения, а не к первой строке.
- В карточке компании: вид (юрлицо/бренд/группа), реквизиты по типу (ИНН, ОГРН, ОГРНИП), явные связи (бренд, группа,
  правопреемник). Поиск находит компанию по любому реквизиту из реестра.
- Очередь слияний в админке: предпросмотр обеих сторон, что переносится, что блокирует; «Слить» с версиями и ключом;
  журнал слияний с отменой. Если после слияния появились новые данные, отмена отказывает и показывает план разнесения.
- Применение слияния включается флагом `MERGE_APPLY_ENABLED` (по умолчанию выключено).

## Непроверенное, остаточные риски, решения

- Экран 390 px глазами не проверялся (CSS: колонки с 768 px).
- Решения аналитика при слиянии не переносятся на утверждение живой сущности — остаются в истории исходного и
  требуют пересмотра (консервативно, по требованию «не переносить безусловно»).
- Неоднозначное совпадение останавливает публикацию кандидата 03B до разбора очереди `resolution_ambiguities`; UI
  разбора этой очереди нет (есть `GET /api/entities/ambiguities`) — следующий UI-этап.
- Legacy-строки компаний без `normalizer_version` будут просканированы ренормализацией целиком (однократно).
- Разбор иерархии распознаёт только явные формы; «секция», «литера» в названиях и сложные адреса — как название.
- Реквизит, найденный в тексте, остаётся привязанным к редакции, но не к конкретному `evidence` — связь с цитатой
  через редакцию; прямой `evidence_id` заполняется при ручном вводе/следующих этапах.
- Метрики светофора пересчитываются после слияния/отмены, но логика legacy (этап 07).
- Внешние реестры и адресные нормализаторы не подключались.
