# ADR-004 — Неизменяемые запуски извлечения и атомарная публикация набора

Статус: принято на этапе 03B (2026-09-14). Термины DATA_CONTRACTS: ExtractionRun, ExtractionChunk, promotion.

## Контекст

Старый путь `raw_documents → extractions → apply` перед записью удалял все упоминания, события и роли
документа (`clearDocumentContribution`). Переразбор одного документа стирал роль, подтверждённую другим
источником; частичный разбор мог заменить полный; повтор с тем же ключом не сохранял новый ответ; два
worker'а и поздний старый разбор не различались. С 01 этот путь заблокирован в коде.

## Решение

Миграция `013_extraction_runs_publications.sql`, модуль `backend/src/reprocess/`.

1. **Запуск** (`extraction_runs`) — по редакции (`revision_id`), с `fingerprint` = sha256 от версии и хэша
   промпта, версии и хэша схемы, провайдера, модели, параметров генерации и параметров нарезки
   (`chunker@2-codepoints`, размер, лимит, перекрытие). Повтор провалившегося — **новый** запуск; строки
   прежнего не меняются. Одна живая (queued/running) пара редакция+отпечаток — частичный уникальный индекс.
2. **Lease и fencing.** Захват — `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED)`, срок lease,
   `fencing_token` растёт при каждом захвате. Каждая запись (чанки, ответ, итог) — короткая транзакция с
   `SELECT … FOR UPDATE` запуска и сверкой токена; устаревший держатель получает `StaleLeaseError`.
   Транзакция не держится, пока модель отвечает. Исчерпавший `MAX_CLAIMS=3` захвата запуск — `failed`.
3. **Чанки** (`extraction_chunks`) — диапазоны `[range_start, range_end)` в code points `document_revisions.body`
   (тот же счёт, что у доказательств и PostgreSQL `substring`). Ответы — `extraction_chunk_responses`,
   append-only (триггер): попытка, токен, исход (`ok/invalid_json/schema_error/llm_error/timeout/truncated_input`),
   payload + sha256, сырой ответ при ошибке, usage. Повторный захват не отдаёт модели готовые чанки.
4. **Итог.** `completed` — только если все чанки `ok` и объединение их диапазонов покрывает весь текст
   (перекрытие не считается дважды, дыра видна). Иначе `partial`/`failed` с числами покрытия. Хвост сверх
   лимита чанков — `failed` без вызова модели. Ответ на укороченном тексте — `truncated_input`, не `ok`.
   Размер чанка — в символах, это приближение к токенам с запасом; окно контекста задаётся в LM Studio.
5. **Набор кандидатов** (`candidate_sets`, `candidate_assertions`) создаётся в той же транзакции, что итог
   `completed`. Проверка ответа (`verifyExtraction`) идёт по тексту своего чанка — цитата и реквизиты
   локальны. Упоминания получают id `c<чанк>:<вид>:<n>`; связи и события ссылаются на сущность своего чанка.
   Сущности чанков объединяются только при совпадении ключа имени **и** ИНН (у компании) / города
   (у объекта): неизвестный реквизит не совпадение. События не объединяются по type/company/project;
   одинаковыми считаются только с той же абсолютной позицией цитаты (перекрытие чанков). Содержание
   кандидата хранит описание сторон — набор самодостаточен для предпросмотра и публикации.
6. **Публикация** (`publishCandidateSet`) — одна транзакция:
   - блокировка набора и `item_publications` (указатель на активный набор публикации + `version`);
   - набор уже активен → `already_published` (идемпотентно, без записи);
   - `expectedVersion` не совпала → `PublicationConflictError` (API 409);
   - перепроверка `ai_processing` источника → `rejected_policy` (набор остаётся технически сохранённым);
   - устаревший набор (активен разбор более новой редакции или более позднего запуска той же редакции,
     либо у публикации есть более новая редакция) → `rejected_stale`, публикация только с `allowStale`;
   - стороны разрешаются резолвером; сначала переиспользуется ровно одна сущность, уже разрешённая
     прежними наборами **этой же** публикации (иначе объект без города размножался бы при каждом переразборе);
   - `upsertAssertion` (origin `extraction`); событие без даты, суммы и контрагента получает `event_discriminator`
     (хэш нормализованной цитаты) — два суда одной компании остаются двумя утверждениями;
   - `addEvidence` с `extraction_chunk_id`; позиция, замещённая
     прежним набором (`superseded`), снова активна, отозванная аналитиком — нет;
   - доказательства прежнего набора, которых нет в новом, — `superseded` (строки остаются); состояние
     затронутых утверждений пересчитывается: решение аналитика остаётся, изменение набора доказательств
     даёт `needs_revalidation`; `reviewed_supported` машина не выставляет;
   - статусы наборов, `version + 1`, `publication_history` (append-only).
7. **Проекции для карточек.** `replaced_legacy_documents_v` — legacy-документы, чья публикация уже имеет
   активный набор. `card_participations_v` и `card_events_v` — legacy-строки незамещённых документов плюс
   утверждения активных наборов (`published_assertions_v`). Вручную подтверждённое legacy-событие остаётся
   видимым и после замещения. Legacy-таблицы новым конвейером не пишутся и не удаляются.
8. **Переключение.** `PIPELINE_ENABLED=true` запускает новый worker (`reprocess/worker.ts`): автопостановка
   только ещё не разобранных последних редакций, выполнение, публикация — только при
   `REPROCESS_AUTO_PUBLISH=true` (по умолчанию false). CLI: `--reextract --limit N` (≤ 200), `--retry` (новые
   запуски), без флагов/`--loop` (выполнение), `--runs`, `--preview`, `--publish [--allow-stale]`. API:
   `GET /api/reprocess/runs`, `GET /api/reprocess/sets/:id/preview`, `POST /api/reprocess/sets/:id/publish`.
   Старый `apply`, `--retry-skipped`, `--renormalize`/`--recheck` без `--dry`, `--merge` остаются заблокированы.

## Последствия

- Карточка читает либо весь старый, либо весь новый набор публикации; сбой внутри публикации не оставляет
  половины. Поздний старый разбор не перезаписывает новый без отдельного решения.
- Нерелевантный новый разбор снимает только вклад этой публикации; компания и чужие подтверждения остаются.
- Метрики светофора (`company_metrics`) по-прежнему считаются по legacy-таблицам и не видят замещения — до
  этапа 07. Лента упоминаний (`mentions`) — legacy.
- Отзыв `ai_processing` не снимает уже опубликованные наборы (право обработки ≠ опровержение); новые захваты
  и публикации запрещаются. Отражение статуса источника в карточке — вместе с сигналами (этапы 05–07).
- Резолвер при публикации может создать компанию/объект и пару в `merge_queue` — как раньше, без автослияния
  в серой зоне.

## Откат

Остановить writer: `PIPELINE_ENABLED=false`, `REPROCESS_AUTO_PUBLISH=false`. Карточки продолжают читать
последний опубликованный набор. Вернуть прежний набор — `--publish <старый набор> --allow-stale` (отдельное
решение оператора). Не возвращать `clearDocumentContribution`, не удалять строки 013.
