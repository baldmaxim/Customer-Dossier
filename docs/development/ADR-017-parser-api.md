# ADR-017 — parser-api.com: открытые реестры о компании по ИНН, а не источник публикаций

Статус: принято 2026-10-06 (этап 24A — каркас и сбор; карты и экраны — 24B, 24C; включение — ключ и проба владельца).

## Контекст

Владелец (06.10.2026): портал должен за минуту отвечать «как дела у Заказчика», когда тот обращается к нам
(генподрядчику) или когда в Telegram замечен его новый объект. Публикации и проектная декларация не говорят о
финансовом положении, судах и долгах. Это есть в открытых реестрах: ГИР БО (бухгалтерская отчётность), «Прозрачный
бизнес» ФНС (численность, налоги, недоимка), картотека арбитражных дел, ФССП, Федресурс (банкротство). Напрямую
программой их читать нельзя (капча, защита от роботов), поэтому владелец выбрал посредника — parser-api.com, только
API (кода стороннего парсера в портале нет). Контур.Фокус на паузе по решению владельца (05.10.2026).

Приложенное владельцем ревью чужой системы скоринга контрагентов (`TASK_11_REVIEW_COMMENTS_RU.md`) взято как перечень
ошибок работы с теми же источниками; сам скоринг (цвета, hard triggers, приоритет по авансу) — нет (ADR-009).

Свойства сервиса (по его документации; живой ответ сверяется пробой):

1. **Ключ в адресе запроса**: `https://parser-api.com/parser/<api>/<метод>?key=…`. Бесплатно — 200 запросов в месяц;
   считаются только ответы `success = 1`. Метода остатка лимита нет.
2. **Ответы разные**: признак успеха `success` / `Success` (КАД) / `done` (ФССП); отказ — `error` и `error_code`:
   40301 ключ, 40302 подписка, 40303 адрес не разрешён (ключ бывает привязан к IP), 40304 / 40305 лимит суток / месяца,
   40001 параметры.
3. **Поиск → детали**: ГИР БО и Федресурс сначала ищут по ИНН (возвращают и чужие записи), детали — по внутреннему id.
   Картотека дел и ФССП отдают страницы.

## Решение

Миграция `044_parser_api.sql`, модуль `backend/src/parserApi/`, ключ — `settings/parserApiKey.ts`.

1. **Справочник по реквизиту, как Контур.Фокус (ADR-015).** В `sources` его нет; допуск — ключ администратора
   (`parserapi.manage`) и рубильник `PARSER_API_ENABLED` (по умолчанию false). Без ключа запросов нет. Спрашиваем только
   ИНН с верной контрольной суммой; два разных ИНН у карточки — не спрашиваем.
2. **Сеть — `net/safeFetch`**: один хост, без перенаправлений; ключ не попадает ни в журнал, ни в текст ошибки.
3. **Наборы, а не методы** (`parserApi/datasets.ts`): finance (ГИР БО: поиск → детали), tax («Прозрачный бизнес»),
   courts (КАД: 24 месяца с первого числа месяца, любая роль, страниц ≤ `PARSER_API_KAD_MAX_PAGES`), fssp, bankruptcy
   (Федресурс: поиск → карточка). Запись поиска берётся только с тем же ИНН. Срок повторной проверки — по набору
   (90 / 30 / 7 / 14 / 7 дней).
4. **Состояние отдельно от данных** (ревью R-07): нет строки — не проверяли; `found` — есть; `not_found` — сервис
   ответил «записей нет»; `partial` — часть (детали или страницы не пришли, причина в `payload.missing`); неудача первого
   запроса — снимка нет, повтор с растущей паузой. Неполное не выдаётся ни за полное, ни за пустое.
5. **Лимит резервируется до каждого запроса** (ревью R-12): строка журнала `pending` под общей блокировкой; оплаченным
   считается только `success = 1`, неудача место освобождает. Сутки — скользящие, месяц — календарный (Москва).
   Свой лимит кончился — проход стоит, срок набора не сдвигается. Отказ сервиса по ключу, подписке, адресу или лимиту
   останавливает проход: очередь не перебирается.
6. **Снимки как есть** (`parser_api_records`): набор целиком (параметры без ключа, ответы по порядку, окно, чего нет),
   новая строка — только при изменении (`sha256-canonical-json@1`). «Проверено» — `parser_api_checks.checked_at`,
   «сведения от» — время первого получения того же ответа (ревью R-14). Карта полей — на чтении (24B, 24C), поэтому
   правка карты после пробы не требует повторных запросов. Таблицы ключуются ИНН без ссылок на компании — слияние их
   не трогает.
7. **В канон не идёт.** Выручка, долги, дела изменчивы, а конвейер не умеет отзывать утверждения (ADR-012, ADR-015).
   Оценки надёжности, баллов и светофора нет (ADR-009): экран показывает числа, их источник и дату.
8. **Кого проверять.** Расписание — только компании «на контроле» (ADR-016): полная проверка стоит 6–9 запросов,
   бесплатный месяц — 25–30 компаний. Остальные — кнопкой «Обновить» в карточке (`sources.manage`, не чаще раза в
   10 минут на набор).

## Последствия

- Перед включением расписания — проба каждого метода (`npm run parserapi -- --probe <метод> <ИНН>`): имена полей без
  значений; карта 24B/24C пишется по ним, а не по документации.
- Ключ, привязанный к IP, с сервера даст 40303, пока исходящий адрес не добавлен в личном кабинете сервиса.
- ГИР БО — тыс. руб., картотека — руб.: единица хранится рядом с числом, в формулах — один масштаб (ревью R-11).
  ФССП: «действующее / окончено / не ясно» по полям окончания, сумма — «по исполнительному документу», не «остаток
  долга» (ревью R-10).
- Новый метод сервиса = строка CHECK `parser_api_requests_method` + шаг набора + расход тарифа: отдельное решение.

## Карты на чтении (этап 24B, 06.10.2026)

Формы сверены с живыми ответами по ПАО «Инград» (ИНН 7702336269). `finance-map@1`: отчёт ГИР БО за год — собственный
(`current`); пересчёт этого года в следующем отчёте (`previous`) его не подменяет; несколько отчётов за год — наибольший
`correction_number`; тыс. руб. × 1000; знак расходных строк в ГИР БО от отчёта к отчёту разный — «Проценты к уплате» по
модулю, строки прибыли со знаком. `tax-map@1`: суммы в рублях, недоимка — последняя выгрузка ФНС по (`year`, `period`),
прежние — итогом; это сведения ФНС на дату выгрузки, а не «долг сейчас». Обе карты — чистые функции; незнакомая форма —
`recognized: false` с причиной.

## Суды, ФССП, банкротство (этап 24C, 06.10.2026)

`courts-map@1`: роль компании — по её ИНН среди сторон дела; вид — по CaseType; роль в деле о банкротстве (Б) не говорит,
чьё банкротство, — о самой компании говорит только ЕФРСБ; сумм исков в поиске картотеки нет (только в карточке дела), и
по одному запросу на дело их не добираем — тариф. `fssp-map@1`: сервис не присылает пустые поля, поэтому «нет даты
окончания» = «не окончено по данным ФССП», а не «действует и взыскивается»; основание без даты — статус не ясен; «Сумма
долга», «Остаток долга по исполнительному документу» и «Исполнительский сбор» не складываются, остаток — только где ФССП
его указала (ревью R-10). `bankruptcy-map@1`: «есть в ЕФРСБ» — не вывод о банкротстве.

## Суммы исков из карточек дел (06.10.2026, решение владельца)

Владелец: «арбитражные дела — можем выводить с суммами?». В поиске картотеки сумм нет; они в карточке дела
(`arbitr_api/details_by_id`, `InstanceEvents[].ClaimSum`), а карточка — платный запрос на каждое дело. Решение владельца:
спрашивать только **экономические споры (CaseType Г), где компания — ответчик**, и **каждое дело один раз**.

1. Миграция `048_parser_api_case_cards.sql`: `parser_api_case_cards` — строка на дело (UNIQUE `case_id`, ответ как есть),
   метод `kad_details` в CHECK журнала. Ссылок на компании нет; карточка общая для сторон дела — полученную для одной
   компании видит и другая.
2. Выбор дел — `map/courts.ts::claimCardTargets` из последнего снимка картотеки (та же роль по ИНН, что на экране), новые
   сверху; загрузка — `parserApi/caseCards.ts`: тот же резерв лимита до запроса, остановки как у наборов, два сбоя —
   конец прохода, не больше `PARSER_API_KAD_CARDS_MAX` (10) за проверку компании, остальное — следующей проверкой
   картотеки. Расписание спрашивает карточки после наборов всех компаний прохода (наборы важнее сумм). «Обновить» —
   после ответа, в фоне (карточки вместе не уложатся в ожидание прокси); экран видит `claimsFetching` и перечитывает блок
   каждые 10 с, пока загрузка идёт. Свежая картотека (< 10 минут) не мешает догрузить недостающие карточки.
3. Карта `case-card-map@1` (`map/caseCard.ts`), на чтении: ClaimSum событий первой инстанции (нет такой — всех); «при
   подаче» — самое раннее событие с суммой > 0, другая сумма самого позднего — «позже в карточке» (уточнение); 0 или нет
   поля — «сумма в карточке не указана», а не 0 ₽. Форма — по документации сервиса; перед доверием числам —
   `npm run parserapi -- --probe kad_details <ИНН> --id <CaseId>` (печатает инстанции и типы событий с суммой, без сумм).
4. Экран: «иск 1,3 млн ₽» в строке дела, строка «Суммы исков — получены у K из N», подпись «требование истца по карточке на
   дату её получения, а не долг компании». Итога по делам нет: сумма исков — не долг (ADR-009, brief).
5. Повторно карточка не спрашивается: уточнение иска после даты получения портал не увидит. Перезапрос по незавершённым
   делам — отдельное решение (расход тарифа).

## Сообщения ЕФРСБ, основания ФССП, «Прозрачный бизнес» — по документации сервиса (06.10.2026)

Владелец передал архив системы проверки контрагентов `counterparty-risk` (документация parser-api.com по картотеке,
ФССП, Федресурсу, ГИР БО, ЕГРЮЛ и «Прозрачному бизнесу», её ревью TASK 11 и сырые ответы сентября 2026: 15 списков
сообщений ЕФРСБ, 415 сообщений, 217 ответов ФССП, 229 карточек «Прозрачного бизнеса», 201 карточка дела). Сверка с нашим
модулем дала три пробела; скоринг и цвета из архива не берём (ADR-009).

1. **ЕФРСБ: сообщения должника вместо карточки (`bankruptcy-map@2`, миграция 049).** `get_org` о банкротстве ничего не
   говорит — набор `bankruptcy` больше его не спрашивает. Цепочка: `search_ur` (orgCode) → `get_org_messages` (список,
   новые сверху; страницы по `from_record` = сколько получено, ≤ `EFRSB_MAX_LIST_PAGES` = 5; на живых ответах до 118 записей
   приходило одной страницей) → `get_message` только для неаннулированных «Сообщение о судебном акте», новые первыми,
   ≤ `EFRSB_MAX_ACTS` = 5 за проход. Сообщение ЕФРСБ не меняется (аннулирование — отдельное сообщение и пометка
   «(аннулировано)» в типе списка), поэтому карточка, полученная прошлым снимком, переносится без запроса
   (`IDatasetOptions.previous`, `store.latestRecord`) и снимок без изменений новой строкой не пишется. Компания не в ЕФРСБ
   — по-прежнему один запрос.
   Карта: вид сообщения по типу (`messageKind`: судебные акты, собрания, требования кредиторов, сделки, субсидиарная
   ответственность, торги, имущество, аннулирование, другое — незнакомый тип не прячется); акт — словами ЕФРСБ, `actEffect`
   только раскладывает: введение процедуры, прекращение, завершение, «процедурное» (продление, смена управляющего).
   «Процедура по последнему акту» — самый новый неаннулированный акт, меняющий процедуру; продление после него — строкой
   «позже»; незнакомая формулировка процедурой не считается. Старый снимок (`@1`) — «сообщения не запрашивались».
   **Пробел источника, а не наш:** намерения кредиторов обратиться в суд публикуются на fedresurs.ru (ЕФРСФДЮЛ), не в
   ЕФРСБ; сервис их не отдаёт (ревью TASK 11, DEF-001). «Записей в ЕФРСБ нет» — не «рисков нет», экран так и пишет.
2. **ФССП: основание окончания по 229-ФЗ (`fssp-map@2`).** ФССП пишет ссылку на закон («ст. 46 ч. 1 п. 4»); `stopMeaning`:
   ст. 46 ч. 1 п. 3 — не найдены должник, имущество или счета; п. 4 — нет имущества; прочие пункты ст. 46 ч. 1 и ст. 47 ч. 1
   п. 4 — возвращено взыскателю; ст. 47 ч. 1 п. 1–2 — фактическое исполнение, п. 6 — удержание периодических платежей,
   п. 7 — должник признан банкротом, п. 8 — ликвидация, п. 9 — срок давности; ст. 43 и ст. 47 ч. 1 п. 5 — прекращение;
   незнакомое — «другое основание», ссылка рядом. «Окончено» ≠ «погашено»: по ст. 46 ч. 1 п. 3–4 долг не взыскан —
   `ended.uncollected` с суммой долга «у K из N». В живых ответах: п. 7 ст. 47 — 100 из 195 оконченных, ст. 46 п. 3–4 — 91.
   `done = 0` без `error` (2 из 217) — нестабильность источника: повтор с паузой, как прежде.
3. **«Прозрачный бизнес» (`tax-map@2`).** Добавлены `offenses` (штраф за год; `[]` — ФНС нарушений не указала, нет поля —
   не знаем), `status` словами ФНС (экран показывает только не «Действующая…»: действующий статус уже в шапке из ЕГРЮЛ) и
   `director[].count`/`owner[].count` — во скольких юрлицах человек в той же роли, считая эту. Порога «массовости» нет.
4. **«Новое» (`news@1`, вид `bankruptcy`).** Компания появилась в ЕФРСБ или в списке её сообщений — новое «Сообщение о
   судебном акте» (сравнивается список, а не полученные карточки: догрузка старого акта — не новость). Первый список после
   снимка `@1` — начальная загрузка, новостью не считается.
5. **Сверка карты соседнего этапа:** `case-card-map@1` совпала с 187 живыми карточками дел архива — `Cases[0].CaseInstances[]
   .Name` «Первая/Апелляционная/Кассационная инстанция», `ClaimSum` — число; сумма > 0 в первой инстанции у 141 дела, только
   в других инстанциях — ни у одного; самое раннее событие с суммой — «Заявление».

Не делали: ЕГРЮЛ через parser-api (есть Контур.Фокус, ADR-015), `search_limit_org` и `search_dis` (отдельный платный запрос
на компанию/человека), поиск по сообщениям ЕФРСБ (`search_messages` — обход реестра, не проверка компании), PDF судебных
актов (`pdf_download`), этапы банкротства из событий карточки дела (`EventContentTypeName`) — их даёт ЕФРСБ.

## Лимиты по сервисам тарифа (06.10.2026, решение владельца)

Личный кабинет parser-api.com показал: тариф считается **по сервисам** — arbitr, fssp, fedresurs, nalog_pb, nalog_bo
(и nalog_egrul, mosgorsud, ras_arbitr, которых портал не спрашивает), у каждого свои «лимит в день», «лимит в месяц» и
срок оплаты («Минимальный» — 1000 и 1000). Общий счётчик портала на все сервисы (п. 5) занижал доступное в пять раз и
одним отказом сервиса останавливал проверку остальных. Решение владельца: «надо добить лимиты».

1. Сервис — первая часть пути метода без `_api` (`client.ts::serviceOf`); набор → сервис — `datasets.ts::DATASET_SERVICE`.
   `PARSER_API_DAILY_LIMIT` / `PARSER_API_MONTHLY_LIMIT` — предел портала **на каждый сервис**; резерв — под блокировкой
   сервиса и по журналу его методов (проверка ключа — в nalog_bo). Миграции нет: журнал уже хранит метод.
2. Ключ не принят или адрес не разрешён — по-прежнему стоп всего прохода. Лимит (свой или 40304 / 40305) и подписка
   (40302) — стоп только сервиса: его наборы в этом проходе не спрашиваются (и у следующих компаний прохода), остальные
   идут; срок проверки не сдвигается (`refresh.ts`, `blocked`).
3. Пауза сервиса (`servicePauses.ts`, в памяти процесса): после отказа по суточному лимиту — 3 часа, по месячному и
   подписке — сутки; успешный ответ снимает. Расписание не берёт наборы сервиса на паузе и без места в своём лимите
   (`dueParserApiTargets(…, datasets)`) — иначе компании с непроверенной картотекой стояли бы первыми всегда. Кнопка
   «Обновить» паузу не смотрит (продлённую подписку проверяют сразу); исчерпанный сервис — предупреждением, ошибка — только
   если не обновилось ничего.
4. Месяц портала — календарный по Москве, у сервиса — срок оплаты, и запросы того же ключа извне портал не видит: точный
   отказ всё равно приходит от сервиса и ставит паузу.
