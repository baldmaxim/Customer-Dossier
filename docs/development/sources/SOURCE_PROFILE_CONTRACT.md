# Контракт профиля источника и подключение (этап 16)

Версии: `source-profile@1` (meta профиля), `source-health@1` (состояние для оператора), адаптеры `site@1`, `tg_web@2`, `telegram_bot_text@1`.
Код: `backend/src/ingest/profileMeta.ts`, `sourceHealth.ts`, `capabilities.ts`; профили адаптеров — `ingest/sites/profile.ts`
(строгая схема) и `ingest/telegram/webCrawler.ts::telegramProfileSchema`. Шаблоны — `site-profile.template.json`,
`telegram-profile.template.json` (draft, адрес-заглушка `.invalid`, основания пустые; проверяются unit-тестом).

## 1. Профиль

Профиль = настройки адаптера (как раньше) + `meta` (`source-profile@1`), в `sources.config`.

| Поле meta | Смысл | По умолчанию |
|---|---|---|
| `owner` | кто отвечает за источник у оператора | `null` |
| `collectionMethod` | `rss` / `html_list` / `telegram_web_preview` / `telegram_bot` | `unknown` |
| `allowedOrigins` | хосты для сверки с allowlist; сеть определяет `safeFetch` | `[]` |
| `allowedPathPrefixes` | **сужает** обход сайта: записи вне префиксов не открываются (`layout_stats.outside_path_prefix`) | `[]` — без ограничения |
| `expectedCompleteness` | полнота по контракту источника; фактическая — по происхождению редакции | `unknown` |
| `dateNotes`, `restrictions` | форматы дат, ограничения условий | пусто |
| `frequency.pollIntervalSec`, `maxRequestsPerRun` | бюджет запросов (справочно; лимиты прохода — в настройках адаптера) | `null` |
| `permissionsEvidence.collect / aiProcessing` | ссылка на основание оператора `{reference, checkedAt, checkedBy}` | `null` |
| `reviewStatus` | `draft` / `operator_checked` | `draft` |

**Допуск профилем не выдаётся.** Сбор и ИИ-обработка разрешаются только `sources.access_status` / `ai_processing_status`
(оператор в админке, с основанием). Проверка схемы профиля, заполненное `permissionsEvidence` и `operator_checked` ничего не открывают.
Публичность адреса — не основание.

## 2. Возможности адаптеров (`ingest/capabilities.ts`)

| Адаптер | История | Полный текст | Правки | Удаления | Медиа | Даты |
|---|---|---|---|---|---|---|
| сайт RSS | limited: окно ленты | limited: content:encoded полон только по `rssContentIsFull`, иначе статья по `bodySelector`, сбой — анонс | limited (`refetchKnown`) | not_observable | limited: отмечаются, OCR нет | limited: без даты — unknown |
| сайт HTML-список | limited: до `maxPages`, хвост — следующим проходом | limited: только совпавший `bodySelector` без `truncatedSelector` | limited | not_observable | limited | limited |
| Telegram t.me/s/ | limited: свежие посты + ограниченная догрузка разрыва; первый запуск историю не собирает | текст поста; медиа-пост — caption_only | limited: окно перепроверки | not_observable | limited | дата поста; дата правки не видна |
| форвард-бот | not_supported: только пересланное боту | пересланный текст | supported (`edited_message`) | not_observable | limited | дата правки есть |

HTML-адаптер для сайтов есть (этап 05A) — прежний вывод «только RSS» к текущему коду не относится.

## 3. Состояние источника (`source-health@1`)

| Состояние | Когда | Что делать |
|---|---|---|
| `never_run` | попыток не было | «пусто» ничего не значит; проба/проход после допуска |
| `policy_blocked` | нет действующего допуска на сбор, или источник ответил 401/403/451, или допуск отозван во время прохода | основание и допуск оператора; обход ограничений не делается |
| `degraded` | `parser_degraded` (селектор/лента дали 0 при ожидаемых записях, цикл пагинации), `config_invalid`, `identity_uncertain` | сверить профиль пробой; «новостей нет» не выводится |
| `temporary_error` | сеть, 5xx, 429 (`Retry-After`), размер | повтор с паузой по расписанию |
| `partial_history` | успех, но записан разрыв Telegram, недочитанный хвост сайта, `max_pages` / `failed` / `pagination_loop` | дождаться догрузки; границы разрыва видны |
| `healthy` | успех без записанных разрывов | — |

Во всех состояниях `coverage.totalKnown = false`: общее число публикаций источника не наблюдается, количество собранного — не полнота.
Сбор и ИИ показываются раздельно (`aiAllowed`).

## 4. Курсоры и повторы (без изменений контракта 05A/05B)
Записи страницы и курсор — одна транзакция; сбой поздней страницы оставляет курсор на недочитанной странице (`backlogNext`/`gap`);
повтор не удваивает редакции (личность `(source_id, item_key)`), изменённый текст — новая редакция той же публикации.
429 — пауза по `Retry-After` без роста счётчика неудач. Этап 16 добавил остановку цикла пагинации в пределах прохода.

## 5. Сеть
Только `net/safeFetch.ts`: allowlist хостов профиля, запрет внутренних адресов в момент соединения, проверка каждого редиректа,
лимиты времени и размера; ссылки из текста статьи не открываются. ETag/Last-Modified — только если сервер их отдаёт.

## 6. Подключение (runbook)
Только после явного списка адресов и оснований от владельца. По одному источнику: сначала сайт, потом канал.

1. Регистрация без сети: `npm run ingest:once -- --add-site <url>` или `--add <канал>` (на паузе, допуск `unknown`).
2. Профиль из шаблона → заполнить селекторы/лимиты/`meta` → `--site-profile <ключ> --file <profile.json>` или
   `--telegram-profile <канал> --file <profile.json>` (схема проверяется до записи; допуск не меняется).
3. Оператор в админке ставит допуск **на сбор** с основанием (ИИ — отдельно и только если есть основание).
4. Проба без записи: `--probe-site <ключ>` (1 страница, 3 записи; в админке «Проба») или `--probe <канал>`.
   Смотреть: исход, `layout_stats`, образцы текста и их полноту. Проба не пишет публикаций и курсора.
5. Один ограниченный проход: `--source <ключ>` при `INGEST_ENABLED=false` (фон выключен). Результат: состояние, покрытие, редакции.
6. ИИ-обработка — только при отдельном допуске и явной постановке запуска (этап 15B), без автопубликации.
7. Результат вносится в `VALIDATED_SOURCES.md` отдельно по сбору, полноте текста и ИИ-допуску. Без прогона пользователя таблица пуста.
Остановка: статус `paused` или отзыв допуска; удаление источника с документами запрещено.

## 7. Источник-реестр (`mode: registry_api`, этап 20A)

Реестр подключается тем же порядком §6 и теми же командами: это режим профиля, а не отдельный вид источника
(`sources.kind` остаётся `website`). Отличия по шагам:

- шаг 2 — шаблон `registry-profile.template.json`. Вместо селекторов заполняются шаблоны адресов
  (`endpoints.object` с `{id}`, при обходе каталога `endpoints.list` с `{offset}`), перечень записей
  (`objectIds`, `developerIds`), путь к записи в ответе (`responsePath`), карта полей и якоря идентичности
  (`identity`: название, город, адрес, застройщик, ИНН, группа компаний, дата сведений);
- **имена полей в шаблоне не проверены** и приведены как ориентир: сверить их с живым ответом — работа шага 4;
- шаг 4 — та же `--probe-site <ключ>` и та же кнопка «Проба». Смотреть: исход, `layout_stats.object_fields`
  (сколько полей карты реально нашлось) и образец текста снимка — в нём должны стоять строка застройщика
  с ИНН и нужные поля. Ноль полей при HTTP 200 означает, что карта полей не совпала с ответом;
- шаг 6 — **ИИ-допуск реестру не выдаётся**: записи уже структурированы, модель в их разборе не участвует.

Отказ источника читается по исходу запуска и не толкуется как пустой реестр: `blocked` — 401/403/451,
`rate_limited` — 429 с паузой до `Retry-After`, `parser_degraded` — ответ не разобран как JSON или карта полей
ничего не нашла, `config_invalid` — профиль негоден (запросов не было).

Кириллический адрес записывается как есть (`https://наш.дом.рф/...`); в allowlist и в `meta.allowedOrigins`
хост указывается в punycode (`xn--80az8a.xn--d1aqf.xn--p1ai`), путь в `allowedPathPrefixes` — в процентной
кодировке.
