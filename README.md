# Досье Заказчика

Локальный портал досье участников строительного рынка России. Собирает тексты из
согласованных Telegram-каналов и сайтов, структурирует их локальной моделью в LM Studio
и показывает, что известно о компании — с дословными цитатами и источниками.

Карточка компании: объекты и роли на них, контрагенты на объектах, лента упоминаний
с дословными цитатами, события (срывы сроков, суды, смена подрядчика) и объяснимые сигналы:
идентификация и полнота данных, опыт по объектам, публикации и события — у каждого числа видно
правило и исходные записи. Итоговой оценки надёжности нет и не будет: **это не проверка контрагента**.

Рабочий сценарий: найти компанию среди одноимённых по реквизитам → записать обращение (объект, корпус, вид работ,
заявленная роль и заказчик) → посмотреть, что установлено в источниках и что только заявлено, кто заказывает работы,
контекст объекта и вопросы контрагенту → разобрать противоречия в «Проверке». Досье строится из сохранённых данных
и работает при выключенной модели.

---

## Что нужно

| | |
|---|---|
| Node.js | 20+ (проверено на 24) |
| PostgreSQL | 14+ (проверено на 17 и 18) |
| LM Studio | с загруженной моделью, локальный сервер включён |
| Видеокарта | 8 ГБ VRAM хватает для Qwen3-8B Q4_K_M |

Telegram API (`api_id`/`api_hash`) **не нужен**. Публичные каналы читаются со страницы
`t.me/s/<канал>` обычным GET-запросом, закрытые — пересылкой боту. Публичность канала
не заменяет основания для сбора и ИИ-обработки: допуск каждого источника подтверждает оператор.

## Установка

### 1. База данных

```bash
createdb tg_info
```

### 2. Настройки

```bash
cd backend
cp .env.example .env
```

Заполните в `.env` минимум `DATABASE_URL`. Фоновые задания по умолчанию выключены,
API слушает только `127.0.0.1`.

### 3. Схема

```bash
cd backend
npm ci
npm run migrate -- --dry   # план: ничего не пишет в базу, destructive помечены
npm run migrate            # применить
```

Повторный запуск безопасен: применённые миграции пропускаются.

**Миграция `009_switch_to_russia.sql` меняет существующие данные** (обнуляет суммы
событий, переименовывает колонку реквизитов). Раннер не применит её без флага
`--allow-destructive`. На базе с данными — сначала `pg_dump`, потом решение.

### 4. LM Studio

Загрузите **Qwen3-8B**, квантование **Q4_K_M** (~4.9 ГБ). Настройки:

- контекст **8192**
- Flash Attention — **включить**
- KV cache — **Q8**
- запустить локальный сервер (вкладка Developer → Start Server)

Проверка из проекта:

```bash
npm run pipeline:once -- --check
```

> `/no_think` в системном промпте обязателен и уже прописан в коде. Без него Qwen3
> уходит в режим рассуждения, сжигает `max_tokens` и возвращает пустой ответ.

### 5. Запуск и вход

```bash
cd backend && npm run dev                  # API на http://127.0.0.1:4100
cd frontend && npm ci && npm run dev       # UI на http://127.0.0.1:5173
```

При первом запуске без `OPERATOR_TOKEN` в `.env` создаётся файл
`backend/.local/operator-token` (в git не попадает). Токен из него вводится на экране
входа. В браузере остаётся только серверная сессия в HttpOnly-cookie.

Фоновые задания включаются явно в `backend/.env` (только `true`/`false`/`1`/`0`):

| Флаг | Что делает |
|---|---|
| `INGEST_ENABLED` | опрос источников по расписанию (только с допуском к сбору) |
| `METRICS_AUTO_REFRESH` | пересчёт агрегатов карточки раз в 10 минут |
| `BOT_ENABLED` | приём форвардов ботом (нужны `TG_BOT_TOKEN` и допуск `manual:bot`) |
| `PIPELINE_ENABLED` | разбор моделью новым конвейером: запуски и наборы кандидатов (карточки меняет только публикация) |
| `REPROCESS_AUTO_PUBLISH` | публиковать наборы автоматически, без проверки человеком (по умолчанию false) |
| `MERGE_APPLY_ENABLED` | применение и отмена слияния сущностей (по умолчанию false: предпросмотр и журнал доступны) |

### 6. Источники и допуск

1. Добавьте источник в админке или CLI — он заводится **на паузе** с допуском «не подтверждён»,
   без сетевых запросов.
2. В админке → «Источники» → «Допуск»: отдельно решение о сборе и об ИИ-обработке,
   основание, ответственный, срок. Решение пишется в журнал.
3. Только после этого: проба вёрстки и включение опроса.

```bash
npm run ingest:once -- --add имя_канала
npm run ingest:once -- --probe имя_канала    # после допуска: сколько узлов нашёл каждый селектор
npm run ingest:once -- --source имя_канала   # разовый прогон
```

Если `--probe` показывает `wrap = 0` при большой странице — вёрстка `t.me/s/` изменилась,
парсер надо чинить (`TG_SELECTORS` в [telegramWeb.ts](backend/src/ingest/telegramWeb.ts))
до включения опроса.

За проход читается первая страница; если с прошлого прохода вышло больше постов, чем на ней,
разрыв записывается в курсор и догружается не более `maxPagesPerRun` страниц (профиль источника).
При первом запуске история канала не собирается — граница видна в покрытии запуска. Удаления
постов не наблюдаются, правки — только у постов первой страницы.

### 7. Форвард-бот (для закрытых каналов)

1. Создайте бота у [@BotFather](https://t.me/BotFather), получите токен.
2. Узнайте свой Telegram user id (например, у [@userinfobot](https://t.me/userinfobot)).
3. Впишите в `.env`: `TG_BOT_TOKEN`, `TG_BOT_ALLOWED_USER_IDS`, `BOT_ENABLED=true`.
4. Подтвердите допуск источника «Форварды в Telegram-бота» в админке.

> Пустой `TG_BOT_ALLOWED_USER_IDS` означает **не принимать никого**. Это не оплошность:
> бот, открытый всем, — прямой канал вливания произвольного текста в вашу базу.

Бот получает только то, что ему переслали, и не является архивом канала: сообщения, пришедшие,
пока он был выключен дольше срока хранения обновлений Telegram, не придут. Повтор обновления
после перезапуска не дублирует сообщение; правка пересланного сообщения сохраняется новой редакцией.

## Команды

### Ингест

```bash
npm run ingest:once -- --add <канал>        # добавить публичный канал (пауза, без допуска)
npm run ingest:once -- --add-site <url> [--rss <лента>]  # добавить сайт без сетевых запросов
npm run ingest:once -- --probe <канал>      # сверить селекторы с живой страницей (нужен допуск)
npm run ingest:once -- --probe-site <ключ>  # проба: 1 страница, до 3 записей, ничего не сохраняет (нужен допуск)
npm run ingest:once -- --site-profile <ключ> --file profile.json  # проверить и записать профиль сайта
npm run ingest:once -- --remove <ключ>      # удалить источник без документов
npm run ingest:once -- --env-check          # какие ключи видит программа в .env
npm run ingest:once -- --bot-check          # проверить форвард-бота
npm run ingest:once -- --source <ключ>      # прогнать один источник (нужен допуск)
npm run ingest:once                         # все просроченные источники с допуском
npm run ingest:once -- --stats              # документы, очередь, доля дублей
```

### Пайплайн извлечения

Разбор идёт новым конвейером (этап 03B): запуск по редакции → чанки → набор
кандидатов → публикация набора. Карточки меняются только публикацией, одной
транзакцией; повтор публикации ничего не дублирует, устаревший разбор не
перезаписывает новый без `--allow-stale`. Заблокированы (legacy-запись):
`--retry-skipped`, `--renormalize` и `--recheck` без `--dry` (ключи пересчитывает
версионный `npm run backfill:identity -- --renormalize` на копии базы).

```bash
npm run pipeline:once -- --reextract --limit 20   # поставить запуски (лимит обязателен, ≤ 200)
npm run pipeline:once                          # выполнить поставленные запуски (--loop — до конца очереди)
npm run pipeline:once -- --runs                # запуски: статус, покрытие, наборы
npm run pipeline:once -- --preview <набор>     # что изменит публикация
npm run pipeline:once -- --publish <набор>     # опубликовать (--allow-stale — отдельным решением)
npm run pipeline:once -- --retry               # новые запуски вместо failed/partial
npm run pipeline:once -- --check              # LM Studio поднят? модель загружена?
npm run pipeline:once -- --stats              # очередь и доля неудачных вызовов
npm run pipeline:once -- --errors             # последние отказы с текстом ошибки
npm run pipeline:once -- --skipped            # тексты, признанные нерелевантными
npm run pipeline:once -- --doc <id>           # документ целиком: текст, разбор, канон
npm run pipeline:once -- --queue              # очередь проверки: идентичность, утверждение и отрицание, исправление, спор
npm run pipeline:once -- --audit              # дубли, роли, объекты-компании, выборка
npm run pipeline:once -- --renormalize --dry  # что изменил бы пересчёт ключей
npm run pipeline:once -- --recheck --dry      # какие города и адреса не подтверждены
npm run pipeline:once -- --shadow 30          # прогнать текущую модель, не трогая карточки
npm run pipeline:once -- --compare            # сравнить модели на одних документах
npm run pipeline:once -- --merges             # очередь на ручное слияние
npm run pipeline:once -- --merge <id>         # предпросмотр: реквизиты, конфликты, что переносится
npm run pipeline:once -- --merge <id> --yes   # применить (MERGE_APPLY_ENABLED=true)
npm run pipeline:once -- --merge-history      # журнал слияний
npm run pipeline:once -- --merge-undo <id>    # отменить, если после слияния ничего не изменилось
npm run pipeline:once -- --reject <id>        # отклонить пару
```

С этапа 06 модель отвечает по схеме extract@3: участие в объекте, прямой договор и корпоративная связь —
разные утверждения со своей цитатой; отрицание, план и слух сохраняются, но ролью и событием карточки не
становятся. Ответ, противоречащий цитате, ждёт проверки и не публикуется. Откат для новых запусков —
`EXTRACT_SCHEMA_VERSION=extract@2`. Качество модели на синтетическом корпусе — `npm run benchmark:model`
(только вымышленные тексты, база не нужна); это не оценка точности на реальных данных.

Слияние (этап 04) не удаляет исходную сущность и ничего не угадывает: разные
реквизиты одного типа, бренд и юрлицо, разные города, корпус и комплекс — блокируются.
Отмена возможна, пока после слияния не появилось новых данных; иначе выдаётся план
ручного разнесения.

### Проверки

```bash
cd backend
npm run typecheck
npm test                     # unit: без сети и БД, внешний DATABASE_URL игнорируется

# интеграционные: только выделенная локальная база tg_info_test с маркером
docker compose -f test-db/docker-compose.yml up -d --wait
TEST_DATABASE_URL=postgresql://tg_test:tg_test@127.0.0.1:55433/tg_info_test npm run test:integration
docker compose -f test-db/docker-compose.yml down

npm run metrics:refresh      # снимок сигналов на текущий срез (-- --cutoff ISO — на заданный)
npm run backfill:revisions   # dry-run переноса старых документов в публикации/редакции; запись: -- --apply
npm run backfill:assertions  # затем: dry-run переноса канона в утверждения и доказательства; запись: -- --apply
cd ../frontend && npm run build && npm run icons:generate
```

Пошаговая проверка этапа с ожидаемыми результатами — [docs/development/TESTING_LOCAL.md](docs/development/TESTING_LOCAL.md).
Интеграционный профиль откажется работать, если адрес не loopback, имя базы не
`tg_info_test*`, нет маркера или цель совпадает с `DATABASE_URL`. Он пересоздаёт схему
`public` тестовой базы — ни на что, кроме неё, его не направлять.

## Как это устроено

```
источники → raw_documents → extractions → канонический слой → карточка
 t.me/s/     дедуп по        LM Studio     компании, объекты,   цитаты,
 RSS сайтов  нормализ.       + проверка    роли, события        события
 бот/форма   хэшу            цитат
```

Как пользоваться порталом — [docs/USAGE.md](docs/USAGE.md).
Подробности архитектуры и принятых решений — в [CLAUDE.md](CLAUDE.md),
промпты — в [docs/PROMPTS.md](docs/PROMPTS.md), план развития —
`prompts/Customer_Dossier_Prompts/` и [docs/development/](docs/development/).

### Что стоит знать до правок

**Цитата — доказательство того, что написано, а не истинности.** Каждая сущность несёт
дословную цитату, имя сущности обязано стоять внутри неё; ИНН, сумма и город принимаются
только из собственной цитаты. Модель на 8B охотно «вспоминает» компании, которых в тексте
нет; подставить выдуманное название в реальный фрагмент она не может.

**Слияние компаний асимметрично и сейчас выключено.** Слить легко, разлить почти
невозможно. Резолвер в спорных случаях создаёт **новую** компанию и кладёт пару в очередь;
само слияние вернётся с проверкой реквизитов и откатом (этап 04).

**Серый индекс — не «всё хорошо», зелёный — тоже.** Отсутствие сигналов в собранных
публикациях ничего не говорит о надёжности контрагента.

## Ограничения

- Один оператор на этой же машине. Доступ из сети, несколько пользователей и
  публичное размещение в этой версии не поддерживаются.
- Читаются только **публичные** Telegram-каналы и только с подтверждённым допуском.
  Закрытые — вручную через бота.
- Данные собраны из новостей, а не из реестров (ЕГРЮЛ, ЕИСЖС, картотека дел).
  Это повод задать вопросы, а не проверка контрагента.
- Сайты читаются только через RSS. Если ленты нет, источник придётся добавлять
  вручную или обходиться Telegram и вставкой текста.
- Разбор моделью публикуется в карточки только после предпросмотра и `--publish`
  (или при `REPROCESS_AUTO_PUBLISH=true` — без проверки человеком). Сигналы и
  статистика подрядчиков — снимок на срез: после новых публикаций нужен `npm run metrics:refresh`.
